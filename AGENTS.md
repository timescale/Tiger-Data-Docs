# AGENTS.md

Single source of truth for AI coding agents working in this repository (Claude Code, Cursor, Warp, and others). `CLAUDE.md` imports this file, so keep all agent guidance here.

## Project Overview

Tiger Data Docs is a documentation site built with **Astro 6 + Starlight + Stainless Docs** (`@stainless-api/docs`). It covers Tiger Cloud and TimescaleDB (including self-hosted and Managed Service for TimescaleDB). Deployed on Vercel.

**Node requirement:** >=22.12.0. Uses pnpm.

## Commands

```bash
pnpm dev              # Start dev server at localhost:4321
pnpm dev:local        # Dev server without Stainless (DOCS_LOCAL_WITHOUT_STAINLESS=1)
pnpm build            # Production build (runs astro sync as prebuild)
pnpm build:local      # Production build without Stainless
pnpm preview          # Preview production build
pnpm format           # Prettier formatting
pnpm lint:prose       # Vale prose lint on changed *.md/*.mdx (--all for everything)
pnpm lint:links       # Build with link checking (CHECK_LINKS=true)
```

**Stainless auth:** API reference generation requires `stl auth login` or `STAINLESS_API_KEY` in `.env`. The `dev:local` / `build:local` variants skip Stainless for faster local work.

## Architecture

### Content

- **MDX docs** live in `src/content/docs/`, organized into seven top-level sections (also the site's tabs): `get-started`, `learn`, `build`, `migrate`, `integrate`, `reference`, `deploy`.
- **Reference content** under `reference/`: `timescaledb/` (SQL function reference), `toolkit/` (Toolkit function reference), and `configuration/` (PostgreSQL/TimescaleDB settings). The Tiger Cloud REST API reference is auto-generated by the `stainlessDocs()` integration from the `tiger-cloud` Stainless project and nested under the Reference tab (no source directory in the repo).
- **Partials** (`src/partials/_*.mdx`) — 300+ reusable MDX snippets imported to reduce duplication. Partials use an underscore prefix.
- **Sidebar navigation and tabs** are defined in `astro.config.ts` (large file, ~1400 lines) — this is the authoritative source for nav structure and redirects.

### Constants System (critical)

All product/brand names are centralized in `src/constants.ts`. Import as:

```ts
import * as C from "@constants";
```

Then use `{C.CLOUD_LONG}`, `{C.PG}`, `{C.TIMESCALE_DB}`, etc. in MDX content. **Never hardcode "PostgreSQL" or "Postgres" in prose** — use `{C.PG}`. The `TigerData.ProductConstants` Vale rule nudges literals toward their constant. Exceptions: inside backticks or URLs. Treat `src/constants.ts` as the source of truth for available constants.

### TypeScript Path Aliases

- `@components/*` → `src/components/*`
- `@constants` → `src/constants.ts`
- `@partials/*` → `src/partials/*`

### Custom Components

Key overrides and components in `src/components/`:

- `Callout.astro` — custom styled callout (Vite aliases `@stainless-api/docs/components` Callout to this).
- `Header.astro`, `Footer.astro`, `PageTitle.astro`, `PageNavigation.astro` — Starlight overrides.
- `PageSidebar.astro` + `LearnMore.astro` — right-rail "Learn more" card driven by per-page frontmatter (`learnMore:` block). Auto-hides when absent. Full authoring guide: [`src/components/LearnMore.README.md`](./src/components/LearnMore.README.md). Prefer this over one-off "related content" patterns.
- `NumberedList.astro` / `NumberedList.tsx` / `NumberedItem` — ordered step components for procedures.
- `AuthorByline.astro`, `SinceRelease.astro`, `ChangelogEntry.astro` (+ `ChangelogFilter`/`ChangelogTag`), `Glossary/`, `IntegrateOverview.astro`, `IntegrateToc/`, `BuildToc/`, `HeaderSearchBar.astro`.
- React `.tsx` components for interactive pieces: `CopyToClipboard`, `Prerequisites`.

### Custom Plugins

- `src/plugins/remark-resolve-constants-in-headings.ts` — resolves `{C.CONSTANT}` syntax in headings.
- `src/plugins/rehype-base-path.ts` — adds `BASE_PATH` to relative URLs.

### Content Schema

Defined in `src/content.config.ts`. Extends Starlight's `docsSchema` with custom fields:

- `pageLabels` — tags like "Experimental", "Popular feature", "Optional".
- `overviewDescription` — dropdown descriptions.
- `integrationSchema` — metadata for the Integrate section.
- `learnMoreSchema` — the right-rail card (see Custom Components).
- `seoDescription` (optional) — SEO/social summary that doesn't affect the sidebar subtitle. If both `description` and `seoDescription` are set, `description` wins for meta and sidebar. Implemented in `src/components/Head.astro`.

### Theming

`theme.css` defines CSS custom properties (accent, background) and uses the CSS `light-dark()` function for light/dark switching. Additional tokens in `src/styles/`.

## Content Conventions

House prose style follows the Google developer documentation style guide, enforced by Vale (`.vale.ini`), plus the TigerData-specific rules below. Accepted product/brand/feature spellings live in the `TigerData` vocabulary (`.github/styles/config/vocabularies/TigerData/accept.txt`). The human-facing version of this guidance lives in `src/content/docs/get-started/contributing.mdx` (published at `/get-started/contributing`).

- **Use constants for product names.** `TigerData.ProductConstants` nudges literal product/brand names toward their constant (suggestion). It covers only product/brand-name constants (the `// General` and `// Products` sections of `src/constants.ts`). Feature/service/project common-nouns (hypertable, chunk, service, job, columnstore, and the like) are accepted in the Vale vocabulary instead. The rule is hand-maintained at `.github/styles/TigerData/ProductConstants.yml` — when you add or rename a product/brand name in `constants.ts`, update the swap list there too. Enforced terms must never be added to the Vale vocabulary (it would suppress the nudge).
- **No em dashes.** `TigerData.NoEmDash` flags `—` in prose (warning); rewrite the sentence. Prefer commas, semicolons, colons, parentheses, or two sentences. For label-and-description lines, use a colon: `**Label**: description`.
- **UI elements in code font, not bold.** `TigerData.UIElementsCodeFont` flags `**Bold**` UI labels after action verbs (warning).
- **Partials use underscore prefix:** `_partial-name.mdx`.
- **No deprecated compression APIs.** TimescaleDB 2.18.0 renamed the compression API to columnstore/hypercore (`compress_chunk` → `convert_to_columnstore`, `*_compression_policy` → `*_columnstore_policy`, `timescaledb.compress` → `timescaledb.enable_columnstore`, etc.). Old names still work as backwards-compat aliases but must not appear in new docs. `TigerData.CompressionAPIs` enforces this (gating error, scans SQL too). Full mapping, carve-outs, and verification grep: [`.claude/references/deprecated-compression-apis.md`](./.claude/references/deprecated-compression-apis.md).

## CI Checks

- **vale.yml** — Lints prose against the Google style guide + custom `TigerData` rules. Only the lines a PR changes are checked, and only errors gate; `TigerData.CompressionAPIs` is the only rule set to error (everything else is advisory). Failures are explained in the run's step summary plus inline annotations. See `.github/scripts/vale_pr_lint.py`.
- **pr-checklist-check.yml** — Ensures PR checklist items are addressed.
- **affected-pages.yml** — Posts preview links for changed pages on successful deploy.

## Hosting, Search, and Cache

The site builds with `pnpm build` and can deploy anywhere that serves static files (Vercel, Netlify, Cloudflare Pages).

- **Search**: Pagefind by default (header search bar and ⌘K). For Algolia, set `PUBLIC_ALGOLIA_APP_ID`, `PUBLIC_ALGOLIA_INDEX`, `PUBLIC_ALGOLIA_SEARCH_KEY`, `PRIVATE_ALGOLIA_WRITE_KEY` (see `.env.example`).
- **Cache headers**: set per [Stainless' recommendation](https://www.stainless.com/docs/docs-platform/hosting-and-deploys/#configuring-cache-headers) — long-lived for `/_astro/*` (versioned assets), shorter TTL for HTML. This repo configures them via `public/_headers` (Netlify, Cloudflare Pages) and `vercel.json` (Vercel).

## Environment

Requires `STAINLESS_API_KEY` for API reference generation (see `.env.example`). Optional Algolia env vars for search (above).
