Updating parameters on a {C.PG} instance will cause an outage. Choose a time that will cause the least issues to tune this database.

<NumberedList>

<NumberedItem title="Tune the Write Ahead Log (WAL) on the RDS/Aurora {C.PG} source database">

<ol type="a">
<li>In <a href="https://console.aws.amazon.com/rds/home#databases:">RDS console</a>, select the RDS instance to migrate.</li>
<li>Click <strong>Configuration</strong>, scroll down and note the <strong>DB instance parameter group</strong>, then click <strong>Parameter Groups</strong>.</li>
</ol>

<img src="/assets/images/migrate/awsrds-parameter-groups.png" alt="Parameter groups" class="main-content__illustration" />

<ol type="a" start="3">

<li>Click <strong>Create parameter group</strong>, fill in the form with the following values, then click <strong>Create</strong>:<br />
• <strong>Parameter group name</strong> — whatever suits your fancy.<br />
• <strong>Description</strong> — knock yourself out with this one.<br />
• <strong>Engine type</strong> — <code>{C.PG}</code><br />
• <strong>Parameter group family</strong> — the same as <strong>DB instance parameter group</strong> in your <strong>Configuration</strong>.</li>
<li>In <strong>Parameter groups</strong>, select the parameter group you created, then click <strong>Edit</strong>.</li>
<li>Update the following parameters, then click <strong>Save changes</strong>:<br />
<code>rds.logical_replication</code> set to <code>1</code>: record the information needed for logical decoding.<br />
<code>wal_sender_timeout</code> set to <code>0</code>: disable the timeout for the sender process.</li>
<li>In RDS, navigate back to your <a href="https://console.aws.amazon.com/rds/home#databases:">databases</a>, select the RDS instance to migrate, and click <strong>Modify</strong>.</li>
<li>Scroll down to <strong>Database options</strong>, select your new parameter group, and click <strong>Continue</strong>.</li>
<li>Click <strong>Apply immediately</strong> or choose a maintenance window, then click <strong>Modify DB instance</strong>.</li>
</ol>

Changing parameters will cause an outage. Wait for the database instance to reboot before continuing. After it comes back up, verify that the new settings are in effect on your database.

</NumberedItem>

<NumberedItem title="Create a user for the {C.PG_CONNECTOR} and assign permissions">

<ol type="a">
<li>Create <code>&lt;pg connector username&gt;</code>:</li>
</ol>

```bash
psql $SOURCE -c "CREATE USER <pg connector username> PASSWORD '<password>'"
```

You can use an existing user. However, you must ensure that the user has the following permissions.

<ol type="a" start="2">
<li>Grant permissions to create a replication slot:</li>
</ol>

```bash
psql $SOURCE -c "GRANT rds_replication TO <pg connector username>"
```

<ol type="a" start="3">
<li>Grant permissions to create a publication:</li>
</ol>

```bash
psql $SOURCE -c "GRANT CREATE ON DATABASE <database name> TO <pg connector username>"
```

<ol type="a" start="4">
<li>Assign the user permissions on the source database:</li>
</ol>

```bash
psql $SOURCE <<EOF
GRANT USAGE ON SCHEMA "public" TO <pg connector username>;
GRANT SELECT ON ALL TABLES IN SCHEMA "public" TO <pg connector username>;
ALTER DEFAULT PRIVILEGES IN SCHEMA "public" GRANT SELECT ON TABLES TO <pg connector username>;
EOF
```

If the tables you are syncing are not in the <code>public</code> schema, grant the user permissions for each schema you are syncing:

```bash
psql $SOURCE <<EOF
GRANT USAGE ON SCHEMA <schema> TO <pg connector username>;
GRANT SELECT ON ALL TABLES IN SCHEMA <schema> TO <pg connector username>;
ALTER DEFAULT PRIVILEGES IN SCHEMA <schema> GRANT SELECT ON TABLES TO <pg connector username>;
EOF
```

<ol type="a" start="5">
<li>On each table you want to sync, make <code>&lt;pg connector username&gt;</code> the owner:</li>
</ol>

```bash
psql $SOURCE -c 'ALTER TABLE <table name> OWNER TO <pg connector username>;'
```

You can skip this step if the replicating user is already the owner of the tables.
