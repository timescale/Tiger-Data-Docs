* Using {C.TIMESCALE_DB} as the source has limited support (no CAGGs).

* The source must be running {C.PG} 13 or later.

* Schema changes must be co-ordinated.

  Make compatible changes to the schema in your {C.SERVICE_LONG} first, then make
  the same changes to the source {C.PG} instance.

* Detaching or dropping a partition, and `TRUNCATE`, are not synced from the source.

  This includes `pg_partman` retention, and {C.TIMESCALE_DB} retention policies that drop
  {C.CHUNK}s. The target keeps the removed rows. If the source writes rows with the same
  keys as the removed ones, the sync stops with a duplicate key error, or the target gets a
  duplicate row when the table has no primary key or unique constraint.

  Repeat these operations on the target: delete the rows of each detached or dropped
  partition, and truncate each truncated table. For partition or {C.CHUNK} retention, you
  can instead use a {C.HYPERTABLE} on the target with a matching
  [retention policy](/reference/timescaledb/data-retention/add_retention_policy). To recover
  from the duplicate key error, see [Troubleshooting](/migrate/livesync-replication-troubleshooting#duplicate-key-error-after-rows-are-removed-on-the-source).

* Ensure that the source {C.PG} instance and the target {C.SERVICE_LONG} have the same extensions installed.

  The {C.PG_CONNECTOR} does not create extensions on the target. If the table uses
  column types from an extension, first create the extension on the
  target {C.SERVICE_LONG} before syncing the table.

* There is WAL volume growth on the source {C.PG} instance during large table copy.

* Continuous aggregate invalidation

  The connector uses `session_replication_role=replica` during data replication,
  which prevents table triggers from firing. This includes the internal
  triggers that mark continuous aggregates as invalid when underlying data
  changes.

  If you have continuous aggregates on your target database, they do not
  automatically refresh for data inserted during the migration. This limitation
  only applies to data below the continuous aggregate's materialization
  watermark. For example, backfilled data. New rows synced above the continuous
  aggregate watermark are used correctly when refreshing.

  This can lead to:

  - Missing data in continuous aggregates for the migration period.
  - Stale aggregate data.
  - Queries returning incomplete results.

  If the continuous aggregate exists in the source database, best
  practice is to add it to the {C.PG} connector publication. If it only exists on the
  target database, manually refresh the continuous aggregate using the `force`
  option of [refresh_continuous_aggregate](/reference/timescaledb/continuous-aggregates/refresh_continuous_aggregate#samples).
