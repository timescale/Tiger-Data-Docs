A fork is a full, independent copy of a {C.SERVICE_SHORT} at a point in time. It has its own compute and storage,
its own configuration, and its own `tsdbadmin` password. It supports every feature of the primary {C.SERVICE_SHORT}:
high availability, read replicas, backups, and point-in-time recovery. Changes to a fork never reach the primary,
and changes to the primary never reach the fork.

Forks are built for environments that stay around. Use one for staging on production data, for disaster recovery
from a known-good state, or to rehearse a major {C.PG} upgrade before you apply it to the live {C.SERVICE_SHORT}.

Because a fork copies the whole {C.SERVICE_SHORT}, creation time grows with the amount of data: typically 5 to 20
minutes, and hours for multi-terabyte {C.SERVICE_SHORT}s.{props.fluid && <> For a short-lived copy that is ready in a minute or two, create a [branch](../service-management/branch-services) of a Fluid {C.SERVICE_SHORT} instead.</>}

## Understand {C.SERVICE_SHORT} forks

You can use {C.SERVICE_SHORT} forks for disaster recovery, CI/CD automation, and testing and development. For example, you
can automatically test a major {C.PG} upgrade on a fork before applying it to your production {C.SERVICE_SHORT}.

{C.CLOUD_LONG} offers the following fork strategies:

- `now`: create a fresh fork of your database at the current time.
   Use when:
   - You need the absolute latest data
   - Recent changes must be included in the fork

- `last-snapshot`: fork from the most recent [automatic backup](../high-availability/backup-restore). Because {C.CLOUD_LONG} takes automatic backups daily, this is usually within the previous 24 hours of your {C.SERVICE_SHORT}. To see when the latest backup was taken, check [`Backup history`](../high-availability/backup-restore#automatic-backups) in {C.CONSOLE}.
  Use when:
  - You want the fastest possible fork creation
  - Up to 24 hours behind current data is acceptable

- `timestamp`: fork from a specific point in time within the recovery period for your [{C.PRICING_PLAN}](../pricing-and-account-management#features-included-in-each-pricing-plan).
  Use when:
  - Disaster recovery from a known-good state
  - Investigating issues that occurred at a specific time
  - Testing "what-if" scenarios from historical data

### Billing

A fork is billed as a {C.SERVICE_SHORT} of its own: its compute, and the full high-performance storage it holds.
[Tiered data](/build/data-management/storage/manage-storage) is shared across forks: chunks in the object storage
tier are billed once, regardless of the number of forks, and only new or modified chunks in a fork incur additional
costs. For details, see [Replicas and forks with tiered data](/build/data-management/storage/tiered-data-replicas-forks).

You can fork a free {C.SERVICE_SHORT} to a free or a Standard {C.SERVICE_SHORT}, but not a Standard {C.SERVICE_SHORT}
to a free one.

## Integrate {C.SERVICE_SHORT} forks in your CI/CD pipeline

To fork your {C.SERVICE_LONG} using GitHub actions:

<NumberedList>

<NumberedItem title={`Store your ${C.CLOUD_LONG} API key as a GitHub Actions secret`}>

1. In [{C.CONSOLE_LONG}](https://console.cloud.tigerdata.com/dashboard/settings), click `Create credentials`.
1. Save the `Public key` and `Secret key` locally, then click `Done`.
1. In your GitHub repository, click `Settings`, open `Secrets and variables`, then click `Actions`.
1. Click `New repository secret`, then set `Name` to `TIGERDATA_API_KEY`.
1. Set `Secret` to your {C.CLOUD_LONG} API key in the following format `<Public key>:<Secret key>`, then click `Add secret`.

</NumberedItem>

<NumberedItem title="Add the GitHub Actions Marketplace to your workflow YAML files">

   For example, the following workflow forks a {C.SERVICE_SHORT} when a pull request is opened,
   running tests against the fork, then automatically cleans up.

    ```yaml
    name: Test on a service fork
    on: pull_request

    jobs:
      test:
        runs-on: ubuntu-latest
        steps:
          - uses: actions/checkout@v4

          - name: Fork Database
            id: fork
            uses: timescale/fork-service@v1
            with:
              project_id: ${{ secrets.TIGERDATA_PROJECT_ID }}
              service_id: ${{ secrets.TIGERDATA_SERVICE_ID }}
              api_key: ${{ secrets.TIGERDATA_API_KEY }}
              fork_strategy: last-snapshot
              cleanup: true
              name: pr-${{ github.event.pull_request.number }}

          - name: Run Integration Tests
            env:
              DATABASE_URL: postgresql://tsdbadmin:${{ steps.fork.outputs.initial_password }}@${{ steps.fork.outputs.host }}:${{ steps.fork.outputs.port }}/tsdb?sslmode=require
            run: |
              npm install
              npm test
          - name: Run Migrations
            env:
              DATABASE_URL: postgresql://tsdbadmin:${{ steps.fork.outputs.initial_password }}@${{ steps.fork.outputs.host }}:${{ steps.fork.outputs.port }}/tsdb?sslmode=require
            run: npm run migrate
    ```

    For the full list of inputs, outputs, and configuration options, see the [Tiger Data - Fork Service](https://github.com/marketplace/actions/tiger-data-fork-service) in GitHub marketplace.

</NumberedItem>
