## Access your Kafka cluster in Confluent Cloud

Take the following steps to prepare your Kafka cluster for connection to {C.CLOUD_LONG}:

<NumberedList>
<NumberedItem title="Create a service account">
If you already have a service account for {C.CLOUD_LONG}, you can reuse it. To create a new service account:

<ol type="a">
<li>Log in to [Confluent Cloud](https://confluent.cloud/).</li>
<li>Click the burger menu at the top-right of the pane, then press
`Access control` > `Service accounts` > `Add service account`.</li>
<li>

Enter the following details:

- Name: `tigerdata-access`
- Description: `Service account for the Tiger Cloud source connector`

</li>
<li>Add the service account owner role, then click `Next`.</li>
<li>Select a role assignment, then click `Add`.</li>
<li>Click `Next`, then click `Create service account`.</li>
</ol>
</NumberedItem>

<NumberedItem title="Create API keys">
<ol type="a">
<li>In Confluent Cloud, click `Home` > `Environments` > Select your environment > Select your cluster.</li>
<li>Under `Cluster overview` in the left sidebar, select `API Keys`.</li>
<li>Click `Add key`, choose `Service Account` and click `Next`.</li>
<li>Select `tigerdata-access`, then click `Next`.</li>
<li>

For your cluster, choose the `Operation` and select the following `Permission`s, then click `Next`:

- `Resource type`: `Cluster`
- `Operation`: `DESCRIBE`
- `Permission`: `ALLOW`

</li>
<li>Click `Download and continue`, then securely store the ACL.</li>
<li>

Use the same procedure to add the following keys:

- ACL 2: Topic access
  - `Resource type`: `Topic`
  - `Topic name`: Select the topics that {C.CLOUD_LONG} should read
  - `Pattern type`: `LITERAL`
  - `Operation`: `READ`
  - `Permission`: `ALLOW`
- ACL 3: Consumer group access
  - `Resource type`: `Consumer group`
  - `Consumer group ID`: `tigerdata-kafka/<tiger_cloud_project_id>`. See [Find your connection details](/integrate/find-connection-details) for where to find your project ID
  - `Pattern type`: `PREFIXED`
  - `Operation`: `READ`
  - `Permission`: `ALLOW`

You need these to configure your Kafka source connector in {C.CLOUD_LONG}.

</li>
</ol>
</NumberedItem>
</NumberedList>

## Configure Confluent Cloud Schema Registry

{C.CLOUD_LONG} requires access to the Schema Registry to fetch schemas for Kafka topics. To configure the Schema Registry:

<NumberedList>
<NumberedItem title="Navigate to `Schema Registry`">
In Confluent Cloud, click `Environments` and select your environment, then click `Stream Governance`.
</NumberedItem>

<NumberedItem title="Create a Schema Registry API key">
<ol type="a">
<li>Click `API Keys`, then click `Add API Key`.</li>
<li>Choose `Service Account`, select `tigerdata-access`, then click `Next`.</li>
<li>Under `Resource scope`, choose `Schema Registry`, select the `default` environment, then click `Next`.</li>
<li>

In `Create API Key`, add the following, then click `Create API Key`:

- `Name`: `tigerdata-schema-registry-access`
- `Description`: `API key for Tiger Cloud schema registry access`

</li>
<li>Click `Download API Key` and securely store the API key and secret, then click `Complete`.</li>
</ol>
</NumberedItem>

<NumberedItem title="Assign roles for Schema Registry">
<ol type="a">
<li>Click the burger menu at the top-right of the pane, then press
`Access control` > `Accounts & access` > `Service accounts`.</li>
<li>Select the `tigerdata-access` service account.</li>
<li>

In the `Access` tab, add the following role assignments for `All schema subjects`:

- `ResourceOwner` on the service account.
- `DeveloperRead` on schema subjects.

  Choose `All schema subjects` or restrict to specific subjects as required.

</li>
<li>Save the role assignments.</li>
</ol>

Your Confluent Cloud Schema Registry is now accessible to {C.CLOUD_LONG} using the API key and secret.
</NumberedItem>
</NumberedList>

## Add Kafka source connector in {C.CLOUD_LONG}

Take the following steps to create a Kafka source connector in {C.CONSOLE_LONG}.

<NumberedList>
<NumberedItem title={`In ${C.CONSOLE_SHORT}, select your ${C.SERVICE_SHORT}`}>
Open [{C.CONSOLE_SHORT}](https://console.cloud.tigerdata.com/) and select your {C.SERVICE_SHORT}.
</NumberedItem>

<NumberedItem title={`Go to Connectors > Source connectors`}>
Click `New Connector`, then select `Kafka`.
</NumberedItem>

<NumberedItem title="Set the connector name">
Click the pencil icon, then set the connector name.
</NumberedItem>

<NumberedItem title="Set up Kafka authentication">
Enter the name of your cluster in Confluent Cloud and the information from the first `api-key-*.txt` that you
downloaded, then click `Authenticate`.
</NumberedItem>

<NumberedItem title="Set up the Schema Registry">
Enter the service account ID and the information from the second `api-key-*.txt` that you
downloaded, then click `Authenticate`.
</NumberedItem>

<NumberedItem title="Select topics to sync">
Add the schema and table, map the columns in the table, and click `Create connector`.

Your Kafka connector is configured and ready to stream events.
</NumberedItem>
</NumberedList>

## Known limitations and unsupported types

The following Avro schema types are not supported:

### Union types

Multi-type non-nullable unions are blocked.

Examples:

- Multiple type union:

    ```json
    {
      "type": "record",
      "name": "Message",
      "fields": [
        {"name": "content", "type": ["string", "bytes", "null"]}
      ]
    }
    ```

- Union as root schema:

    ```json
    ["null", "string"]
    ```

### Reference types (named type references)

Referencing a previously defined named type by name, instead of inline, is not supported.

Examples:

- Named type definition:

    ```json
    {
      "type": "record",
      "name": "Address",
      "fields": [
        {"name": "street", "type": "string"},
        {"name": "city", "type": "string"}
      ]
    }
    ```

- Failing reference:

    ```json
    {
      "type": "record",
      "name": "Person",
      "fields": [
        {"name": "name", "type": "string"},
        {"name": "address", "type": "Address"}
      ]
    }
    ```

### Unsupported logical types

Only the logical types in the hardcoded supported list are supported. This includes:

* decimal, date, time-millis, time-micros
* timestamp-millis, timestamp-micros, timestamp-nanos
* local-timestamp-millis, local-timestamp-micros, local-timestamp-nanos
* uuid, duration

Unsupported examples:

```json
{
  "type": "int",
  "logicalType": "date-time"
}

{
  "type": "string",
  "logicalType": "json"
}

{
  "type": "bytes",
  "logicalType": "custom-type"
}
```
