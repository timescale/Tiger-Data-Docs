Advanced scenarios for [Livesync replication](/migrate/livesync-replication) migrations: continuous aggregates, compressed hypertables on older {C.TIMESCALE_DB} versions, identity columns, and merging many source tables into one hypertable.

## Migrating continuous aggregates

Livesync replicates the {C.CAGG}'s underlying materialization {C.HYPERTABLE}, not the view. The {C.CAGG} must already exist with data on the source and be defined (empty) on the target.

<NumberedList>
<NumberedItem title={`Resolve materialization ${C.HYPERTABLE} names on both source and target`}>

The `_materialized_hypertable_<N>` suffix differs per environment:

```sql
SELECT materialization_hypertable_schema AS mat_schema,
       materialization_hypertable_name   AS mat_name
FROM timescaledb_information.continuous_aggregates
WHERE view_schema = '<schema>' AND view_name = '<cagg_name>';
```

</NumberedItem>

<NumberedItem title={`Set replica identity on the source materialization ${C.HYPERTABLE}`}>

Required when the publication replicates `UPDATE`/`DELETE` (the default). {C.CAGG_CAP} refreshes issue `DELETE`s; without a replica identity the next refresh fails with `cannot delete from table ... because it does not have a replica identity and publishes deletes`.

```sql
ALTER TABLE _timescaledb_internal._materialized_hypertable_<N>
  REPLICA IDENTITY FULL;
```

</NumberedItem>

<NumberedItem title={`Add the materialization ${C.HYPERTABLE} to the publication`}>

```sql
ALTER PUBLICATION <publication_name>
  ADD TABLE _timescaledb_internal._materialized_hypertable_<N>;
```

</NumberedItem>

<NumberedItem title={`Map source matview ${C.HYPERTABLE} to target matview ${C.HYPERTABLE}`}>

- **{C.CONSOLE}:** edit the connector, select the source `_materialized_hypertable_<N>`, and set its target mapping to the target's `_materialized_hypertable_<M>`.
- **Docker:** add a `--table-map` entry and refresh:

  ```text
  --table-map '{
    "source": {"schema": "_timescaledb_internal", "table": "_materialized_hypertable_<N>"},
    "target": {"schema": "_timescaledb_internal", "table": "_materialized_hypertable_<M>"}
  }'
  ```

</NumberedItem>

<NumberedItem title="Do not attach a refresh policy on the target">

While Livesync is running, the target {C.CAGG} is kept current via replication. Attach the refresh policy on the target only after cutover.

</NumberedItem>
</NumberedList>

## Replica identity on compressed hypertables (older {C.TIMESCALE_DB})

On older {C.TIMESCALE_DB} versions, `ALTER TABLE ... REPLICA IDENTITY ...` fails on compressed {C.HYPERTABLE}s:

```text
ERROR:  operation not supported on hypertables that have compression enabled
```

Newer versions accept the command directly on the {C.HYPERTABLE} and propagate it to chunks. If you can upgrade {C.TIMESCALE_DB} on the source first, do that and skip this section.

If upgrading isn't an option, wrap the work in `timescaledb_pre_restore()` / `timescaledb_post_restore()` (these disable the catalog hooks that block the operation). Iterate over all chunks of the {C.HYPERTABLE}, set `REPLICA IDENTITY FULL` on each, and set it on the {C.HYPERTABLE} itself so new chunks inherit:

```bash
psql "$SOURCE" -v schema='<schema>' -v hypertable='<hypertable>' <<'EOF'
BEGIN;
SELECT timescaledb_pre_restore();

SELECT format('ALTER TABLE %I.%I REPLICA IDENTITY FULL;',
              chunk_schema, chunk_name)
FROM timescaledb_information.chunks
WHERE hypertable_schema = :'schema'
  AND hypertable_name   = :'hypertable'
\gexec

ALTER TABLE :"schema".:"hypertable" REPLICA IDENTITY FULL;

SELECT timescaledb_post_restore();
COMMIT;
EOF
```

Run as a single transaction. Dry-run on a non-production instance first.

## Tables with `GENERATED ALWAYS AS IDENTITY` columns

CDC `UPDATE` replication currently fails on target tables whose columns are defined as `GENERATED ALWAYS AS IDENTITY`, because the apply worker tries to write the source value into a column that {C.PG} forbids assigning to. Until Livesync handles this automatically, work around it by relaxing the column to `GENERATED BY DEFAULT` for the duration of the migration. This does not rewrite the column or change runtime behavior for existing sequences.

<NumberedList>
<NumberedItem title="Find affected columns on the source">

```sql
psql "$SOURCE" <<'EOF'
SELECT
    n.nspname AS schema,
    c.relname AS table,
    a.attname AS column
FROM pg_attribute a
JOIN pg_class c ON c.oid = a.attrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE a.attidentity = 'a'  -- 'a' = ALWAYS, 'd' = BY DEFAULT
  AND c.relkind IN ('r', 'p')
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n.nspname, c.relname, a.attnum;
EOF
```

</NumberedItem>

<NumberedItem title={`Relax to \`BY DEFAULT\` before migration`}>

For each row returned above, run on **both** source and target:

```sql
ALTER TABLE <schema>.<table>
  ALTER COLUMN <column> SET GENERATED BY DEFAULT;
```

</NumberedItem>

<NumberedItem title={`Restore to \`ALWAYS\` after cutover`}>

After the application is running on {C.CLOUD_LONG}, restore the original constraint on the target:

```sql
ALTER TABLE <schema>.<table>
  ALTER COLUMN <column> SET GENERATED ALWAYS;
```

</NumberedItem>
</NumberedList>

## Merge many source tables into one hypertable

Some apps partition data themselves, with one table per period: `metrics-001`, `metrics-002`, and so on. Livesync can merge such tables into a single {C.HYPERTABLE} on the target, because the `table` in a `--table-map` source is a [Go regular expression](https://pkg.go.dev/regexp/syntax). The pattern is anchored for you, so `metrics-[0-9]+` matches `metrics-001` but not `app_metrics-001`. When you pass several `--table-map` flags, the first match wins. Tables that match no mapping sync one-to-one:

```bash
--table-map '{"source": {"schema": "public", "table": "metrics-[0-9]+"}, "target": {"schema": "public", "table": "metrics"}}'
```

Before you start Livesync, make the three changes below for every table you merge. The rest of the migration follows the [Livesync replication](/migrate/livesync-replication) steps.

### Make the replica identity unique across the merged tables

Livesync applies `UPDATE` and `DELETE` on the target by matching the source table's [replica identity](/migrate/livesync-replication#replication-identity) columns, by default the primary key. The target doesn't know which source table a row came from.

<Callout variant="warning">
If the replica identity is only unique within each source table, for example an `id` sequence that restarts at 1 in every monthly table, one `UPDATE` or `DELETE` on the source changes or removes the matching row of **every** merged table, with no error. An `UPDATE` that changes the partition column fails instead, and replication halts for the whole subscription.
</Callout>

Choose one option for every merged table on the source. Changing the replica identity only affects changes made afterwards, so do it before you create the publication:

- **Append-only data**: create the publication for these tables `WITH (publish = 'insert')`. Livesync then never receives `UPDATE` or `DELETE` for them.
- **A key that is unique across all the tables**, such as `(device_id, time)` when the tables cover different time ranges: create a unique index on it in each table and run `ALTER TABLE ... REPLICA IDENTITY USING INDEX ...`.
- **Any other case**: `ALTER TABLE ... REPLICA IDENTITY FULL`. Livesync then matches on every column. This needs no new index but increases the write-ahead log volume on the source.

### Create the target hypertable

[Schema migration](/migrate/livesync-replication#schema-migration) creates the source tables on the target as regular tables. Use one of them as the template, then drop the copied `serial` default, which points at that table's own sequence:

```sql
CREATE TABLE public.metrics (LIKE public."metrics-001" INCLUDING DEFAULTS)
WITH (
  tsdb.hypertable,
  tsdb.partition_column = 'time',
  tsdb.chunk_interval = '7 days'
);

ALTER TABLE public.metrics ALTER COLUMN id DROP DEFAULT;
```

`LIKE` doesn't copy the primary key, so the per-table key on `id` stays behind. Don't add a unique constraint on a column that is only unique within each source table: the initial copy of the second table then fails with `duplicate key value violates unique constraint`. Finally, drop the merged source tables from the target, since Livesync doesn't write to them.

### Publish the tables and check the mapping

List every merged table explicitly in the [publication](/migrate/livesync-replication#publication). After you start Livesync, confirm that each one maps to the {C.HYPERTABLE}:

```sql
SELECT schemaname, tablename, target_table, state
FROM _ts_live_sync.subscription_rel
ORDER BY tablename;
```

When your app creates a new table during the migration, set its replica identity, add it to the publication, and run `refresh-publication` with the same `--table-map` flags. Without them, the new table maps to a target table with the same name.
