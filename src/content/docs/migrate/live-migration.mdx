## Overview

Learn how to migrate your existing {C.PG} database to Tiger Cloud with minimal or zero downtime. Live migration uses logical replication to keep your source and target databases synchronized while your application continues to serve traffic, then performs a quick cutover when ready.

## Prerequisites

- Source database running {C.PG} 10 or later with logical replication enabled
- A Tiger Cloud service provisioned with sufficient storage for your data
- Network connectivity between source database and Tiger Cloud
- Superuser or replication privileges on the source database
- `wal_level` set to `logical` on the source database
- Sufficient `max_replication_slots` and `max_wal_senders` configured

## When to use live migration

This section helps you determine if live migration is the right approach for your use case.

### Ideal scenarios

- Production databases that cannot tolerate extended downtime
- Large databases (100GB+) where dump/restore would take hours
- Applications requiring continuous availability during migration
- Databases with high write throughput

### Considerations

- Logical replication adds some overhead to your source database
- Requires more setup and monitoring than offline migration
- Some {C.PG} features may not replicate (large objects, sequences, DDL changes)

## Migration strategies

### Logical replication

Use {C.PG}'s built-in logical replication to stream changes from your source database to Tiger Cloud in real-time.

#### Set up the publication on source

Configure which tables and data to replicate from your source database.

#### Set up the subscription on Tiger Cloud

Create a subscription on your Tiger Cloud service to receive replicated data.

#### Monitor replication lag

Track the replication lag to determine when the databases are synchronized and ready for cutover.

### Using pgcopydb for large databases

For terabyte-scale migrations, use pgcopydb to efficiently copy data while maintaining a live replication stream.

### Expand and contract pattern

Implement a dual-write strategy where your application writes to both databases during the migration window, allowing gradual traffic shifting.

## Performing the cutover

### Pre-cutover checklist

Verify replication lag is minimal, application is ready for connection string change, and rollback plan is in place.

### Cutover steps

1. Freeze writes on the source database (maintenance mode or read-only)
2. Verify replication is fully caught up
3. Update application connection strings to Tiger Cloud
4. Resume normal operations
5. Monitor for issues

### Rollback considerations

Plan for rollback scenarios in case issues arise during or after cutover.

## Best practices

- Test the entire migration process in a staging environment first
- Monitor replication lag continuously during the migration
- Schedule the cutover during low-traffic periods
- Prepare application teams for the connection string change
- Have a clear rollback plan documented and tested
- Use connection pooling to make connection string changes easier

## Troubleshooting

### Replication lag keeps increasing

Check for long-running transactions on the source, network bandwidth limitations, or resource constraints on either database.

### Replication slot not found

Verify the publication exists and the subscription was created with the correct connection details.

### Sequence values not synchronized

Logical replication does not sync sequences automatically. Manually set sequence values on the target after cutover.

### Permission errors during replication

Ensure the replication user has the necessary privileges on all replicated tables.
