<Callout variant="tip">
**Livesync replication vs. {C.PG_CONNECTOR}:** Livesync replication is a **one-time migration** to {C.CLOUD_LONG} with a cutover at the end. For **continuous ongoing replication** where {C.PG} stays the primary and {C.CLOUD_LONG} acts as a logical replica, see [Sync from {C.PG}](/migrate/livesync-for-postgresql) instead. Both features share the same underlying technology, but the workflows and end states differ.
</Callout>

Livesync replication uses the {C.PG} logical replication protocol to synchronize data from a source database to a {C.SERVICE_LONG} or an {C.MST_SERVICE_SHORT}, then cut over once the target is caught up. Because it relies on the standard {C.PG} protocol, you get compatibility, familiarity, and a broad knowledge base.

The same technology powers two distribution channels: the **self-hosted Docker image** (`timescale/live-sync`) is commonly referred to as **Livesync**, and the **managed {C.CONSOLE} integration** is referred to as the **{C.PG_CONNECTOR_CAP}**. Both produce the same migration result; this page covers both.

This page replaces the older Live migration workflow.

The migration runs in four stages:

1. **Schema migration:** export structure from the source, apply it to the target.
2. **Initial data copy:** bulk `COPY` at 300 GB/hr to 2.2 TB/hr depending on `--table-sync-workers` tuning, target bandwidth, and IOPS. Publication tables are copied in parallel; large individual tables still use a single connection, except {C.PG} declarative partitioned tables published with `publish_via_partition_root = false`, which Livesync (v0.23.0 and later) copies leaf partition by leaf partition in parallel, the same way hypertable chunks are copied. Foreign key validation is disabled during sync.
3. **CDC:** real-time replication of ongoing changes up to 50K operations per second.
4. **Cutover:** validate, stop sync, switch the application connection strings.

You can drive Livesync replication from the {C.CONSOLE} UI or from a self-hosted Docker container. {C.CONSOLE} supports multiple Livesync instances per service, dropdown-based schema and table selection, and live progress metadata (rows copied during initial data copy, replication lag during CDC).

<Prerequisites context="procedure">

- **Source:** {C.PG} 13 or later with `wal_level = logical`. The source must be a primary, not a read replica or standby.
- **Target:** A {C.SERVICE_LONG} or an {C.MST_SERVICE_SHORT}. An {C.MST_SERVICE_SHORT} target is supported only with the self-hosted Docker image, not the {C.CONSOLE} wizard. Target spec should be close to the source spec for a full migration. Minimum 4 CPU / 16 GB RAM on both source and target for roughly 300 GB/hr to 2.2 TB/hr transfer. `tsdbadmin` credentials.
- **Migration host:** A separate machine to run the migration commands, with Docker, `psql`, `pg_dump`, and `vacuumdb` installed and network access to both source and target databases.
- An [adjusted maintenance window](/deploy/tiger-cloud/tiger-cloud-aws/upgrades#define-your-maintenance-window) to prevent maintenance from running during migration.
- Environment variables for the source and target connections:

  ```bash
  export SOURCE="postgres://<user>:<password>@<source_host>:<port>/<db_name>"
  export TARGET="postgres://tsdbadmin:<password>@<target_host>:<port>/tsdb?sslmode=require"
  ```
</Prerequisites>

## Limitations

- **Compressed {C.HYPERTABLE} chunks are copied uncompressed.** Livesync copies logical data by decompressing compressed chunks on the fly during the table copy. This removes the {C.TIMESCALE_DB} extension-version coupling between source and target, but the target starts with {C.COLUMNSTORE} data in row form. Copying compressed chunks as-is is on the roadmap but not yet available; re-enable columnstore on the target after the sync (see [Columnstore](/learn/columnar-storage/understand-hypercore) / [Post-sync](#post-sync)).
- **{C.TIMESCALE_DB} source must be on 2.16.0 or newer** if any chunk is ever compressed or decompressed during the migration. Earlier versions don't emit the decompression-boundary markers that Livesync needs to deduplicate the WAL stream, so the target ends up with duplicate records. This affects all of:
  - `INSERT`s into a chunk that the compression policy later compresses.
  - Explicit `convert_to_columnstore()` or `convert_to_rowstore()` calls.
  - `UPDATE` or `DELETE` on a compressed chunk, which decompresses, mutates, then recompresses.

  The pre-2.16.0 GUC `timescaledb.enable_decompression_logrep_markers` is incomplete (it doesn't cover compression policies or explicit compress/decompress) and requires {C.PG} 14 or later to do anything.

  If you can't upgrade, the practical mitigations are: keep chunks that may receive writes uncompressed (for example, the last three months), pause compression policies during the migration, or plan to re-sync affected hypertables.

## Roles

Dump roles from the source and apply to the target:

```bash
pg_dumpall --roles-only -d "$SOURCE" > roles.sql
```

Review and apply:

```bash
cat roles.sql
psql "$TARGET" -f roles.sql
```

`pg_dumpall --roles-only` includes passwords (from `pg_authid`), role attributes, and memberships. You may need to edit out `postgres`, `tsdbadmin`, and other system roles before applying to the target.

**Primary dimension**

```bash

SELECT format(
```

**Additional dimensions (optional)**

{C.TIMESCALE_DB} generally discourages using more than one dimension. Additional dimensions carry a risk of [partition explosion](/learn/hypertables/partitioning-hypertables#space-partitioning-hash-dimension) and prevent the use of [data tiering](/learn/data-lifecycle/storage/about-storage-tiers#low-cost-storage) (tiered storage requires single-dimension hypertables). Only add extra dimensions if the source explicitly uses them and you have validated the need.

```bash
psql "$SOURCE" -t -A <<'EOF' > add_dimensions.sql
SELECT format(
  'SELECT add_dimension(%L, %s);',
  format('%I.%I', d.hypertable_schema, d.hypertable_name),
  CASE
    WHEN d.num_partitions IS NOT NULL THEN
      format('by_hash(%L, %s)', d.column_name, d.num_partitions)
    ELSE
      format('by_range(%L%s)', d.column_name,
        CASE WHEN d.time_interval IS NOT NULL
          THEN format(', %L::interval', d.time_interval::text)
          ELSE ''
        END)
  END
)
FROM timescaledb_information.dimensions d
JOIN timescaledb_information.hypertables h
  ON d.hypertable_schema = h.hypertable_schema
 AND d.hypertable_name = h.hypertable_name
WHERE d.dimension_number > 1
  AND h.hypertable_name NOT LIKE '_materialized_hypertable_%'
ORDER BY d.hypertable_schema, d.hypertable_name, d.dimension_number;
EOF

cat add_dimensions.sql
psql "$TARGET" -f add_dimensions.sql
```

<NumberedItem title="Convert tables to hypertables">

Good candidates for [{C.HYPERTABLE}s](/learn/hypertables/understand-hypertables):

- **Tables with a time-based column:** any column of type `TIMESTAMPTZ`, `TIMESTAMP`, `DATE`, or `INTEGER`/`BIGINT` (epoch). See [supported partition column types](/learn/hypertables/creating-and-configuring-hypertables).
- **Append-mostly tables:** sensor readings, metrics, events, logs, or any table where rows are predominantly inserted in time order and rarely updated.
- **{C.PG} declarative partitioned tables:** these can be converted directly to {C.HYPERTABLE}s. Rename the partitioned table, create a regular table with the same name, then convert (see example below).
- **Large tables with time-range queries:** tables frequently queried with `WHERE ts > now() - interval '...'` benefit most from chunk exclusion.

Convert on the target:

```sql
-- Regular table
SELECT create_hypertable(
  '<schema>.<table>',
  by_range('<time_column>', INTERVAL '7 days'),
  create_default_indexes => false,
  if_not_exists => true
);

-- PostgreSQL declarative partitioned table
BEGIN;
ALTER TABLE <schema>.<table> RENAME TO <table>_part;
CREATE TABLE <schema>.<table>(LIKE <schema>.<table>_part INCLUDING ALL);
SELECT create_hypertable('<schema>.<table>', by_range('<time_column>', INTERVAL '7 days'));
COMMIT;
```

Primary key and unique constraints must include the partition column.

### Apply privileges

After restoring the schema on the target, export privileges from the source and apply them to the migrated objects:

```bash
psql "$SOURCE" -t -A <<'EOF' > privileges.sql
-- Schema privileges
SELECT 'GRANT ' || acl.privilege_type ||
  ' ON SCHEMA ' || quote_ident(nspname) ||
  ' TO ' || CASE WHEN acl.grantee = 0 THEN 'PUBLIC'
    ELSE acl.grantee::regrole::text END ||
  CASE WHEN acl.is_grantable THEN ' WITH GRANT OPTION' ELSE '' END || ';'
FROM pg_namespace, LATERAL aclexplode(nspacl) AS acl
WHERE nspacl IS NOT NULL
  AND nspname NOT IN ('pg_catalog', 'information_schema')
  AND nspname NOT LIKE '_timescale%'
  AND nspname NOT LIKE 'timescaledb%'
  AND nspname NOT LIKE 'toolkit%'
  AND acl.grantee::regrole::text NOT LIKE 'pg_%'
  AND acl.grantee::regrole::text NOT LIKE 'timescaledb%'
  AND acl.grantee::regrole::text NOT IN ('postgres')
ORDER BY nspname;

-- Table privileges
SELECT 'GRANT ' || acl.privilege_type ||
  ' ON TABLE ' || format('%I.%I', n.nspname, c.relname) ||
  ' TO ' || CASE WHEN acl.grantee = 0 THEN 'PUBLIC'
    ELSE acl.grantee::regrole::text END ||
  CASE WHEN acl.is_grantable THEN ' WITH GRANT OPTION' ELSE '' END || ';'
FROM pg_class c
JOIN pg_namespace n ON c.relnamespace = n.oid,
LATERAL aclexplode(relacl) AS acl
WHERE relacl IS NOT NULL
  AND relkind IN ('r', 'v', 'm', 'f', 'p')
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND n.nspname NOT LIKE '_timescale%'
  AND n.nspname NOT LIKE 'timescaledb%'
  AND n.nspname NOT LIKE 'toolkit%'
  AND acl.grantee::regrole::text NOT LIKE 'pg_%'
  AND acl.grantee::regrole::text NOT LIKE 'timescaledb%'
  AND acl.grantee::regrole::text NOT IN ('postgres')
ORDER BY n.nspname, c.relname;
EOF

cat privileges.sql
psql "$TARGET" -f privileges.sql
```

## Consolidate multiple source tables into one hypertable

Some applications partition data themselves: every period gets its own table with the same columns, for example `metrics-001`, `metrics-002`, and so on, one per month. Livesync can merge these tables into a single {C.HYPERTABLE} on the target during the migration, so the target ends up with one `metrics` {C.HYPERTABLE} partitioned by time instead of many tables. Tables that you don't map, such as lookup tables, sync one-to-one alongside it.

To do this, point several source tables at the same target with a regular expression in `--table-map`. This section uses the {C.SELF_SHORT} Docker image. Many tables with the same shape suit the initial copy well: each source table is copied by its own worker, in parallel with the others.

Complete the steps in this section before you [start Livesync](#data-migration). They build on [Schema migration](#schema-migration), and replace the parts of [Publication](#publication) and [Replication identity](#replication-identity) that concern the tables you consolidate.

### How `--table-map` matches tables

Each `--table-map` value is a JSON object with a `source` and a `target`, each with a `schema` and a `table`:

- **Schema**: `source.schema` must match the source schema exactly.
- **Table**: `source.table` is a [Go regular expression](https://pkg.go.dev/regexp/syntax). Livesync anchors it for you, so `metrics-[0-9]+` matches `metrics-001` but not `app_metrics-001` or `metrics-001_old`.
- **Anchors**: Livesync adds `^` and `$` only when the pattern has neither. Write both anchors or none. `^metrics-[0-9]+` on its own also matches `metrics-001_old`.
- **Order**: rules apply in the order you pass them, and the first match wins. Put specific rules before broad patterns.
- **Whole schema**: omit `table` in both `source` and `target` to sync every table in a schema to another schema, keeping the table names.
- **No match**: a table that matches no rule syncs to the table with the same schema and name on the target.

Repeat `--table-map` once for each rule. Use double quotes inside the JSON. Single quotes fail with `failed to unmarshal TableMap`.

The examples below consolidate `public."metrics-001"`, `public."metrics-002"`, and so on into `public.metrics`, and sync `public.devices` one-to-one. Table names that contain a hyphen need double quotes in SQL.

<NumberedList>
<NumberedItem title="Make the replica identity unique across the merged tables">

Livesync applies `UPDATE` and `DELETE` on the target by matching the source table's [replica identity](#replication-identity) columns, by default the primary key. The target doesn't record which source table a row came from. If the replica identity is only unique within each source table, for example an `id` sequence that restarts at 1 in every monthly table, one `UPDATE` or `DELETE` on the source matches the rows with the same key from every merged table.

<Callout variant="warning">
With a replica identity that is not unique across the merged tables:

- An `UPDATE` rewrites the matching row of every merged table. On a {C.HYPERTABLE}, this usually violates a chunk constraint: Livesync retries, then stops, and replication halts for every table in the subscription. On a regular table, the `UPDATE` succeeds and overwrites rows that came from other source tables, with no error.
- A `DELETE` removes the matching row of every merged table, with no error.

Changing the replica identity only affects changes made after the change. Set it before you create the publication and start Livesync.
</Callout>

Choose one of these options for every source table you merge:

- **Append-only data**: publish inserts only, and skip the rest of this step. Livesync then never receives `UPDATE` or `DELETE` for these tables, so changes of that kind on the source are not replicated. Put the tables in their own publication, as shown in the publication step below.

- **A key that is unique across all the tables**, such as `(device_id, time)` when the tables cover different time ranges: create a unique index on it in each source table, and use that index as the replica identity. The index columns must be `NOT NULL`. First, confirm the key has no duplicates across the tables. This query must return `0`:

  ```bash
  psql "$SOURCE" -t -A <<'EOF' > check_key.sql
  SELECT 'SELECT count(*) FROM (SELECT device_id, time FROM ('
    || string_agg(format('SELECT device_id, time FROM %I.%I', schemaname, tablename), ' UNION ALL ')
    || ') u GROUP BY device_id, time HAVING count(*) > 1) d;'
  FROM pg_tables
  WHERE schemaname = 'public' AND tablename ~ '^metrics-[0-9]+$';
  EOF

  psql "$SOURCE" -f check_key.sql
  ```

  Then create the indexes and set the replica identity:

  ```bash
  psql "$SOURCE" -t -A <<'EOF' > replica_identity.sql
  SELECT format(
    E'CREATE UNIQUE INDEX CONCURRENTLY %I ON %I.%I (device_id, time);\nALTER TABLE %I.%I REPLICA IDENTITY USING INDEX %I;',
    tablename || '_device_time', schemaname, tablename,
    schemaname, tablename, tablename || '_device_time'
  )
  FROM pg_tables
  WHERE schemaname = 'public' AND tablename ~ '^metrics-[0-9]+$';
  EOF

  cat replica_identity.sql
  psql "$SOURCE" -f replica_identity.sql
  ```

- **Any other case**: use `REPLICA IDENTITY FULL`. Livesync then matches on every column of the row. This needs no new index on the source, but {C.PG} writes the whole old row to the write-ahead log for every `UPDATE` and `DELETE`, which increases the write-ahead log volume on the source:

  ```bash
  psql "$SOURCE" -t -A <<'EOF' > replica_identity.sql
  SELECT format('ALTER TABLE %I.%I REPLICA IDENTITY FULL;', schemaname, tablename)
  FROM pg_tables
  WHERE schemaname = 'public' AND tablename ~ '^metrics-[0-9]+$';
  EOF

  cat replica_identity.sql
  psql "$SOURCE" -f replica_identity.sql
  ```

</NumberedItem>

<NumberedItem title="Create the target hypertable">

Livesync doesn't create target tables. Create the consolidated table on the target and make it a {C.HYPERTABLE} before you start Livesync. Converting a table to a {C.HYPERTABLE} after its sync has started is not supported: you have to remove the table from the sync, then add it back, which copies its data again.

Run [Schema migration](#schema-migration) as usual. It creates the source tables you merge on the target as regular tables. Use one of them as the template for the {C.HYPERTABLE}:

```sql
psql "$TARGET" <<'EOF'
CREATE TABLE public.metrics (LIKE public."metrics-001" INCLUDING DEFAULTS)
WITH (
  tsdb.hypertable,
  tsdb.partition_column = 'time',
  tsdb.chunk_interval = '7 days'
);

ALTER TABLE public.metrics ALTER COLUMN id DROP DEFAULT;
EOF
```

`LIKE` copies the column names, types, `NOT NULL` constraints, and, with `INCLUDING DEFAULTS`, the column defaults. It doesn't copy the primary key, unique constraints, or indexes, so the per-table key on `id` stays behind. The `ALTER TABLE` statement removes the default that `INCLUDING DEFAULTS` copies from a `serial` or `bigserial` column: it points to the sequence of `metrics-001`, which means nothing for merged data and would stop you from dropping `metrics-001` in the next step. Run it for each such column.

Livesync doesn't sync to the source tables you merge, so drop them from the target:

```bash
psql "$TARGET" -t -A <<'EOF' > drop_merged_tables.sql
SELECT format('DROP TABLE %I.%I;', schemaname, tablename)
FROM pg_tables
WHERE schemaname = 'public' AND tablename ~ '^metrics-[0-9]+$';
EOF

cat drop_merged_tables.sql
psql "$TARGET" -f drop_merged_tables.sql
```

If a view or foreign key on the target still references one of these tables, `DROP TABLE` fails. Point that object at `public.metrics` instead, then drop the table.

Choose the target's keys with the merged data in mind:

- Primary key and unique constraints on a {C.HYPERTABLE} must include the partition column.
- Don't add a primary key or unique constraint on a column that is only unique within each source table, such as a per-table `id` sequence. The initial copy of the second source table then fails with `duplicate key value violates unique constraint`. A colliding `INSERT` during replication halts replication for the whole subscription.
- If you need a unique constraint, use a key that you confirmed is unique across the tables, for example `UNIQUE (device_id, time)`.

</NumberedItem>

<NumberedItem title="Create the publication">

List every source table explicitly. This query generates the statement for the tables that match the pattern:

```bash
psql "$SOURCE" -t -A <<'EOF' > publication.sql
SELECT 'CREATE PUBLICATION metrics_pub FOR TABLE '
  || string_agg(format('%I.%I', schemaname, tablename), ', ' ORDER BY tablename)
  || ';'
FROM pg_tables
WHERE schemaname = 'public' AND tablename ~ '^metrics-[0-9]+$';
EOF

cat publication.sql
psql "$SOURCE" -f publication.sql
```

For append-only data, append `WITH (publish = 'insert')` to the generated statement before you run it. Create a separate publication for the tables you sync one-to-one:

```sql
psql "$SOURCE" <<'EOF'
CREATE PUBLICATION app_pub FOR TABLE public.devices;
EOF
```

</NumberedItem>

<NumberedItem title="Start Livesync with the table map">

Pass one `--table-map` rule for each group of tables you merge. `public.devices` matches no rule, so it syncs to `public.devices`:

```bash
docker run -d --name livesync timescale/live-sync:latest run \
  --publication metrics_pub \
  --publication app_pub \
  --subscription <subscription_name> \
  --source "$SOURCE" \
  --target "$TARGET" \
  --table-map '{"source": {"schema": "public", "table": "metrics-[0-9]+"}, "target": {"schema": "public", "table": "metrics"}}'
```

While you validate the migration, run the container without `--rm`. If Livesync stops after repeated errors, for example because of a replica identity that is not unique across the merged tables, the process exits with status `0`. Docker then removes the container and its logs if you started it with `--rm`. The error appears only in `docker logs livesync`, not in `_ts_live_sync.subscription`.

</NumberedItem>

<NumberedItem title="Check the mapping">

Confirm that every source table maps to the intended target:

```bash
psql "$TARGET" -c "
  SELECT schemaname, tablename, target_schema, target_table, state
  FROM _ts_live_sync.subscription_rel
  ORDER BY schemaname, tablename;
"
```

After all tables reach state `r`, compare the row count of the {C.HYPERTABLE} on the target with the sum of the row counts of the source tables.

</NumberedItem>
</NumberedList>

### Add source tables during the sync

When your app creates a new table during the migration, for example at the start of a new month, the regular expression already matches its name, but Livesync picks it up only after you add it to the publication and refresh:

<NumberedList>
<NumberedItem title="Set the replica identity of the new table">

Use the same option you chose for the other merged tables, for example:

```sql
psql "$SOURCE" <<'EOF'
ALTER TABLE public."metrics-013" REPLICA IDENTITY FULL;
EOF
```

</NumberedItem>

<NumberedItem title="Add the table to the publication">

```sql
psql "$SOURCE" <<'EOF'
ALTER PUBLICATION metrics_pub ADD TABLE public."metrics-013";
EOF
```

</NumberedItem>

<NumberedItem title="Refresh the publication with the same table map">

Pass the same `--table-map` rules that the running Livesync uses:

```bash
docker run -it --rm --name livesync-refresh \
  timescale/live-sync:latest refresh-publication \
  --subscription <subscription_name> \
  --source "$SOURCE" \
  --target "$TARGET" \
  --table-map '{"source": {"schema": "public", "table": "metrics-[0-9]+"}, "target": {"schema": "public", "table": "metrics"}}'
```

Livesync copies the rows the new table already contains, then replicates its changes. Rows written before you added the table to the publication are included in that copy.

</NumberedItem>
</NumberedList>

<Callout variant="important">
If you run `refresh-publication` without `--table-map`, Livesync maps the new table to a target table with the same name. The copy then fails with `relation "public.metrics-013" does not exist`, and running `refresh-publication` again with `--table-map` doesn't change the mapping of a table that is already registered. To fix it, remove the table from the publication, run `refresh-publication`, add the table back, and run `refresh-publication` with `--table-map`.
</Callout>

<NumberedItem title="Apply database and role settings">

Settings applied on the source via `ALTER DATABASE ... SET` or `ALTER ROLE ... IN DATABASE ... SET` (for example, `search_path`, `timezone`, `statement_timeout`, `default_transaction_isolation`) are **not** included in `pg_dump --schema-only` or `pg_dumpall --roles-only`. If your application relies on them, generate equivalent statements from the source catalogs and apply them on the target.

Both `ALTER DATABASE ... SET` and `ALTER ROLE ... IN DATABASE ... SET` settings live in `pg_db_role_setting`, distinguished by `setrole = 0` (database-level) versus `setrole != 0` (role-specific). The query below reads settings from the source and generates statements that reference the target database name. Source and target database names typically differ (for example, source `migrate`, target `tsdb`):

```bash
# Resolve the target database name
TGT_DB=$(psql "$TARGET" -t -A -c "SELECT current_database();")

psql "$SOURCE" -t -A -v tgt_db="$TGT_DB" <<'EOF' > db_settings.sql
WITH pairs AS (
  SELECT
    drs.setrole,
    r.rolname,
    split_part(s, '=', 1) AS guc,
    CASE
      WHEN substring(s FROM position('=' IN s) + 1) LIKE '"%"' THEN
        replace(
          substring(s FROM position('=' IN s) + 2 FOR length(s) - position('=' IN s) - 2),
          '""', '"')
      ELSE
        substring(s FROM position('=' IN s) + 1)
    END AS val
  FROM pg_db_role_setting drs
  JOIN pg_database d ON d.oid = drs.setdatabase
  LEFT JOIN pg_roles r ON r.oid = drs.setrole,
  LATERAL unnest(drs.setconfig) s
  WHERE d.datname = current_database()
    AND (drs.setrole = 0
         OR (r.rolname NOT LIKE 'pg_%'
             AND r.rolname NOT IN ('postgres', 'tsdbadmin')))
)
SELECT
  CASE
    WHEN setrole = 0 THEN
      format('ALTER DATABASE %I SET %I = %L;', :'tgt_db', guc, val)
    ELSE
      format('ALTER ROLE %I IN DATABASE %I SET %I = %L;', rolname, :'tgt_db', guc, val)
  END
FROM pairs
ORDER BY setrole, guc;
EOF

cat db_settings.sql
psql "$TARGET" -f db_settings.sql
```

Review the generated statements before applying. Some settings (for example, shared library paths, filesystem paths, replication-specific parameters) may not apply to a managed {C.SERVICE_LONG} and should be removed.

</NumberedItem>
</NumberedList>
