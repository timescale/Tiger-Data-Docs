[sqlflow](https://github.com/turbolytics/sql-flow) is a stream processor that runs SQL over batches of messages. It reads a source such as Kafka, runs a DuckDB query over each batch, and writes the result to a sink. It runs as a single container.

Devices export readings to a Kafka topic as they happen. Each reading carries a device ID and a value, but not the site or model that dashboards group by. This page puts sqlflow between the topic and your {C.SERVICE_LONG}: every batch of readings joins a `devices` table that lives in the service, and the enriched rows land in a {C.HYPERTABLE}. Queries read wide rows without a join, and the reference data stays in one place.

Every command and output on this page was run on 2026-09-11 with sqlflow `v1.2.0` against a {C.SERVICE_LONG} running {C.TIMESCALE_DB} 2.29.2. The commands pin that image tag.

In this integration guide, you:

- Create a `devices` reference table and a `readings` {C.HYPERTABLE} in your {C.SERVICE_LONG}.
- Create a Kafka topic and write the sqlflow pipeline that joins each batch from it against `devices` and inserts the result into `readings`.
- Publish test readings to the topic and verify the enriched rows in your {C.HYPERTABLE}.

## Prepare your service

The pipeline reads one table and writes another. `devices` is the reference data, one row per device. `readings` is the {C.HYPERTABLE} that receives the enriched stream.

<NumberedList>
  <NumberedItem title={`Connect to your ${C.SERVICE_LONG}`}>
    Use the [{C.CONSOLE}](/build/data-management/run-queries-from-tiger-console), `psql`, or any SQL editor to connect to your service.
  </NumberedItem>
  <NumberedItem title="Create the reference table and load it">
    `site` and `model` are the columns the join copies onto every reading:

    ```sql
    CREATE TABLE devices (
      device_id TEXT PRIMARY KEY,
      site      TEXT NOT NULL,
      model     TEXT NOT NULL
    );

    INSERT INTO devices (device_id, site, model) VALUES
      ('d-100', 'oslo',   'tx-2'),
      ('d-200', 'lisbon', 'tx-2'),
      ('d-300', 'lisbon', 'tx-3');
    ```
  </NumberedItem>
  <NumberedItem title={`Create a ${C.HYPERTABLE} for the enriched readings`}>
    `site` and `model` are nullable. A reading from a device that is not in `devices` still lands, with those two columns empty, rather than being dropped:

    ```sql
    CREATE TABLE readings (
      time      TIMESTAMPTZ      NOT NULL,
      device_id TEXT             NOT NULL,
      site      TEXT,
      model     TEXT,
      value     DOUBLE PRECISION,
      PRIMARY KEY (time, device_id)
    ) WITH (
      timescaledb.hypertable,
      timescaledb.chunk_interval = '7 days'
    );
    ```

    The primary key is what makes the pipeline safe to restart. sqlflow delivers at least once: if it stops after writing a batch but before committing its Kafka offset, it writes that batch again on restart. The sink's `ON CONFLICT DO NOTHING` below turns that second write into a no-op. It has to be a primary key rather than a unique index, because DuckDB only learns about primary keys on an attached table. One reading per device per timestamp is the key.
  </NumberedItem>
</NumberedList>

## Prepare the Kafka topic

sqlflow does not create topics. On a broker with `auto.create.topics.enable=false`, a missing topic means the pipeline starts and waits forever.

<NumberedList>
  <NumberedItem title="Create the readings topic">
    In `<KAFKA_HOME>`, run:

    ```bash
    ./bin/kafka-topics.sh --create \
      --topic readings \
      --bootstrap-server localhost:9092
    ```

    Replace `localhost:9092` with your broker address if Kafka runs elsewhere. The command prints `Created topic readings.`
  </NumberedItem>
</NumberedList>

## Configure sqlflow

A sqlflow pipeline is one YAML file. The `commands` block runs once at startup and attaches your service to DuckDB. The `handler` query runs once per batch, with the batch's messages available as a table named `batch`. The `sink` inserts the handler's output, available as `sqlflow_sink_batch`, into your {C.HYPERTABLE}.

<NumberedList>
  <NumberedItem title="Write the pipeline configuration">
    Create an empty directory, and save the following in it as `tigerdata.enrich.yml`. Values in `{{ }}` are read from environment variables when the pipeline starts; the ones with `default(...)` are optional:

    ```yaml
    commands:
      - name: load the postgres extension
        sql: |
          INSTALL postgres;
          LOAD postgres;

      # One attach serves both directions: the join reads devices from it and
      # the sink inserts readings into it. The DSN is a required input with no
      # default on purpose; a production pipeline should not carry a bunk one.
      - name: attach the service
        sql: |
          ATTACH '{{ SQLFLOW_TIGERDATA_DSN }}' AS tiger (TYPE POSTGRES);

    pipeline:
      name: tigerdata-enrich
      description: "Enrich a stream of readings with device metadata from the service, and land them in a hypertable"
      batch_size: {{ SQLFLOW_BATCH_SIZE|default('500') }}

      source:
        type: kafka
        kafka:
          brokers: [{{ SQLFLOW_KAFKA_BROKERS|default('localhost:9092') }}]
          group_id: {{ SQLFLOW_GROUP_ID|default('tigerdata-enrich') }}
          auto_offset_reset: earliest
          topics:
            - "{{ SQLFLOW_TOPIC|default('readings') }}"

      # LEFT JOIN, so a reading from a device the reference table does not know
      # still lands, with site and model NULL, rather than being dropped.
      handler:
        type: 'handlers.InferredMemBatch'
        sql: |
          SELECT
            CAST(batch.ts AS TIMESTAMPTZ) AS time,
            batch.device_id,
            devices.site,
            devices.model,
            batch.value
          FROM batch
          LEFT JOIN tiger.{{ SQLFLOW_TIGERDATA_SCHEMA|default('public') }}.devices AS devices
            ON batch.device_id = devices.device_id

      # Delivery is at-least-once: a crash between this insert and the offset
      # commit replays the batch on restart. The unique index on (time,
      # device_id) plus ON CONFLICT DO NOTHING makes the replay a no-op.
      sink:
        type: sqlcommand
        sqlcommand:
          sql: |
            INSERT INTO tiger.{{ SQLFLOW_TIGERDATA_SCHEMA|default('public') }}.readings
              (time, device_id, site, model, value)
            SELECT time, device_id, site, model, value FROM sqlflow_sink_batch
            ON CONFLICT DO NOTHING
    ```

    What each part does:

    - `commands` installs and loads DuckDB's {C.PG} extension, then attaches your service under the name `tiger`. Tables in the service are reachable as `tiger.<schema>.<table>`.
    - `source` subscribes to the topic as consumer group `tigerdata-enrich`. `auto_offset_reset: earliest` reads a topic from its first message when the group has no committed offset yet.
    - `handler` runs the join. Each Kafka message must be a JSON object with three fields: `ts`, a timestamp string such as `2026-09-11T15:00:00Z`; `device_id`, a string; and `value`, a number. Extra fields are ignored.
    - `sink` inserts the joined rows. `batch_size` is how many messages one handler call sees. A batch that has not filled after 30 seconds is written anyway, so a quiet topic still lands its readings.
    - `SQLFLOW_TIGERDATA_SCHEMA` defaults to `public`. Set it if you created the tables in another schema.
  </NumberedItem>
  <NumberedItem title="Set the connection string and validate the pipeline">
    Build the connection string from your [connection details](/integrate/find-connection-details) and export it. `sslmode=require` is needed for {C.CLOUD_LONG}. If the password contains characters such as `@`, `/`, or `#`, percent-encode them:

    ```bash
    export SQLFLOW_TIGERDATA_DSN="postgres://tsdbadmin:<password>@<host>:<port>/tsdb?sslmode=require"
    ```

    Then, from the directory that holds `tigerdata.enrich.yml`, check the file:

    ```bash
    docker run --rm -v "$PWD":/conf \
      -e SQLFLOW_TIGERDATA_DSN \
      turbolytics/sql-flow:v1.2.0 validate /conf/tigerdata.enrich.yml
    ```

    `-v "$PWD":/conf` mounts the current directory into the container, which is where the file path `/conf/tigerdata.enrich.yml` comes from. `-e SQLFLOW_TIGERDATA_DSN` passes the exported variable through. `validate` checks the file offline without reaching the broker or the service. The report ends with:

    ```
    /conf/tigerdata.enrich.yml: valid
    ```
  </NumberedItem>
  <NumberedItem title="Start the pipeline">
    From the same directory:

    ```bash
    docker run -d --name sqlflow-tiger -v "$PWD":/conf \
      -e SQLFLOW_TIGERDATA_DSN \
      -e SQLFLOW_KAFKA_BROKERS=<broker>:9092 \
      -e SQLFLOW_TOPIC=readings \
      turbolytics/sql-flow:v1.2.0 run /conf/tigerdata.enrich.yml
    ```

    `-d --name sqlflow-tiger` runs the container in the background under a name the next steps use. `SQLFLOW_KAFKA_BROKERS` must be an address the container can reach. That is not `localhost` when Kafka runs on the host, because `localhost` inside the container is the container. Use the host's IP address, or `host.docker.internal` on Docker Desktop, and make sure the broker advertises a listener on that address.

    Check the log:

    ```bash
    docker logs sqlflow-tiger
    ```

    It shows `consumer loop starting` once the pipeline has attached your service and joined the consumer group. To stop the pipeline later, run `docker stop sqlflow-tiger`.
  </NumberedItem>
</NumberedList>

## Verify the integration

<NumberedList>
  <NumberedItem title="Publish test readings to the topic">
    In `<KAFKA_HOME>`, send three readings with the console producer. The third names a device that is not in `devices`:

    ```bash
    printf '%s\n' \
      '{"ts": "2026-09-11T15:00:00Z", "device_id": "d-100", "value": 21.4}' \
      '{"ts": "2026-09-11T15:00:01Z", "device_id": "d-200", "value": 19.8}' \
      '{"ts": "2026-09-11T15:00:02Z", "device_id": "d-999", "value": 22.1}' \
    | ./bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic readings
    ```

    Within 30 seconds, `docker logs sqlflow-tiger` shows a `throughput` line with `"messages_consumed": 3`.
  </NumberedItem>
  <NumberedItem title={`Query the ${C.HYPERTABLE} in your ${C.SERVICE_LONG}`}>
    Connect to your service and run:

    ```sql
    SELECT time, device_id, site, model, value
    FROM readings
    ORDER BY time;
    ```

    The two known devices carry their site and model. The unknown one landed with both empty:

    ```
              time          | device_id |  site  | model | value
    ------------------------+-----------+--------+-------+-------
     2026-09-11 15:00:00+00 | d-100     | oslo   | tx-2  |  21.4
     2026-09-11 15:00:01+00 | d-200     | lisbon | tx-2  |  19.8
     2026-09-11 15:00:02+00 | d-999     |        |       |  22.1
    (3 rows)
    ```

    Because `site` is already on the row, a dashboard query is a plain aggregate over the {C.HYPERTABLE}:

    ```sql
    SELECT time_bucket('5 minutes', time) AS bucket, site, avg(value)
    FROM readings
    WHERE site IS NOT NULL
    GROUP BY bucket, site
    ORDER BY bucket, site;
    ```

    ```
             bucket         |  site  | avg
    ------------------------+--------+------
     2026-09-11 15:00:00+00 | lisbon | 19.8
     2026-09-11 15:00:00+00 | oslo   | 21.4
    (2 rows)
    ```
  </NumberedItem>
</NumberedList>

You have successfully integrated sqlflow with {C.COMPANY}.

## Troubleshooting

- **The log ends with `Failed to download extension "postgres_scanner"`:** the container cannot reach `extensions.duckdb.org`. The DuckDB {C.PG} extension is fetched on first start, so allow outbound access to that host or run the container on a network that has it.
- **The log repeats `unable to dial` with `127.0.0.1:9092`:** the broker advertised a listener the container cannot reach. Set `SQLFLOW_KAFKA_BROKERS` to a listener that resolves from inside the container, and check the broker's advertised listeners.
- **The log shows `no messages consumed` and nothing lands:** the topic name is wrong, or the consumer group has already committed past your test messages. `auto_offset_reset: earliest` applies only to a group with no committed offset, so set a new `SQLFLOW_GROUP_ID` to read the topic from the start.
- **`ATTACH` fails with an authentication or SSL error:** check the connection string against your connection details, keep `sslmode=require`, and percent-encode any special characters in the password.
- **Rows land with empty `site` and `model`:** the device ID is not in `devices`. Insert the device; rows that already landed keep their empty columns.

For general connection issues, see [Troubleshooting](/integrate/troubleshooting).

## Limitations

- This page runs a stateless pipeline: each batch is enriched and written on its own. sqlflow also runs windowed aggregations over a stream, and those are not covered here.
- Delivery is at least once. The primary key and `ON CONFLICT DO NOTHING` make a replayed batch a no-op, which was checked by consuming the same three readings twice under two consumer groups: the second run inserted nothing. A second reading from the same device with the same `ts` is treated as that replay and dropped.
