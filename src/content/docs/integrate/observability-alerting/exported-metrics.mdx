This page lists the metrics you can export with all {C.CLOUD_LONG} exporters:

- [{C.CLOUD_LONG} metrics](#tiger-cloud-metrics)
- [{C.PG} metrics](#postgresql-metrics): [exporter](#exporter-metrics), [lock](#lock-metrics), [replication](#replication-metrics), [PG settings](#pg-settings-metrics), [PG stats](#pg-stats-metrics)

- [{C.LAKE} metrics](#tiger-lake-metrics): [connector](#connector-metrics), [replication lag](#replication-lag-metrics)

Every metric carries the `project_id`, `region`, and `service_id` labels, so you can filter them by these. Many metrics also carry `role`, and some carry extra labels.

You can also query these metrics ad hoc, without setting up an exporter, using the [`tiger service metrics`](/reference/tiger-cloud/tiger-cli#tiger-service-metrics-available) commands in {C.CLI_LONG} or the [metrics tools](/reference/tiger-cloud/tiger-mcp#metrics-tools) in {C.MCP_LONG}.

<Callout variant="note">

The following limitations apply for replica metrics:
- For HA replicas, metrics are only exported for the primary and one HA replica.
- For read replica sets, metrics are exported for the primary/`standby_leader` and one read replica.

</Callout>

## {C.PG} metrics

These additional metrics are collected if you enable **{C.PG} metrics** when creating {C.CLOUD_LONG} exporters.
All metrics have a scrape interval of 15 seconds.

### Exporter metrics

These metrics show the health and status of the metrics collection process, including scrape duration, errors, and total scrape count.

|Metric|Description|
|-|-|
|`pg_exporter_last_scrape_duration_seconds`|Duration of the last scrape of metrics from {C.PG}.|
|`pg_exporter_last_scrape_error`|Whether the last scrape of metrics from {C.PG} resulted in an error (1 for error, 0 for success).|
|`pg_exporter_scrapes_total`|Total number of times {C.PG} was scraped for metrics.|
|`pg_exporter_user_queries_load_error`|Whether the user queries file was loaded and parsed successfully (1 for error, 0 for success).|

## {C.TIMESCALE_DB} metrics

These additional metrics are collected if you enable `TimescaleDB metrics` when creating {C.CLOUD_LONG} exporters. This option is separate from `PostgreSQL metrics`.

### Job metrics

These metrics show the state of the background jobs of your service. This includes policy jobs, such as compression, retention, and continuous aggregate refresh, and your own user-defined jobs.

|Metric|Description|
|-|-|
|`timescaledb_job_runs_total`|Total number of finished job runs. The `status` label is `success` or `failure`.|
|`timescaledb_job_failing_for_seconds`|Seconds since the job last succeeded. This metric exists only while the last run of the job failed.|
|`timescaledb_job_overdue_seconds`|Seconds a scheduled job that is not running is late. This metric exists only while the job is late.|
|`timescaledb_job_running`|Number of jobs running now. This metric exists only while a job is running.|
|`timescaledb_job_schedule_interval_seconds`|How often the job is scheduled to run, in seconds. Paused jobs are included, with the `scheduled` label set to `false`.|

Job metrics carry these extra labels:

|Label|Description|
|-|-|
|`job_type`|The kind of built-in policy the job runs: `columnstore`, `compaction`, `continuous aggregate refresh`, `reorder`, `retention`, or `tiered storage`. It is `user defined` for any other job.|
|`proc_name`|The procedure the job runs, as `schema.name`.|
|`target_object`|The hypertable or continuous aggregate the job acts on, as `schema.name`. It is empty if the job has no target.|

Jobs only run on the primary, so job metrics carry no `role` or `ordinal` label, except `timescaledb_job_running`.

Each metric covers at most 1000 jobs per service. In `timescaledb_job_runs_total`, the jobs beyond the first 1000 are summed into one series for each `job_type` and `status`, with `proc_name` and `target_object` set to `overflow`.
