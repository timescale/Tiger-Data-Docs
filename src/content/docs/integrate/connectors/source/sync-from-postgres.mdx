# Source Postgres connector

The source {C.PG} connector is the connection tool Tiger Cloud uses to synchronize data from a {C.PG} instance to your service. It uses the [{C.PG} logical replication protocol](https://www.postgresql.org/docs/current/logical-replication.html) and the [PUBLICATION](https://www.postgresql.org/docs/current/sql-createpublication.html) interface, so you can add or remove tables on demand and keep the connector compatible with standard {C.PG} tooling and knowledge.

## What the connector does

- **Copy existing data** from a {C.PG} instance to a Tiger Cloud service (initial load).
- **Stream ongoing changes** in real time (logical replication).
- **Respect PUBLICATION** so you control which tables are replicated by adding or removing them from the publication on the source.

The connector is intended for **synchronization** (continuous replication), not one-off migration. For migration workflows and full how-to steps, use [Sync data from Postgres](/migrate/livesync-for-postgresql).

## Capabilities

- **Throughput:** Copy at up to ~150 GB/hr. Minimum recommended: 4 CPU / 16 GB on both source and target.
- **Parallel copy:** Publication tables are copied in parallel; very large tables use a single connection (parallel per-table is planned).
- **Foreign keys:** Disabled during sync. You can sync a table without syncing its referenced tables; the connector does not validate FKs on the target.
- **Progress:** {C.PG} exposes copy progress in `pg_stat_progress_copy` so you can monitor initial load.

## Connection and source requirements

- **Direct connection:** Use a connection string that reaches the database directly. Do not route through connection poolers (e.g. PgBouncer); the connector needs a direct connection.
- **Source version:** {C.PG} 13 or later.
- **Network:** Source must be reachable from the Internet. Connector support for sources behind a firewall or VPC is on the roadmap.
- **Extensions:** Source and target must have the same extensions installed. The connector does not create extensions on the target. If a table uses extension types, create the extension on the target Tiger Cloud service before syncing that table.

## Tune your source database

For the connector to work, the source must have logical replication enabled. Set:

- `wal_level = logical`
- Sufficient `max_replication_slots` and `max_wal_senders`

The exact connection string and parameters used by the connector (e.g. for the `<pg connector username>`) are shown in Tiger Console when you add a source {C.PG} connector. Use the same connection details and ensure the source user has privileges to use logical replication and the chosen publication.

## Limitations (reference)

- Indexes, primary key, unique constraints, and sequences are **not** migrated. Create needed indexes on the target for your queries.
- TimescaleDB as source has limited support (e.g. no continuous aggregates).
- Schema changes must be coordinated: apply compatible changes on the target first, then on the source.
- WAL volume on the source increases during large table copy.
- **Continuous aggregates:** The connector uses `session_replication_role=replica` during copy, so triggers (including continuous aggregate invalidation) do not run. Data synced during initial load below a continuous aggregate’s materialization watermark may not appear in the aggregate until you manually refresh. If the aggregate exists on the source, include it in the connector’s publication; if only on the target, use the `force` option of [refresh_continuous_aggregate](/api-reference/timescaledb/continuous-aggregates/refresh_continuous_aggregate) to refresh affected ranges.
