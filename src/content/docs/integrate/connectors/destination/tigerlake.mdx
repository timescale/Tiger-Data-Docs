{C.ICEBERG_CONNECTOR_LONG} enables you to build real-time applications alongside efficient data pipeline management within a single
system.

<ThemeImage light={imgIcebergConnectorTigerCloudLight} dark={imgIcebergConnectorTigerCloudDark} alt="Tiger Lake architecture: Iceberg connector in Tiger Cloud" />

{C.ICEBERG_CONNECTOR_LONG} synchronizes {C.HYPERTABLE}s and relational tables running in {C.SERVICE_LONG}s to Apache Iceberg
tables. You can write to [Amazon S3 Tables](https://aws.amazon.com/s3/features/tables/) in your AWS account, or
connect to a compatible Iceberg REST catalog.

{C.ICEBERG_CONNECTOR_SHORT} takes an initial snapshot of the source table, then continuously applies inserts, updates, and
deletes using {C.PG} logical replication. This makes operational data available in your data lake without building
and operating a separate ETL pipeline.

Once set up, you can query that data directly. For example, see
[Query {C.LAKE} S3 Tables with AWS Glue and Athena](/integrate/connectors/destination/athena) or
[Query {C.LAKE} S3 Tables from Snowflake](/integrate/connectors/destination/snowflake).

## Choose an Iceberg catalog

{C.ICEBERG_CONNECTOR_LONG} supports the following catalog options:

| Catalog | Use when |
| --- | --- |
| Amazon S3 Tables | You want an AWS-managed Iceberg catalog and storage service. {C.ICEBERG_CONNECTOR_SHORT} connects using an IAM role. |
| Generic Iceberg REST catalog | You already use a compatible Iceberg REST catalog, such as Snowflake Open Catalog, Apache Polaris, Snowflake Horizon Catalog, or Databricks Unity Catalog. {C.ICEBERG_CONNECTOR_SHORT} connects using OAuth 2.0 client credentials or a personal access token. |

{C.LAKE} is available for {C.SERVICE_SHORT}s on AWS and Azure. Amazon S3 Tables requires a {C.SERVICE_SHORT} on AWS;
{C.SERVICE_SHORT}s on Azure connect through a generic Iceberg REST catalog.

Amazon S3 Tables is configured separately because it uses AWS IAM and SigV4 authentication. Generic REST catalogs
use the Iceberg REST Catalog API, and can provide access to the underlying object storage through vended
credentials.

<Callout variant="note">
Some catalogs and query engines, such as Snowflake and Databricks, cannot read Iceberg equality deletes. If
yours cannot, use [changelog mode](/integrate/connectors/destination/tigerlake#changelog-mode).
</Callout>

## Connect using an Iceberg REST catalog

Before creating the connector, configure a catalog principal with permission to:

- Access the target warehouse.
- List and create namespaces.
- Create and update Iceberg tables.
- Commit Iceberg table metadata.
- Access the underlying object storage, if the catalog vends storage credentials.

To connect your {C.SERVICE_LONG} to a generic Iceberg REST catalog:

<NumberedList>
  <NumberedItem title="Select the catalog type">
    1. In [{C.CONSOLE}](https://console.cloud.tigerdata.com/dashboard/services), select your {C.SERVICE_SHORT}, then click `Connectors` > `Destination connectors` > `Create a new destination connector`.
    1. Select `Generic REST catalog`.
    1. Choose a preset for your catalog provider (`Snowflake Open Catalog / Polaris`, `Snowflake Horizon`, or `Databricks`), or keep `Generic REST` to configure the connection manually.
  </NumberedItem>
  <NumberedItem title="Configure the catalog connection">
    Enter the catalog connection and authentication settings:

    | Setting | Required | Description |
    | --- | --- | --- |
    | `Catalog URI` | Yes | HTTPS base URL of the Iceberg REST catalog. Don't include a namespace or table path. |
    | `Warehouse` | Yes | Warehouse, catalog, or external volume identifier expected by the catalog. The exact value depends on the catalog provider. |
    | `Client ID` | No | OAuth 2.0 client identifier. Leave empty when authenticating with a personal access token instead. |
    | `Client secret` | Yes | OAuth 2.0 client secret, or personal access token. {C.CLOUD_LONG} stores this value securely. |
    | `OAuth2 server URI` | No | Token endpoint of the catalog. Defaults to `<catalog-uri>/v1/oauth/tokens`. |
    | `Scope` | No | OAuth 2.0 scope required by the catalog. |
    | `Vended credentials` | No | Requests temporary object storage credentials from the catalog. Turn this on if your catalog supports it. |
    | `Additional headers` | No | Catalog-specific HTTP headers to include with REST requests. |

    The `Snowflake Horizon` preset asks for the Snowflake database instead of a warehouse and for a programmatic
    access token instead of a client secret, turns on vended credentials, and syncs every table in
    [changelog mode](#changelog-mode), because Snowflake cannot read equality deletes. Snowflake creates the schema
    and the tables with lowercase names, so quote them in queries.
  </NumberedItem>
  <NumberedItem title="Create the connector">
    Click `Set up connector`. {C.CLOUD_LONG} validates the catalog connection, credentials, and warehouse access
    before creating the connector. Initialization takes a couple of minutes.
  </NumberedItem>
  <NumberedItem title="Select the tables to sync">
    Choose a schema and the tables to sync, then click `Sync tables`. The connector creates the namespace and the
    Iceberg tables in the catalog. The `Advanced settings` are the same as for
    [Amazon S3 Tables](#connect-using-amazon-s3-tables).
  </NumberedItem>
</NumberedList>

<Callout variant="important">
The catalog URI must use HTTPS. The catalog principal must have permission to access the configured warehouse, and
to create or update its Iceberg namespaces and tables.
</Callout>

### Storage access for REST catalogs

A REST catalog manages Iceberg metadata; the underlying table data is still stored in object storage. When you turn
on `Vended credentials`, {C.ICEBERG_CONNECTOR_SHORT} requests temporary storage credentials from the catalog and uses them to
write Iceberg data files. Otherwise, configure your catalog's own access controls to grant {C.ICEBERG_CONNECTOR_SHORT} the
storage access it needs directly.

### Catalog-specific setup

The endpoint, warehouse identifier, OAuth 2.0 scope, and access-control model differ between catalog providers. Create
the required catalog principal and warehouse permissions in your catalog provider's own console before configuring
the connector in {C.CONSOLE}.

Selecting a preset in {C.CONSOLE} fills in known defaults for that provider. It doesn't create the warehouse,
catalog principal, or permissions on your behalf.

## Stream data from your service to your data lake

Records are imported in time order, from oldest to newest.
Your {C.HYPERTABLE} or relational table must have a primary key, or a composite primary key, to sync to Iceberg.
Continuous aggregates are the exception, see [Continuous aggregates](#continuous-aggregates).

When you start syncing, all data in the table is streamed to Iceberg in the following processes:

- Table snapshot: stream data from a snapshot of the source table to the destination Iceberg table at
  approximately 300,000 records a second. For larger tables, import speeds are approximately 1 billion records
  or 100 GB of data an hour. However, these numbers vary on table width and the complexity of the schema.
- Table changes: changes made to the source table after the snapshot (CDC) stream to a branch of the destination
  Iceberg table at approximately 30,000 events a second. Bursts above this rate are absorbed and caught up over
  time, depending on how long the burst lasts and how many extra events it brings.

Once the snapshot is imported, the snapshot and CDC branches are merged. Merging takes from a few seconds to ten minutes for tables of 5 TB or more. During the merge, new events wait in the WAL and are streamed to Iceberg afterwards. The Iceberg table is eventually consistent with the source.

To stream data from a {C.PG} relational table, or a {C.HYPERTABLE} in your {C.SERVICE_LONG} to your data lake, run the following
statement:

```sql
ALTER TABLE <table_name> SET (
  tigerlake.iceberg_sync = true | false,
  tigerlake.iceberg_partitionby = '<partition_specification>',
  tigerlake.iceberg_namespace = '<namespace>',
  tigerlake.iceberg_table = '<table>',
  tigerlake.iceberg_columns = '<column>, <column>',
  tigerlake.iceberg_spec_version = 2 | 3,
  tigerlake.enable_tiered_reads = true | false,
  tigerlake.iceberg_changelog_mode = true | false
)
```

- `tigerlake.iceberg_sync`: `boolean`, set to `true` to start streaming, or `false` to stop the stream. A stopped
  stream does not resume: setting the property to `true` again starts a new sync. Options you do not set in that
  statement take their defaults, including the table name, and the Iceberg table from the previous sync stays in
  the catalog.
- `tigerlake.iceberg_partitionby`: optional property to define a partition specification in Iceberg. By default the
  Iceberg table is partitioned as `day(<time-column of {HYPERTABLE}>)`. This default behavior is only applicable
  to {C.HYPERTABLE}s. You can only set this property when you start the sync. For more information, see
  [partitioning](/integrate/connectors/destination/tigerlake#partitioning-intervals).
- `tigerlake.iceberg_namespace`: optional property to set a namespace, the default is `timescaledb`.
- `tigerlake.iceberg_table`: optional property to specify a different table name. The default is
  `tigerlake_<database>_<schema>_<table>`, in lowercase. You can only set this property when you start the sync.
  For more information, see [Sample code](#sample-code).
- `tigerlake.iceberg_columns`: optional comma-separated list of the columns to sync. By default, all columns are
  synced. Include the primary key columns: without them, updates and deletes on the table fail. You can only set
  this property when you start the sync. For more information, see
  [Sync a subset of columns](#sync-a-subset-of-columns).
- `tigerlake.iceberg_spec_version`: optional `integer`, either `2` or `3`. The default for new syncs is `3`. Set it
  to `2` if the query engine or catalog you read the table with does not support format version 3. You can only set
  this property when you start the sync. For more information, see
  [Iceberg format version](/integrate/connectors/destination/tigerlake#iceberg-format-version).
- `tigerlake.enable_tiered_reads`: optional `boolean`, the default is `true`. Set to `false` to exclude data that has
  been moved to the [low-cost object storage tier](/learn/data-lifecycle/storage/about-storage-tiers) from the sync.
  You can only set this property when you start the sync. For more information, see
  [tiered data](/integrate/connectors/destination/tigerlake#tiered-data).
- `tigerlake.iceberg_changelog_mode`: optional `boolean`, the default is `false`. Set to `true` to write the Iceberg
  table as an append-only change log instead of one row per primary key. You can only set this property when you
  start the sync. For more information, see
  [changelog mode](/integrate/connectors/destination/tigerlake#changelog-mode).

### Partitioning intervals

By default, an Iceberg table synced from a {C.HYPERTABLE} is partitioned by `day(<time-column>)`. A table synced
from a {C.PG} relational table is not partitioned. To set the partitioning, use
[tigerlake.iceberg\_partitionby](/integrate/connectors/destination/tigerlake#sample-code). The following transforms are supported:

| Interval      | Description                                                               | Source types |
| ------------- |---------------------------------------------------------------------------| --- |
| `hour`        | Extract a timestamp hour, as hours from epoch. Epoch is 1970-01-01.       | `timestamp`, `timestamptz` |
| `day`         | Extract a date or timestamp day, as days from epoch.                      | `date`, `timestamp`, `timestamptz` |
| `month`       | Extract a date or timestamp month, as months from epoch.                  | `date`, `timestamp`, `timestamptz` |
| `year`        | Extract a date or timestamp year, as years from epoch.                    | `date`, `timestamp`, `timestamptz` |
| `truncate(<column>, <width>)` | Value truncated to width `<width>`, see [options](https://iceberg.apache.org/spec/#truncate-transform-details) | integer types |

These partitions define the behavior using the [Iceberg partition specification](https://iceberg.apache.org/spec/#partition-transforms).
The `week` transform is not supported.

### Tiered data

By default, data that has been moved to the [low-cost object storage tier](/learn/data-lifecycle/storage/about-storage-tiers)
is synced to Iceberg along with the data in local storage. To exclude it, set `tigerlake.enable_tiered_reads` to
`false` in the same statement that starts the sync:

```sql
ALTER TABLE my_hypertable SET (
  tigerlake.iceberg_sync = true,
  tigerlake.enable_tiered_reads = false
);
```

Note the following:

- You can only set `tigerlake.enable_tiered_reads` when you start the sync. Setting it on a table that is already
  syncing returns an error, because whether tiered data is included changes which rows the initial snapshot reads.
  To change it, stop the sync and start a new one.
- This property applies to the sync only, and is independent of the `timescaledb.enable_tiered_reads` setting that
  controls whether [your own queries read tiered data](/build/data-management/storage/query-tiered-data). Setting
  `tigerlake.enable_tiered_reads` to `false` keeps tiered data out of Iceberg even when
  `timescaledb.enable_tiered_reads` is enabled for the database or the session.
- Tiered data can be much larger than the data in local storage. Including it increases both the duration of the
  initial snapshot and the volume of data written to Iceberg.
- Tables that started syncing before this property was available were stamped with the value of
  `timescaledb.enable_tiered_reads` at the time of the upgrade, so their behavior did not change.

### Iceberg format version

New syncs create the Iceberg table using [format version](https://iceberg.apache.org/spec/#format-versioning) 3.
To use format version 2 instead, set `tigerlake.iceberg_spec_version` in the statement that starts the sync:

```sql
ALTER TABLE my_hypertable SET (
  tigerlake.iceberg_sync = true,
  tigerlake.iceberg_spec_version = 2
);
```

Note the following:

- The only accepted values are `2` and `3`. Any other value returns an error.
- You can only set `tigerlake.iceberg_spec_version` when you start the sync. To change the format version of a table
  that is already syncing, stop the sync and start a new one.
- Tables that started syncing before this property was available remain on format version 2.
- Amazon Athena reads format version 2 only. If you query Amazon S3 Tables with Athena, start the sync with
  `tigerlake.iceberg_spec_version = 2`, or select `Iceberg format v2` in {C.CONSOLE}.

### Changelog mode

By default, the Iceberg table holds one row per primary key. Updates and deletes are applied in place using Iceberg
equality deletes. Some query engines, such as Snowflake and Databricks, do not implement the full Iceberg
specification and cannot read equality delete files. These engines fail or return an error when the table contains
them.

Changelog mode writes every change as an insert into the Iceberg table, so the sync never produces an equality
delete. Use it when a downstream engine cannot read equality deletes, or when it reads the raw change events and
merges them itself.

To turn it on, set `tigerlake.iceberg_changelog_mode` to `true` in the same statement that starts the sync:

```sql
ALTER TABLE my_hypertable SET (
  tigerlake.iceberg_sync = true,
  tigerlake.iceberg_changelog_mode = true
);
```

The following table compares the two modes:

|  | Default | Changelog mode |
| --- | --- | --- |
| Table shape | One row per primary key | One row per change |
| Updates and deletes | Applied with equality deletes | Appended as new rows, nothing is removed |
| Extra columns | None | `_tsdb_op` and `_tsdb_commit_lsn` |
| Iceberg identifier fields and sort order | The primary key columns | None |

Changelog mode adds two columns to the Iceberg table:

- `_tsdb_op`: a required `string` that holds `INSERT`, `UPDATE`, or `DELETE`. Rows written by the initial snapshot
  hold `INSERT`.
- `_tsdb_commit_lsn`: an optional `long` that holds the commit log sequence number (LSN) of the {C.PG} transaction that produced the
  change. Rows written by the initial snapshot have no originating transaction, so this column is empty for them.

Note the following:

- You can only set `tigerlake.iceberg_changelog_mode` when you start the sync. Setting it on a table that is already
  syncing returns an error. To change it, stop the sync and start a new one.
- Several changes to the same primary key inside one {C.PG} transaction collapse into a single row that holds the
  net effect of that transaction.
- The source table must not have a column named `_tsdb_op` or `_tsdb_commit_lsn`, because the names collide with
  the preceding columns. Starting the sync returns an error. Rename the column first, or start the sync without
  changelog mode.
- The Iceberg table has no identifier fields and no sort order, because many rows share the same primary key.

### Schema changes

While a table syncs, you can add a column, drop a column, and rename a column. Each change propagates to the Iceberg
table. The following statements return an error while the sync is active:

- `ADD COLUMN` with a `NOT NULL` constraint or a `DEFAULT` value.
- `ALTER COLUMN ... TYPE`.

### Supported data types

{C.LAKE} syncs columns of the following {C.PG} types:

| Category | Types |
| --- | --- |
| Numeric | `smallint`, `integer`, `bigint`, `real`, `double precision`, `numeric`, `oid` |
| Date and time | `date`, `time`, `timestamp`, `timestamptz`, `interval` |
| Text and binary | `text`, `varchar`, `char`, `bytea` |
| Other | `boolean`, `json`, `jsonb`, `uuid` |

Note the following:

- A table with a column of any other type, such as an array, an enum, `timetz`, `inet`, or a PostGIS type, cannot
  start syncing. To sync the rest of the table, leave the column out with
  [`tigerlake.iceberg_columns`](#sync-a-subset-of-columns).
- A `numeric` column without a precision and scale, or with a precision and scale that do not fit an Iceberg
  `decimal`, syncs as an Iceberg `string` column.
- Adding a column of an unsupported type to a table that is syncing returns an error.

### Sync a subset of columns

To leave columns out of the Iceberg table, list the columns to sync in `tigerlake.iceberg_columns` when you start
the sync:

```sql
ALTER TABLE my_hypertable SET (
  tigerlake.iceberg_sync = true,
  tigerlake.iceberg_columns = 'ts, device_id, temperature'
);
```

Include the primary key columns in the list: without them, updates and deletes on the table fail with
`cannot update table`. {C.LAKE} only checks the data types of the columns you list.

### Compressed data

Data in the [columnstore](/learn/hypertables/optimize-data-in-hypertables) syncs like any other data. Inserts,
updates, and deletes on compressed chunks propagate to Iceberg. Compressing or decompressing a chunk does not
change the data, so it does not produce changes in Iceberg.

### Data retention

Dropping chunks, with a [retention policy](/build/data-management/about-automation) or `drop_chunks`, does not
delete the rows from Iceberg. This lets you keep recent data in your {C.SERVICE_SHORT} and the full history in your
data lake. Rows you delete with `DELETE` are removed from Iceberg as usual, or recorded as a `DELETE` in
[changelog mode](#changelog-mode).

### Continuous aggregates

You can sync a continuous aggregate to Iceberg. Start the sync with `ALTER MATERIALIZED VIEW`:

```sql
ALTER MATERIALIZED VIEW my_cagg SET (tigerlake.iceberg_sync = true);
```

A continuous aggregate does not need a primary key. The Iceberg table uses its grouping columns, including the
time bucket, as the key. Rows that each refresh writes sync to Iceberg like changes to any other table.

### Sample code

The following samples show you how to tune data sync from a {C.HYPERTABLE} or a {C.PG} relational table to your
data lake:

- **Sync a {C.HYPERTABLE} with the default one-day partitioning interval on the `ts_column` column**

  To start syncing data from a {C.HYPERTABLE} to your data lake using the default one-day chunk interval as the
  partitioning scheme to the Iceberg table, run the following statement:

  ```sql
  ALTER TABLE my_hypertable SET (tigerlake.iceberg_sync = true);
  ```

  This is equivalent to `day(ts_column)`.

- **Specify a custom partitioning scheme for a {C.HYPERTABLE}**

  You use the `tigerlake.iceberg_partitionby` property to specify a different partitioning scheme for the Iceberg
  table at sync start.  For example, to enforce an hourly partition scheme from the chunks on `ts_column` on a
  {C.HYPERTABLE}, run the following statement:

  ```sql
  ALTER TABLE my_hypertable SET (
    tigerlake.iceberg_sync = true,
    tigerlake.iceberg_partitionby = 'hour(ts_column)'
  );
  ```

- **Set the partition to sync relational tables**

  {C.PG} relational tables do not forward a partitioning scheme to Iceberg, you must specify the partitioning scheme using
  `tigerlake.iceberg_partitionby` when you start the sync. For example, for a standard {C.PG} table to sync to the Iceberg
  table with daily partitioning , run the following statement:

  ```sql
  ALTER TABLE my_postgres_table SET (
    tigerlake.iceberg_sync = true,
    tigerlake.iceberg_partitionby = 'day(timestamp_col)'
  );
  ```

- **Stop sync to an Iceberg table for a {C.HYPERTABLE} or a {C.PG} relational table**

  ```sql
  ALTER TABLE my_hypertable SET (tigerlake.iceberg_sync = false);
  ```

  To change the partitioning scheme, the namespace, or the table name of an Iceberg table, stop the sync and start a
  new one with the new options.

**Specify a different namespace**

By default, tables are created in the `timescaledb` namespace. To specify a different namespace when you start the sync, use the  `tigerlake.iceberg_namespace` property. For example:

```sql
ALTER TABLE my_hypertable SET (
  tigerlake.iceberg_sync = true,
  tigerlake.iceberg_namespace = 'my_namespace'
);
```

**Specify a different Iceberg table name**

By default, the Iceberg table is named `tigerlake_<database>_<schema>_<table>`, in lowercase. For example, the
`Mixed_CASE_TableNAME` table in the `public` schema of the `tsdb` database syncs to
`tigerlake_tsdb_public_mixed_case_tablename`. To define a different table name when you start the sync, use the
`tigerlake.iceberg_table` property. The name must consist of lowercase letters, digits, and underscores, and must
not start or end with an underscore. For example:

```sql
ALTER TABLE Mixed_CASE_TableNAME SET (
  tigerlake.iceberg_sync = true,
  tigerlake.iceberg_table = 'my_table_name'
);
```

## Monitor the sync

In [{C.CONSOLE}](https://console.cloud.tigerdata.com/dashboard/services), select your {C.SERVICE_SHORT}, then click
`Connectors` and open the connector. The connector page shows its status, throughput, replication lag, retained
WAL, record counts, and data read, and the sync status of each table, including initial copy progress and errors.

To check the sync from SQL, query the following views:

- `timescaledb_lake.iceberg_sync_tables`: the tables that are syncing, with their Iceberg namespace, table name,
  partition specification, and whether tiered data is included.
- `timescaledb_lake.iceberg_sync_tables_state`: the initial copy state of each table, with its start and end time,
  the number of attempts, and the last error.

```sql
SELECT schema_name, table_name, snapshot_state, last_error
FROM timescaledb_lake.iceberg_sync_tables_state;
```

## Manage the connector

From the connector page in {C.CONSOLE}, you can:

- Add tables to the sync. To stop syncing a table, run `ALTER TABLE <table_name> SET (tigerlake.iceberg_sync = false);`.
- Update the catalog authentication settings.
- Rename the connector.
- Delete the connector.

When you delete the connector, {C.CLOUD_LONG} resets `max_slot_wal_keep_size` on the {C.SERVICE_SHORT} to the
default. If you use a custom value, set it again after you delete the connector. The Iceberg tables stay in your
catalog.

## Limitations

- {C.PG} 17.6 or later is required.
- A {C.SERVICE_SHORT} has one connector, which writes to one catalog.
- [Amazon S3 Tables](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables-integrating-open-source.html) and compatible generic Iceberg REST catalogs are supported. Catalog behavior, authentication requirements, and support for vended credentials vary by provider. Check your catalog provider's documentation for its Iceberg REST and credential-vending support.
- Generic REST catalogs support OAuth 2.0 client-credentials and personal-access-token authentication. Direct configuration of credentials for the underlying object storage is not available; use catalog-vended credentials instead.
- Connecting to a REST catalog provides catalog-managed Iceberg tables. It does not provide native ingestion features specific to that catalog's platform (for example, Snowflake Snowpipe or Streams).
- Throughput figures in [Stream data from your service to your data lake](#stream-data-from-your-service-to-your-data-lake) were measured using Amazon S3 Tables. Generic REST catalog throughput can differ, depending on the catalog's own API latency and table-commit performance.
- To capture deletes in the columnstore, some columnstore optimizations are disabled for {C.HYPERTABLE}s, including [direct compress](/learn/hypertables/optimize-data-in-hypertables#speed-up-data-ingestion).
- The `TRUNCATE` statement is not supported, and does not truncate data in the corresponding Iceberg table.
- You can only set the partitioning scheme, the namespace, the table name, the format version, [tiered data](/integrate/connectors/destination/tigerlake#tiered-data), and [changelog mode](/integrate/connectors/destination/tigerlake#changelog-mode) when you start the sync. To change them later, stop the sync and start a new one.
- Only one {C.SERVICE_SHORT} can write to an S3 table bucket.
- Iceberg snapshots are pruned automatically if the amount exceeds 2500.
- A long continuous aggregate refresh transaction on a syncing {C.HYPERTABLE} can hold the replication slot too long. Batch long refreshes.
