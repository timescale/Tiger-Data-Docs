## Overview

TimescaleDB leverages {C.PG}'s reliable backup and restore functionality. This guide covers the different mechanisms you can use to back up and restore your self-hosted TimescaleDB database, including logical backups with pg_dump/pg_restore and physical backups with pg_basebackup.

## Prerequisites

- A running self-hosted TimescaleDB installation
- Superuser or appropriate backup permissions on the database
- Sufficient disk space for backup files
- Access to the command line on the database server

## Logical backups with pg_dump and pg_restore

Logical backups capture database contents as SQL commands and are portable across different {C.PG} versions.

### When to use logical backups

- Migrating data between {C.PG} versions
- Backing up individual databases
- Creating portable, human-readable backups
- Backing up compressed hypertables (no decompression required)

Step-by-step instructions for using pg_dump to create a database backup.

### Restoring from a logical backup

Step-by-step instructions for using pg_restore to restore a database from backup.

### Best practices for logical backups

- Back up and restore one database at a time
- Track {C.PG} and TimescaleDB versions for compatibility
- Do not use the `-j` flag with pg_restore (does not correctly restore TimescaleDB catalogs)
- Do not use table or schema-specific flags (breaks hypertable relationships)

## Physical backups with pg_basebackup

Physical backups copy the entire database cluster at the file system level and are faster for large databases.

### When to use physical backups

- Creating full instance backups
- Setting up new replicas
- Large databases where logical backup is too slow
