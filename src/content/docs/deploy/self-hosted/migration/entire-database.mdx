Migrate smaller databases by dumping and restoring the entire database at once.
This method works best on databases smaller than 100 GB. For larger
databases, consider [migrating your schema and data
separately](/deploy/self-hosted/migration/schema-then-data).

<Callout variant="warning">
Depending on your database size and network speed, migration can take a very
long time. You can continue reading from your source database during this time,
though performance could be slower. To avoid this problem, fork your database
and migrate your data from the fork. If you write to tables in your source
database during the migration, the new writes might not be transferred to
{C.TIMESCALE_DB}. To avoid this problem, use [Livesync replication](/migrate/livesync-replication).
</Callout>

<Prerequisites context="procedure">

*   The {C.PG} [`pg_dump`](https://www.postgresql.org/docs/current/app-pgdump.html) and [`pg_restore`](https://www.postgresql.org/docs/current/app-pgrestore.html)
    utilities installed.
*   A client for connecting to {C.PG} installed. These instructions use
    `psql`, but any client works.
*   A new empty database in your {C.SELF_LONG} instance, provisioned with enough space for all your data.
*   Any other {C.PG} extensions you use confirmed compatible with
    TimescaleDB.
*   The same major version of {C.PG} on both
    your target and source databases. For information about upgrading
    {C.PG} on your source database, see the
    [upgrade instructions](/deploy/self-hosted/upgrades/upgrade-pg).
*   The same major version of {C.TIMESCALE_DB} on both
    your target and source databases. For more information, see
    [upgrade {C.SELF_LONG}](/deploy/self-hosted/upgrades/major-upgrade).

</Prerequisites>

<Callout variant="note">
To speed up migration, compress older data into the {C.COLUMNSTORE} before you start. Compressed {C.CHUNK}s
are smaller, so they dump and restore faster. You don't need to decompress a {C.CHUNK} to modify it
afterward: {C.TIMESCALE_DB} supports `INSERT`, `UPDATE`, `DELETE`, and `UPSERT` directly on the {C.COLUMNSTORE}.
</Callout>

<NumberedList>
<NumberedItem title="Dump all the data from your source database">
Dump into a `dump.bak` file, using your source database connection details. If you are prompted for a password, use
your source database credentials:

```bash
pg_dump -U <SOURCE_DB_USERNAME> -W \
-h <SOURCE_DB_HOST> -p <SOURCE_DB_PORT> -Fc -v \
-f dump.bak <SOURCE_DB_NAME>
```
</NumberedItem>
<NumberedItem title={`Connect to your ${C.SELF_LONG} instance`}>
```bash
psql "postgres://<USERNAME>:<PASSWORD>@<HOST>:<PORT>/<DATABASE>?sslmode=require"
```
</NumberedItem>
<NumberedItem title={`Prepare your ${C.SELF_LONG} instance for data restoration`}>
Use [`timescaledb_pre_restore`](/reference/timescaledb/administration/timescaledb_pre_restore) to stop background workers:

```sql
SELECT timescaledb_pre_restore();
```
</NumberedItem>
<NumberedItem title="Restore the dumped data">
At the command prompt, restore the dumped data from the `dump.bak` file into
your {C.SELF_LONG} instance, using your connection details. To avoid permissions errors, include the `--no-owner` flag:

```bash
pg_restore -U tsdbadmin -W \
-h <CLOUD_HOST> -p <CLOUD_PORT> --no-owner \
-Fc -v -d tsdb dump.bak
```
</NumberedItem>
<NumberedItem title={`Return your ${C.SELF_LONG} instance to normal operations`}>
Use [`timescaledb_post_restore`](/reference/timescaledb/administration/timescaledb_post_restore):

```sql
SELECT timescaledb_post_restore();
```
</NumberedItem>
<NumberedItem title="Update your table statistics">
Run `ANALYZE` on your entire dataset:

```sql
ANALYZE;
```
</NumberedItem>
</NumberedList>
