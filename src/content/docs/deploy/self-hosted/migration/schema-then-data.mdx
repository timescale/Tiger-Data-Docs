Migrate larger databases by migrating your schema first, then migrating the
data. This method copies each table or chunk separately, which allows you to
restart midway if one copy operation fails.

<Callout variant="note">
For smaller databases, it may be more convenient to migrate your entire database
at once. For more information, see the section on
[choosing a migration method](/deploy/self-hosted/migration).
</Callout>

<Callout variant="warning">
This method does not retain continuous aggregates calculated using
already-deleted data. For example, if you delete raw data after a month but
retain downsampled data in a continuous aggregate for a year, the continuous
aggregate loses any data older than a month upon migration. If you must keep
continuous aggregates calculated using deleted data, migrate your entire
database at once. For more information, see the section on
[choosing a migration method](/deploy/self-hosted/migration).
</Callout>

The procedure to migrate your database requires these steps:

*   [Migrate schema pre-data](#migrate-schema-pre-data)
*   [Restore hypertables in {C.TIMESCALE_DB}](#restore-hypertables-in-your-self-hosted-timescaledb-instance)
*   [Copy data from the source database](#copy-data-from-the-source-database)
*   [Restore data into {C.TIMESCALE_DB}](#restore-data-into-timescaledb)
*   [Migrate schema post-data](#migrate-schema-post-data)
*   [Recreate continuous aggregates](#recreate-continuous-aggregates) (optional)
*   [Recreate policies](#recreate-policies) (optional)
*   [Update table statistics](#update-table-statistics)

<Callout variant="warning">
Depending on your database size and network speed, steps that involve copying
data can take a very long time. You can continue reading from your source
database during this time, though performance could be slower. To avoid this
problem, fork your database and migrate your data from the fork. If you write to
the tables in your source database during the migration, the new writes might
not be transferred to {C.TIMESCALE_DB}. To avoid this problem, see the section on
[migrating an active database](/deploy/self-hosted/migration#migrate-an-active-database).
</Callout>

## Prerequisites

Before you begin, check that you have:

*   Installed the {C.PG} [`pg_dump`](https://www.postgresql.org/docs/current/app-pgdump.html) and [`pg_restore`](https://www.postgresql.org/docs/current/app-pgrestore.html)
    utilities.
*   Installed a client for connecting to {C.PG}. These instructions use
    `psql`, but any client works.
*   Created a new empty database in a {C.SELF_LONG} instance.
    Provision your database with enough space for all your data.
*   Checked that any other {C.PG} extensions you use are compatible with
    {C.TIMESCALE_DB}.
*   Checked that you're running the same major version of {C.PG} on both your
    {C.SELF_LONG} instance and your source database. For information about upgrading
    {C.PG} on your source database, see the [upgrade instructions for
    {C.SELF_LONG}](/deploy/self-hosted/upgrades/upgrade-pg) and
    [{C.MST_LONG}](/deploy/mst/maintenance).
*   Checked that you're running the same major version of {C.TIMESCALE_DB} on both
    your target and source database. For more information, see
    [upgrading {C.TIMESCALE_DB}](/deploy/self-hosted/upgrades/major-upgrade).

## Migrate schema pre-data

Migrate your pre-data from your source database to {C.SELF_LONG}. This
includes table and schema definitions, as well as information on sequences,
owners, and settings. This doesn't include {C.TIMESCALE_DB}-specific schemas.

<NumberedList>
<NumberedItem title="Dump the schema pre-data from your source database into a `dump_pre_data.bak` file">
Exclude {C.TIMESCALE_DB}-specific schemas.
If you are prompted for a password, use your source database credentials:

```bash
pg_dump -U <SOURCE_DB_USERNAME> -W \
-h <SOURCE_DB_HOST> -p <SOURCE_DB_PORT> -Fc -v \
--section=pre-data --exclude-schema="_timescaledb*" \
-f dump_pre_data.bak <DATABASE_NAME>
```
</NumberedItem>
<NumberedItem title={`Restore the dumped data from the dump_pre_data.bak file into your ${C.SELF_LONG} instance`}>
To avoid permissions errors, include the `--no-owner` flag:

```bash
pg_restore -U tsdbadmin -W \
-h <HOST> -p <PORT> --no-owner -Fc \
-v -d tsdb dump_pre_data.bak
```
</NumberedItem>
</NumberedList>

## Restore hypertables in your {C.SELF_LONG} instance

After pre-data migration, your hypertables from your source database become
regular {C.PG} tables in {C.TIMESCALE_DB}. Recreate your hypertables in your {C.SELF_LONG} instance to
restore them.

<NumberedList>
<NumberedItem title={`Connect to your ${C.SELF_LONG} instance`}>
```sql
psql "postgres://<USERNAME>:<PASSWORD>@<HOST>:<PORT>/<DATABASE>?sslmode=require"
```
</NumberedItem>
<NumberedItem title="Restore the hypertable">
```sql
SELECT create_hypertable(
   '<TABLE_NAME>',
   by_range('<COLUMN_NAME>', INTERVAL '<CHUNK_INTERVAL>')
);
```
</NumberedItem>
</NumberedList>

<Callout variant="note">
The `by_range` dimension builder is an addition to {C.TIMESCALE_DB} 2.13.
</Callout>

## Copy data from the source database

After restoring your hypertables, return to your source database to copy your
data, table by table.

<NumberedList>
<NumberedItem title="Connect to your source database">
```bash
psql "postgres://<SOURCE_DB_USERNAME>:<SOURCE_DB_PASSWORD>@<SOURCE_DB_HOST>:<SOURCE_DB_PORT>/<SOURCE_DB_NAME>?sslmode=require"
```
</NumberedItem>
<NumberedItem title="Dump the data from the first table into a .csv file">
```sql
\COPY (SELECT * FROM <TABLE_NAME>) TO <TABLE_NAME>.csv CSV
```

Repeat for each table and hypertable you want to migrate.
</NumberedItem>
</NumberedList>

<Callout variant="note">
If your tables are very large, you can migrate each table in multiple pieces.
Split each table by time range, and copy each range individually. For example:

```sql
\COPY (SELECT * FROM <TABLE_NAME> WHERE time > '2021-11-01' AND time < '2011-11-02') TO <TABLE_NAME_DATE_RANGE>.csv CSV
```
</Callout>

## Restore data into {C.TIMESCALE_DB}

When you have copied your data into `.csv` files, you can restore it to
{C.SELF_LONG} by copying from the `.csv` files. There are two methods: using
regular {C.PG} [`COPY`](https://www.postgresql.org/docs/current/sql-copy.html), or using the {C.TIMESCALE_DB}
[`timescaledb-parallel-copy`](https://github.com/timescale/timescaledb-parallel-copy) function. In tests,
`timescaledb-parallel-copy` is 16% faster. The `timescaledb-parallel-copy` tool
is not included by default. You must install the function.

<Callout variant="warning">
Because `COPY` decompresses data, any compressed data in your source
database is now stored uncompressed in your `.csv` files. If you
provisioned your {C.SELF_LONG} storage for your compressed data, the
uncompressed data may take too much storage. To avoid this problem, periodically
recompress your data as you copy it in.
</Callout>

### Restoring data with timescaledb-parallel-copy

<NumberedList>
<NumberedItem title="Install timescaledb-parallel-copy">
```bash
go get github.com/timescale/timescaledb-parallel-copy/cmd/timescaledb-parallel-copy
```
</NumberedItem>
<NumberedItem title={`Import data into your ${C.SELF_LONG} instance`}>
Set `<NUM_WORKERS>` to twice the number of CPUs in your
database. For example, if you have 4 CPUs, `<NUM_WORKERS>` should be `8`.

```bash
timescaledb-parallel-copy \
--connection "host=<HOST> \
user=tsdbadmin password=<PASSWORD> \
port=<PORT> \
dbname=tsdb \
sslmode=require
" \
--table <TABLE_NAME> \
--file <FILE_NAME>.csv \
--workers <NUM_WORKERS> \
--reporting-period 30s
```

Repeat for each table and hypertable you want to migrate.
</NumberedItem>
</NumberedList>

### Restoring data into {C.SELF_LONG} with COPY

<NumberedList>
<NumberedItem title={`Connect to your ${C.SELF_LONG} instance`}>
```sql
psql "postgres://tsdbadmin:<PASSWORD>@<HOST>:<PORT>/tsdb?sslmode=require"
```
</NumberedItem>
<NumberedItem title={`Restore the data to your ${C.SELF_LONG} instance`}>
```sql
\copy <TABLE_NAME> FROM '<TABLE_NAME>.csv' WITH (FORMAT CSV);
```

Repeat for each table and hypertable you want to migrate.
</NumberedItem>
</NumberedList>

## Migrate schema post-data

When you have migrated your table and hypertable data, migrate your {C.PG} schema post-data. This includes information about constraints.

<NumberedList>
<NumberedItem title="Dump the schema post-data from your source database into a `dump_post_data.dump` file">
Exclude Timescale-specific schemas. If you are prompted for a password, use your
source database credentials:

```bash
pg_dump -U <SOURCE_DB_USERNAME> -W \
-h <SOURCE_DB_HOST> -p <SOURCE_DB_PORT> -Fc -v \
--section=post-data --exclude-schema="_timescaledb*" \
-f dump_post_data.dump <DATABASE_NAME>
```
</NumberedItem>
<NumberedItem title={`Restore the dumped schema post-data from the dump_post_data.dump file into your ${C.SELF_LONG} instance`}>
Using your connection details. To avoid permissions errors, include the `--no-owner` flag:

```bash
pg_restore -U tsdbadmin -W \
-h <HOST> -p <PORT> --no-owner -Fc \
-v -d tsdb dump_post_data.dump
```
</NumberedItem>
</NumberedList>

### Troubleshooting

If you see these errors during the migration process, you can safely ignore
them. The migration still occurs successfully.

```
pg_restore: error: could not execute query: ERROR:  relation "<relation_name>" already exists
```

```
pg_restore: error: could not execute query: ERROR:  trigger "ts_insert_blocker" for relation "<relation_name>" already exists
```

## Recreate continuous aggregates

Continuous aggregates aren't migrated by default when you transfer your schema
and data separately. You can restore them by recreating the continuous aggregate
definitions and recomputing the results on your {C.SELF_LONG} instance. The recomputed
continuous aggregates only aggregate existing data in your {C.SELF_LONG} instance. They
don't include deleted raw data.

<NumberedList>
<NumberedItem title="Connect to your source database">
```bash
psql "postgres://<SOURCE_DB_USERNAME>:<SOURCE_DB_PASSWORD>@<SOURCE_DB_HOST>:<SOURCE_DB_PORT>/<SOURCE_DB_NAME>?sslmode=require"
```
</NumberedItem>
<NumberedItem title="Get a list of your existing continuous aggregate definitions">
```sql
SELECT view_name, view_definition FROM timescaledb_information.continuous_aggregates;
```

This query returns the names and definitions for all your continuous
aggregates. For example:

```sql
view_name       |                                            view_definition
----------------+--------------------------------------------------------------------------------------------------------
avg_fill_levels |  SELECT round(avg(fill_measurements.fill_level), 2) AS avg_fill_level,                                +
                |     time_bucket('01:00:00'::interval, fill_measurements."time") AS bucket,                            +
                |     fill_measurements.sensor_id                                                                       +
                |     FROM fill_measurements                                                                            +
                |     GROUP BY (time_bucket('01:00:00'::interval, fill_measurements."time")), fill_measurements.sensor_id;
(1 row)
```
</NumberedItem>
<NumberedItem title={`Connect to your ${C.SELF_LONG} instance`}>
```bash
psql "postgres://tsdbadmin:<PASSWORD>@<HOST>:<PORT>/tsdb?sslmode=require"
```
</NumberedItem>
<NumberedItem title="Recreate each continuous aggregate definition">
```sql
CREATE MATERIALIZED VIEW <VIEW_NAME>
WITH (timescaledb.continuous) AS
<VIEW_DEFINITION>
```
</NumberedItem>
</NumberedList>

## Recreate policies

By default, policies aren't migrated when you transfer your schema and data
separately. Recreate them on your {C.SELF_LONG} instance.

<NumberedList>
<NumberedItem title="Connect to your source database">
```bash
psql "postgres://<SOURCE_DB_USERNAME>:<SOURCE_DB_PASSWORD>@<SOURCE_DB_HOST>:<SOURCE_DB_PORT>/<SOURCE_DB_NAME>?sslmode=require"
```
</NumberedItem>
<NumberedItem title="Get a list of your existing policies">
This query returns a list of all your policies, including continuous aggregate refresh policies, retention
policies, compression policies, and reorder policies:

```sql
SELECT application_name, schedule_interval, retry_period,
    config, hypertable_name
    FROM timescaledb_information.jobs WHERE owner = '<SOURCE_DB_USERNAME>';
```
</NumberedItem>
<NumberedItem title={`Connect to your ${C.SELF_LONG} instance`}>
```sql
psql "postgres://tsdbadmin:<PASSWORD>@<HOST>:<PORT>/tsdb?sslmode=require"
```
</NumberedItem>
<NumberedItem title="Recreate each policy">
For more information about recreating policies, see
the sections on [continuous-aggregate refresh policies](/build/continuous-aggregates/refresh-policies),
[retention policies](/learn/data-management/data-retention/about-data-retention), and
[reorder policies](/reference/timescaledb/hypertables/add_reorder_policy).
</NumberedItem>
</NumberedList>

## Update table statistics

Update your table statistics by running [`ANALYZE`](https://www.postgresql.org/docs/current/sql-analyze.html) on your entire
dataset. This might take some time depending on the size of your database:

```sql
ANALYZE;
```

### Troubleshooting

If you see errors of the following form when you run `ANALYZE`, you can safely
ignore them:

```
WARNING:  skipping "<TABLE OR INDEX>" --- only superuser can analyze it
```

The skipped tables and indexes correspond to system catalogs that can't be
accessed. Skipping them does not affect statistics on your data.
