## Overview

Connection pooling reduces the overhead of establishing database connections by maintaining a pool of reusable connections. Each {C.PG} connection consumes approximately 10MB of memory, so pooling is essential for applications with many concurrent users or microservices architectures.

## Prerequisites

- An active MST instance
- Understanding of your application's connection patterns
- Knowledge of your expected concurrent connection count

## Why use connection pooling

Database connections are expensive resources that benefit from pooling.

### Connection overhead

Without pooling, each client request may:

- Open a new TCP connection
- Perform TLS handshake
- Authenticate with the database
- Allocate server-side memory (~10MB per connection)
- Release all resources when done

### Pooling benefits

- **Reduced latency** - Reuse existing connections instead of creating new ones
- **Lower memory usage** - Fewer total connections to the database
- **Higher throughput** - Handle more concurrent requests with fewer resources
- **Spike protection** - Queue requests when demand exceeds connection capacity

## Built-in connection pooling

MST provides integrated PgBouncer connection pooling.

### Enabling the connection pool

How to enable and configure the built-in connection pooler through the Tiger Cloud console or API.

### Pool connection string

Connect to the pooler using a dedicated connection string:

```
postgres://user:password@pool.your-instance.tsdb.cloud.tigerdata.com:6432/dbname
```

Note the port difference: pooled connections typically use port 6432 versus 5432 for direct connections.

## Pooling modes

Choose a pooling mode based on your application's requirements.

### Transaction pooling (recommended)

Connections are assigned per transaction and returned to the pool after each transaction completes.

- Best efficiency for most web applications
- Requires transaction-scoped session state
- Use `SET LOCAL` instead of `SET SESSION`

### Session pooling

Connections are assigned for the entire client session.

- Compatible with session-level features (temporary tables, prepared statements)
- Lower efficiency than transaction pooling
- Use when transaction pooling limitations are problematic

### Statement pooling

Connections are rotated after every statement.

- Maximum efficiency but most restrictive
- Multi-statement transactions not supported
- Rarely used in practice

## Configuration parameters

Key settings for tuning connection pool behavior.

### Pool sizing

```ini
# Maximum client connections to the pooler
max_client_conn = 100

# Connections per pool (per user/database combination)
default_pool_size = 20

# Minimum connections to keep open
min_pool_size = 5
```

### Sizing guidelines

- `default_pool_size` should be roughly `max_concurrent_ops / number_of_pools`
- For CPU-bound workloads, keep total connections at 1.5-2x vCPU count
- Start conservative and increase based on monitoring

### Connection lifecycle

```ini
# Maximum connection lifetime in seconds
server_lifetime = 3600

# Close unused connections after this many seconds
server_idle_timeout = 600

# Query to reset connection state
server_reset_query = DISCARD ALL
```

## Transaction pooling limitations

Understand what features work differently with transaction pooling.

### Session state

Session-level settings reset between transactions:

- Use `SET LOCAL` instead of `SET` or `SET SESSION`
- Settings only persist for the current transaction

### Temporary tables

Temporary tables must be created and dropped within the same transaction:

```sql
-- Use ON COMMIT DROP for automatic cleanup
CREATE TEMPORARY TABLE temp_results (...) ON COMMIT DROP;
```

### Prepared statements

Named prepared statements may not work as expected:

- Use your driver's statement caching instead
- Or switch to session pooling if required

### LISTEN/NOTIFY

Asynchronous notifications require persistent connections:

- Use session pooling for LISTEN operations
- Or connect directly without the pooler

## Application-side pooling

When to use client-side connection pooling alongside server-side pooling.

### Connection pool libraries

Most language drivers include connection pooling:

- Python: `psycopg2.pool`, `asyncpg`
- Node.js: `pg-pool`, `node-postgres`
- Java: HikariCP, c3p0
- Go: `pgx` built-in pool

### Coordinating pools

When using both application and server-side pools:

- Size application pools smaller than server pool
- Monitor total connections across all application instances
- Consider server-side pooling as the single source of truth

## Monitoring connection pools

Track pool health and utilization.

### Key metrics

- Active connections vs. pool size
- Client wait time (queue time)
- Connection reuse rate
- Connections per pool

### Alerts

Set up alerts for:

- Pool exhaustion (clients waiting for connections)
- High average wait time
- Connection errors or timeouts

## Troubleshooting

Common connection pooling issues.

- "Too many connections" errors
- Slow connection acquisition
- Transaction pooling incompatibilities
- Connection leaks in application code
