## Overview

Managed Service for TimescaleDB (MST) provides a tiered storage architecture that balances performance and cost. Use high-performance storage for active data requiring fast access, and low-cost object storage for historical data that is rarely queried.

## Prerequisites

- An active MST instance
- Understanding of your data access patterns (hot vs. cold data)
- Familiarity with TimescaleDB hypertables and chunks

## Storage tiers

MST offers two storage tiers optimized for different use cases.

### High-performance storage

The default tier for all data, optimized for fast reads and writes.

- SSD-backed block storage
- Low-latency access for active queries
- Supports the hypercore row-columnar storage engine
- Best for recent data with frequent access

### Object storage tier

Low-cost storage for historical data based on Amazon S3.

- Stores data in Apache Parquet format
- Significant cost savings compared to high-performance storage
- Optimized for analytical queries over large time ranges
- Best for rarely accessed historical data

## Data tiering

Automatically move data between storage tiers based on age.

### How tiering works

TimescaleDB chunks (time-based partitions) can be moved from high-performance storage to object storage as they age. Chunks from a single hypertable can span both tiers.

### Creating tiering policies

Set up automated policies to tier data based on age.

```sql
-- Example: Tier data older than 30 days to object storage
SELECT add_tiering_policy('measurements', INTERVAL '30 days');
```

### Query optimization for tiered data

MST automatically optimizes queries that span both storage tiers:

- **Chunk skipping** - Excludes chunks outside the query time window
- **Row group skipping** - Identifies relevant row groups within Parquet files
- **Column skipping** - Fetches only columns needed by the query

## Compression

Reduce storage consumption with TimescaleDB's native compression.

### About compression

TimescaleDB converts row-based data into columnar format, achieving up to 90%+ compression ratios without significant performance impact.

### Enabling compression

Configure compression on hypertables with appropriate segmentby and orderby columns.

```sql
-- Enable compression on a hypertable
ALTER TABLE measurements SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'device_id',
  timescaledb.compress_orderby = 'time DESC'
);
```

### Compression policies

Automate compression based on chunk age.

```sql
-- Compress chunks older than 7 days
SELECT add_compression_policy('measurements', INTERVAL '7 days');
```
