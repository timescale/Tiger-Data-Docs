This tutorial shows you how to move a self-hosted TimescaleDB database into a Tiger Cloud service with `pg_dump` and `psql`, and verify its policies and continuous aggregates on the target before the application switches. Most of the work happens before the dump and after the restore, because extension versions, settings, roles, and background jobs move partially or stay behind. The source runs in a Docker container on your machine, loaded with a sample dataset, and a reader with a real instance points the inventory step at it. By the end, you'll have an inventory script, a decision record, and a list of what Tiger Cloud now runs for you, all reusable for the next migration.

If you want an overview of the migration methods first, see [Choose a migration approach](https://www.tigerdata.com/docs/migrate/choose-your-approach).

## What you learn

- How to inventory a self-hosted instance for everything that does not migrate on its own.
- How to choose between dump and restore and Livesync replication, and when to open a Support request first.
- How to run the dump and the restore in the order TimescaleDB needs.
- How to verify policies, aggregates, and compression on the target by diffing inventories.
- Which self-hosted runbooks Tiger Cloud retires.

<NumberedItem title="Record the TimescaleDB version on your Tiger Cloud service">

Save the service's connection string in `TARGET` and read its TimescaleDB version by running these commands.

```bash
export TARGET="postgres://tsdbadmin:<password>@<host>:<port>/tsdb?sslmode=require"
```

The dump path needs the same TimescaleDB version on both sides, so the source you set up next starts one minor version behind this one and catches up in a later step. The test for this tutorial used a service on TimescaleDB 2.31.0, which the outputs below show.

<NumberedItem title="Start the source container">

Start a `timescale/timescaledb-ha` container on PostgreSQL 17 by running this command.

```bash
docker run -d --name tsdb-source -p 5433:5432 \
    -v tsdb-source-data:/home/postgres/pgdata/data \
    -e POSTGRES_PASSWORD=<password> \
    timescale/timescaledb-ha:pg17
```

The named volume keeps the data across a container restart, and port 5433 leaves 5432 free for a PostgreSQL already on your machine.

Save the source connection string in `SOURCE`, create the database, and install the TimescaleDB version one minor behind your service by running these commands. Replace `2.30.2` with the version one minor behind the one you recorded; `SELECT version FROM pg_available_extension_versions WHERE name = 'timescaledb';` lists what the image carries, every release back to 2.16.

```bash
export SOURCE="postgres://postgres:<password>@localhost:5433/tsdb_source"
psql "postgres://postgres:<password>@localhost:5433/postgres" \
    -c "CREATE DATABASE tsdb_source TEMPLATE template0;"
psql -X "$SOURCE" -c "CREATE EXTENSION timescaledb VERSION '2.30.2';"
```

The database comes from `template0` because `template1` in this image already carries the newest TimescaleDB version, and a database cloned from it can't take an older one.

<NumberedItem title="Create the hypertable and load the dataset">

Create the `sensor_data` hypertable by running this SQL in a `psql "$SOURCE"` session.

```sql
CREATE TABLE sensor_data (
    reading_id  bigint NOT NULL,
    time        timestamptz NOT NULL,
    device_id   text NOT NULL,
    tag         text NOT NULL,
    value       double precision,
    unit        text,
    description text
) WITH (
    tsdb.hypertable,
    tsdb.partition_column = 'time',
    tsdb.chunk_interval = '7 days',
    tsdb.columnstore = false
);

CREATE INDEX sensor_data_device_tag_time_idx
    ON sensor_data (device_id, tag, time DESC);
```

The chunks are weekly, and the columnstore stays off so that no background job converts chunks while the loading script runs.

Type `\q` to quit `psql`. Download `manufacturing.zip`, unzip it, and install `psycopg`, the PostgreSQL driver for Python, by running these commands.

```bash
unzip manufacturing.zip
pip install "psycopg[binary]"
```

The dataset holds hourly readings from ten sensors on each of five factory machines, over ten years, about 4.4 million records in total.

Save this script as `load_data.py`.

```python
"""
Load manufacturing.csv into the sensor_data hypertable.

The script numbers each reading in file order, which is time order,
and shifts every timestamp forward so the newest reading falls in
the current hour.
"""
import csv
import os
import sys
from datetime import datetime, timezone
from pathlib import Path

import psycopg

CSV_PATH = Path(__file__).resolve().parent / "manufacturing.csv"
COPY_SQL = """
    COPY sensor_data
        (reading_id, time, device_id, tag, value, unit, description)
    FROM STDIN
"""


def read_rows():
    with CSV_PATH.open(newline="", encoding="utf-8") as f:
        yield from csv.DictReader(f)


def main():
    url = os.environ.get("DATABASE_URL")
    if not url:
        sys.exit("Set DATABASE_URL to your service connection string.")
    if not CSV_PATH.exists():
        sys.exit(f"Can't find {CSV_PATH}. Unzip manufacturing.zip first.")

    print("Finding the newest reading in the file...")
    newest = max(datetime.fromisoformat(r["time"]) for r in read_rows())
    this_hour = datetime.now(timezone.utc).replace(
        minute=0, second=0, microsecond=0
    )
    shift = this_hour - newest
    print(f"Shifting timestamps forward by {shift.days} days.")

    with psycopg.connect(url) as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT count(*) FROM sensor_data")
            if cur.fetchone()[0] > 0:
                sys.exit("sensor_data already has rows. Nothing loaded.")

            with cur.copy(COPY_SQL) as copy:
                for reading_id, r in enumerate(read_rows(), start=1):
                    copy.write_row((
                        reading_id,
                        datetime.fromisoformat(r["time"]) + shift,
                        r["device_id"],
                        r["tag"],
                        r["value"],
                        r["unit"],
                        r["description"],
                    ))
                    if reading_id % 500_000 == 0:
                        print(f"Sent {reading_id:,} rows...")

    print(f"Loaded {reading_id:,} rows into sensor_data.")


if __name__ == "__main__":
    main()
```

Point `DATABASE_URL` at the source and run the script in the directory that holds `manufacturing.csv` by running these commands. It takes a minute or two.

```bash
export DATABASE_URL="$SOURCE"
python load_data.py
```

Verify the script loaded about 4.4 million rows. On the test machine, it took under a minute.

<NumberedItem title="Add the policy layer">

Reconnect with `psql "$SOURCE"`. Create a daily continuous aggregate with a refresh policy, a retention policy, and a columnstore policy by running this SQL.

```sql
ANALYZE sensor_data;

CREATE MATERIALIZED VIEW sensor_data_daily
WITH (timescaledb.continuous) AS
SELECT time_bucket('1 day', time) AS day,
       device_id,
       tag,
       avg(value) AS avg_value,
       min(value) AS min_value,
       max(value) AS max_value
FROM sensor_data
GROUP BY day, device_id, tag
WITH NO DATA;

SELECT add_continuous_aggregate_policy('sensor_data_daily',
    start_offset      => INTERVAL '30 days',
    end_offset        => INTERVAL '1 hour',
    schedule_interval => INTERVAL '1 hour',
    initial_start     => now() + INTERVAL '1 hour');

SELECT add_retention_policy('sensor_data',
    drop_after    => INTERVAL '5 years',
    initial_start => now() + INTERVAL '1 hour');

ALTER TABLE sensor_data SET (
    tsdb.enable_columnstore = true,
    tsdb.segmentby = 'device_id, tag',
    tsdb.orderby = 'time DESC'
);

CALL add_columnstore_policy('sensor_data',
    after         => INTERVAL '7 days',
    initial_start => now() + INTERVAL '1 hour');
```

Each policy gets an `initial_start` an hour away, because the scheduler otherwise starts a new policy within seconds and would race the job runs you make yourself below.

Create a `telemetry_app` role that owns a user-defined action by running this SQL.

```sql
CREATE ROLE telemetry_app LOGIN PASSWORD 'telemetry';
GRANT SELECT ON sensor_data TO telemetry_app;

CREATE TABLE sensor_data_counts (
    checked_at timestamptz NOT NULL,
    row_count  bigint NOT NULL
);
ALTER TABLE sensor_data_counts OWNER TO telemetry_app;

CREATE PROCEDURE record_row_count(job_id int, config jsonb)
LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO sensor_data_counts
    SELECT now(), count(*) FROM sensor_data;
END
$$;
ALTER PROCEDURE record_row_count(int, jsonb) OWNER TO telemetry_app;

SET ROLE telemetry_app;
SELECT add_job('record_row_count', INTERVAL '1 day',
    initial_start => now() + INTERVAL '1 hour');
RESET ROLE;
```

A job keeps its owner through the restore and runs as that role on the target, which the verification step has to handle, so the lab plants one.

Set one server parameter with `ALTER SYSTEM` by running this SQL.

```sql
ALTER SYSTEM SET work_mem = '32MB';
SELECT pg_reload_conf();
```

`ALTER SYSTEM` writes the setting to `postgresql.auto.conf`, where a dump never looks, so it is one the inventory has to catch.

Run every job once with [`run_job()`](https://www.tigerdata.com/docs/reference/timescaledb/jobs-automation/run_job) by running this SQL. The columnstore job takes a minute or two.

```sql
DO $$
DECLARE
    job int;
BEGIN
    FOR job IN
        SELECT job_id
        FROM timescaledb_information.jobs
        WHERE job_id >= 1000
        ORDER BY job_id
    LOOP
        CALL run_job(job);
    END LOOP;
END
$$;
```

The jobs run in id order, so the retention job runs before the columnstore job, and the chunks it drops never get compressed.

List the jobs, their owners, and the chunks by compression state with this SQL.

```sql
SELECT job_id, application_name, owner
FROM timescaledb_information.jobs
WHERE job_id >= 1000
ORDER BY job_id;

SELECT is_compressed, count(*) AS chunks
FROM timescaledb_information.chunks
WHERE hypertable_name = 'sensor_data'
GROUP BY is_compressed
ORDER BY is_compressed;
```

Verify that the jobs list shows four jobs with two owners, and that all but the newest one or two chunks are compressed.

```

--------+--------------------------------------------+---------------
```

Save this script as `inventory.sql`.

```sql
-- inventory.sql: list what a TimescaleDB database holds, before and
-- after a migration to Tiger Cloud.
--
-- psql "$SOURCE" -f inventory.sql -o source-inventory.txt

\pset footer off

\qecho == Hypertables
SELECT hypertable_name, num_chunks, compression_enabled
FROM timescaledb_information.hypertables
ORDER BY hypertable_name;

\qecho == Rows in each hypertable
SELECT string_agg(
         format('SELECT %L AS hypertable, count(*) AS rows FROM %I.%I',
                hypertable_name, hypertable_schema, hypertable_name),
         ' UNION ALL ' ORDER BY hypertable_name)
FROM timescaledb_information.hypertables
\gexec

\qecho == Chunks by compression state
SELECT hypertable_name, is_compressed, count(*) AS chunks
FROM timescaledb_information.chunks
GROUP BY hypertable_name, is_compressed
ORDER BY hypertable_name, is_compressed;

\qecho == Columnstore settings
SELECT hypertable, segmentby, orderby
FROM timescaledb_information.hypertable_columnstore_settings
ORDER BY hypertable;

\qecho == Continuous aggregates
SELECT view_name, materialized_only, materialization_hypertable_name
FROM timescaledb_information.continuous_aggregates
ORDER BY view_name;

\qecho == Newest bucket in each continuous aggregate
SELECT string_agg(
         format('SELECT %L AS continuous_aggregate, '
                'max(%I) AS newest_bucket FROM %I.%I',
                ca.view_name, d.column_name,
                ca.view_schema, ca.view_name),
         ' UNION ALL ' ORDER BY ca.view_name)
FROM timescaledb_information.continuous_aggregates AS ca
JOIN timescaledb_information.dimensions AS d
  ON d.hypertable_schema = ca.materialization_hypertable_schema
 AND d.hypertable_name = ca.materialization_hypertable_name
WHERE d.dimension_number = 1
\gexec

\qecho == Jobs
SELECT job_id, application_name, proc_name, owner,
       schedule_interval, scheduled, config
FROM timescaledb_information.jobs
WHERE job_id >= 1000
ORDER BY job_id;

\qecho == Extensions
SELECT extname, extversion, extnamespace::regnamespace AS schema
FROM pg_extension
ORDER BY extname;

\qecho == Server version
SHOW server_version;

\qecho == Roles
SELECT rolname, rolsuper, rolcreaterole, rolcreatedb,
       rolreplication, rolcanlogin
FROM pg_roles
WHERE rolname NOT LIKE 'pg\_%'
ORDER BY rolname;

\qecho == Non-default settings
SELECT name, setting, unit, source
FROM pg_settings
WHERE source NOT IN ('default', 'override', 'client', 'session')
ORDER BY name;
```

The script runs unchanged against the source and the target, so a `diff` of its two outputs is the final check.

## Reconcile versions and extensions

### Update the source's TimescaleDB to the target's version

Update the source to the version you recorded in [Set up the source](#set-up-the-source) by running this command with `psql -X`. Replace `2.31.0` with your target's version.

```bash
psql -X "$SOURCE" -c "ALTER EXTENSION timescaledb UPDATE TO '2.31.0';"
```

The dump carries TimescaleDB's internal catalog, which only the same version can read. `-X` skips your `.psqlrc` file, so nothing in it can run a query that loads the old version before the update.

Verify that `psql "$SOURCE" -c "\dx timescaledb"` shows the target's version.

```
                                                       List of installed extensions
    Name     | Version | Default version | Schema |                                      Description
-------------+---------+-----------------+--------+---------------------------------------------------------------------------------------
 timescaledb | 2.31.0  | 2.31.0          | public | Enables scalable inserts and complex queries for time-series data (Community Edition)
```

If the source already runs a newer TimescaleDB version than the target, the update has nothing to do and the dump can't load. For the lab, create the target first and read its version before you set the source's. For a real source that is ahead, wait for the Tiger Cloud release that carries its version, or open a Support request.

PostgreSQL major versions can differ between the two sides, because the dump is plain SQL. The `pg_dump` client has to be at least as new as the source server.

## Reconcile configuration and roles

### Sort the settings into three columns

Copy each line of the `Non-default settings` section into the `Settings` table of your decision record with one of three dispositions, as in this example.

```markdown
| Setting | Source value | Disposition |
|---|---|---|
| shared_buffers | 502400 8kB | managed by Tiger Cloud |
| work_mem | 32768 kB | set with ALTER DATABASE |
| listen_addresses | * | gone |
```

| Disposition | Settings | What happens on Tiger Cloud |
|---|---|---|
| Managed by Tiger Cloud | Ones that size the server to its hardware: `shared_buffers`, `effective_cache_size`, `max_connections`, `max_worker_processes` | Set for the compute you choose |
| Set with `ALTER DATABASE` | Ones a database owner can set: `work_mem`, `statement_timeout`, `log_min_duration_statement` | You apply them after the restore, in Tiger Console under `Operations` > `Database parameters` or with `ALTER DATABASE` |
| Gone | Ones that describe the machine: `listen_addresses`, `port`, `data_directory`, `shared_preload_libraries`, the `ssl_*` file paths | Nothing to apply |

Verify that every line of the section has a disposition.

### Dump the roles and strip the superuser clauses

Dump the roles with `pg_dumpall` and strip the superuser clauses with the `sed` script from the docs by running these commands.

```bash
pg_dumpall -d "$SOURCE" -l tsdb_source \
    --quote-all-identifiers \
    --roles-only \
    --file=roles.sql

sed -i -E \
    -e '/CREATE ROLE "postgres";/d' \
    -e '/ALTER ROLE "postgres"/d' \
    -e '/CREATE ROLE "tsdbadmin";/d' \
    -e '/ALTER ROLE "tsdbadmin"/d' \
    -e 's/(NO)*SUPERUSER//g' \
    -e 's/(NO)*REPLICATION//g' \
    -e 's/(NO)*BYPASSRLS//g' \
    -e 's/GRANTED BY "[^"]*"//g' \
    roles.sql
```

Tiger Cloud has no superuser, so a role dump must remove those clauses before it loads. The script also drops the `postgres` and `tsdbadmin` roles, which the target already has.

Verify that `roles.sql` creates `telemetry_app` with its password and no `SUPERUSER` or `REPLICATION` clause, by running `grep -A1 telemetry_app roles.sql`.

## Choose the method

Read the data size and the compression state by running this SQL in a `psql "$SOURCE"` session.

```sql
SELECT pg_size_pretty(pg_database_size(current_database())) AS database_size;

SELECT hypertable_name, is_compressed, count(*) AS chunks
FROM timescaledb_information.chunks
GROUP BY hypertable_name, is_compressed
ORDER BY hypertable_name, is_compressed;
```

Fill in the `Method` section of your decision record from four inputs: the data size, the longest write pause the application accepts, whether chunks are compressed, and whether continuous aggregates exist.

| Data size and write pause | Method | What it means for the data |
|---|---|---|
| Under 100 GB, and the application can pause writes | Dump and restore | Compressed chunks move as they are; the TimescaleDB version has to match on both sides; the docs estimate up to twelve hours of downtime near 100 GB |
| Over 100 GB, or writes can't stop | [Livesync replication](https://www.tigerdata.com/docs/migrate/livesync-replication) | Compressed chunks arrive in row form so that the target can run a newer TimescaleDB version |
| Over 400 GB, either method | The same, after a Support request | Support provisions the service's disk before the data arrives |
| Over 1 TB in one table | Livesync replication with a backfill tool | The backfill tool carries the history |

The lab database is 77 MB after compression, far under the line, so the record picks dump and restore.

```markdown
## Method

| Input | Value |
|---|---|
| Data size | 77 MB |
| Longest write pause the application accepts | 1 hour |
| Compressed chunks | 260 of 262 |
| Continuous aggregates | 1 |

Method: dump and restore
Expected duration: a few minutes
```

Verify that the record names the method, the four inputs, and the expected duration.

```sql
SELECT format('CALL run_job(%s);', job_id)
```

<NumberedItem title="Run the dump">

Dump the database in plain format under `time` by running this command.

```bash
time pg_dump -d "$SOURCE" \
    --format=plain \
    --quote-all-identifiers \
    --no-tablespaces \
    --no-owner \
    --no-privileges \
    --file=dump.sql
```

`--no-owner` and `--no-privileges` leave out the `postgres` ownership and the grants, which the target can't replay. `pg_dump` prints a warning about a circular foreign key on TimescaleDB's internal `continuous_agg` table, which needs no action. Record the `real` time and the size of `dump.sql` under `Expected duration` in your decision record. On the test machine, the dump took under a second and produced a 29 MB file from the 77 MB database, because the compressed chunks dump as they are stored.

Verify that `dump.sql` is a fraction of the database's size and contains the hypertable by running these commands.

```bash
ls -lh dump.sql
grep -c 'CREATE TABLE "public"."sensor_data"' dump.sql
```

## Livesync replication with a TimescaleDB source

[Livesync replication](https://www.tigerdata.com/docs/migrate/livesync-replication) carries the mechanics: the publication, the connector in Tiger Console or the Docker image, the table sync, and the cutover. A TimescaleDB source adds the rules below, which that page states in passing.

- **Version floors.** The source needs TimescaleDB 2.16.0 or later if any chunk is compressed or decompressed during the sync, because earlier versions replicate those rows twice. It needs 2.18.0 or later for Livesync to export the columnstore settings from `timescaledb_information.hypertable_columnstore_settings`.
- **The publication.** Name each table. `FOR ALL TABLES` includes the `_timescaledb_catalog` tables, and replicating them corrupts the target's catalog. Add a hypertable with tiered chunks with `ONLY`, since tiered chunks are foreign tables. Leave chunks unmerged and unsplit while the sync runs, and on a Tiger Cloud source pause the tiering jobs with `alter_job()` first.
- **Columnstore settings.** Set `segmentby` and `orderby` on the source before you start, so the export carries them. Compressed chunks arrive in row form, which is what frees the target from the same-version rule, and the columnstore policy is applied on the target after the sync.
- **Continuous aggregates.** Livesync replicates the materialization hypertable, `_timescaledb_internal._materialized_hypertable_<N>`. Set `REPLICA IDENTITY FULL` on it on the source, because a refresh issues deletes; add it to the publication, and map it to the target's own `_materialized_hypertable_<M>`, whose number can differ. Leave the refresh policy off the target until cutover.
- **At cutover.** Reset every sequence with the `copy-sequences` command or `setval()`, because Livesync leaves sequence values behind and the first insert after cutover would reuse a key, then apply the refresh, retention, and columnstore policies from the exported settings. A retention policy that dropped chunks on the source during the sync did not drop them on the target, so run it there once.

<NumberedItem title="Repoint the application">

Set the maintenance window for the long term during a low-traffic period, using the same path as before, because the first window may apply a minor upgrade you did not schedule.

Point the application at the target's connection string and start it, then watch both sides by running this SQL in a session on each.

```sql
SELECT usename, application_name, count(*)
FROM pg_stat_activity
WHERE datname = current_database()
  AND backend_type = 'client backend'
  AND pid <> pg_backend_pid()
```

The source should show no application connections, and the target should show them alongside Tiger Cloud's own `postgres_exporter` and `ForgeExplorer` sessions, which are always there.

Leave the container running as the rollback point, knowing that a rollback loses every write made on Tiger Cloud since cutover.

After the application has run a full cycle on Tiger Cloud, remove the container, its volume, and the dump files with these commands.

`roles.sql` holds password hashes and `dump.sql` holds every row, so neither belongs on disk longer than the migration.

## Troubleshooting

These problems can come up while you follow the tutorial. A load that stops leaves a partial database on the target, and a second load collides with it, so after you fix the cause, delete the service, create a new one, set `TARGET` to its connection string, and load again.

- **The load stops on a `_timescaledb_catalog` table with a column mismatch.** The dump's catalog came from a different TimescaleDB version than the target runs. Update the source to the target's version as in [Reconcile versions and extensions](#reconcile-versions-and-extensions) and dump again.
- **The load stops on `CREATE EXTENSION`.** An extension is missing on the target. If it is on the Tiger Cloud list, create it first. If it is missing from the list, the decision record names its replacement.
- **The load stops on a tablespace or a `SUPERUSER` clause.** The dump was made without `--no-tablespaces`, or `roles.sql` was not run through the `sed` script. Dump again with the flags shown.
- **`ALTER EXTENSION timescaledb UPDATE` is blocked.** The source holds a continuous aggregate in the old format. Migrate it with `cagg_migrate` and update again.
- **The chunk count differs between the inventories.** A retention job ran on one side after the inventory. Compare the `Rows in each hypertable` section. If it matches, run the inventory again on both sides. If the rows differ too, a write landed on the source after the dump started, and the rows since then are on the source only.
- **A job fails on the target with `permission denied`.** The job kept an owner other than `tsdbadmin`, and that role lost its grants in the restore. Grant the role what it needs, as in [Verify the policy layer](#verify-the-policy-layer), and set the job's `next_start` again. A user-defined action that needs the `tsdbadmin` lacks needs a rewrite before it runs on Tiger Cloud.

## Recap

You moved a self-hosted TimescaleDB database into a Tiger Cloud service by inventorying it, matching the TimescaleDB version, stripping what the target can't take, loading the dump between `timescaledb_pre_restore()` and `timescaledb_post_restore()`, and diffing the inventories.

| Artifact | What it holds | When to use it again |
|---|---|---|
| `inventory.sql` | Hypertables, rows, chunks, columnstore settings, continuous aggregates, jobs, extensions, roles, settings | Before and after any migration, upgrade, or restore, to diff |
| `jobs-source.csv` | Every job's settings | When a policy goes missing and has to be recreated |
| `migration-decision.md` | Extension decisions, setting dispositions, the method and its inputs, the runbook table | At the next migration, as the starting point |

These measurements were collected from a source container on PostgreSQL 17.11 with TimescaleDB 2.31.0, running under Docker Desktop on a laptop with an AMD Ryzen 9 5900HX, dumped with `pg_dump` 18.3, and loaded into a Tiger Cloud service with 8 CPUs and 32 GiB of memory on PostgreSQL 18.6 with TimescaleDB 2.31.0.

| Step | Rows | Chunks | Compressed chunks | Size | Duration |
|---|---|---|---|---|---|
| `pg_dump` | 2,193,750 | 262 | 260 | `dump.sql` 29 MB | 0.6 seconds |
