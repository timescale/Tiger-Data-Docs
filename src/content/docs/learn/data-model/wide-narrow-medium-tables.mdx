When you design a {C.PG} schema for time-series data, choosing between **wide** and **narrow** table layouts matters. Each pattern has different advantages for metrics, data types, and query shape. A **medium** layout sits between the two.

## Narrow table layout

A narrow table typically has few data value columns but may include multiple metadata or categorizing columns. This design works well when you have a small set of known metrics and data types. You can give each metric its own table and data type. Adding a new metric is usually as simple as creating a new table.

### Advantages

- Simplifies adding new metrics by creating new tables.
- Allows precise data type management for each metric.

### Disadvantages

- Many tables can become hard to operate.
- Querying several metrics at once may require complex joins or unions and more I/O.

## Wide table layout

A wide table has many columns, often one column per metric. Use it when metrics are known up front and change rarely. Related values live in one row, so you avoid joins across metric tables for common queries.

### Advantages

- Simpler query construction when all metrics live in one table.
- Efficient access to column subsets, especially with columnar compression.

### Disadvantages

- New metrics require schema changes (`ALTER TABLE`), which can be costly.
- Dropped columns do not immediately reclaim disk space.

## Medium table layout

A medium layout balances narrow and wide: one column per necessary **data type**, not necessarily one column per metric. It helps when you know the types you need but not every metric you will add.

### Advantages

- Easier to extend with new metrics without changing the table shape as often as a pure wide design.
- Can simplify multi-tenancy (for example, one hypertable per customer).

### Disadvantages

- You need a mapping from logical metrics to the right typed columns.
- Querying several metrics with different types can require more complex SQL.

## Tiger Cloud and compression

Tiger Cloud supports all of these layouts with compression. Narrow tables often compress very well because columns are uniform. Medium and wide tables still benefit from compression, and NULL-heavy columns typically compress efficiently. Pick wide, narrow, or medium based on metric count, types, how often the schema changes, and how you query.
