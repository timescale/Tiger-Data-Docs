{C.CLOUD_LONG} offers managed database services that provide a stable and reliable environment for your
applications.

Each {C.SERVICE_LONG} is a single optimised {C.PG} instance extended with innovations such as {C.TIMESCALE_DB} in the database
engine, in a cloud infrastructure that delivers speed without sacrifice. A radically faster {C.PG} for transactional,
analytical, and agentic workloads at scale.

{C.CLOUD_LONG} scales {C.PG} to ingest and query vast amounts of live data. {C.CLOUD_LONG}
provides a range of features and optimizations that supercharge your queries while keeping the
costs down. For example:

- The {C.HYPERCORE} row-columnar engine in {C.TIMESCALE_DB} makes queries up to 350x faster, ingests 44% faster, and reduces
  storage by 90%.
- Tiered storage in {C.CLOUD_LONG} seamlessly moves your data from high performance storage for frequently accessed data to
  low cost bottomless storage for rarely accessed data.

## Optimize time-series data in {C.HYPERTABLE}s with {C.HYPERCORE}

Time-series data represents the way a system, process, or behavior changes over time. {C.HYPERTABLE_CAP}s are {C.PG} tables
that help you improve insert and query performance by automatically partitioning your data by time. Each {C.HYPERTABLE}
is made up of child tables called {C.CHUNK}s. Each {C.CHUNK} is assigned a range of time, and only
contains data from that range. When you run a query, {C.TIMESCALE_DB} identifies the correct {C.CHUNK} and runs the query on
it, instead of going through the entire table. You can also tune {C.HYPERTABLE}s to increase performance even more.

<Image src={imgHypertableStructure} alt="Hypertable structure" />

<HypercoreIntroShort />

{C.HYPERTABLE_CAP}s exist alongside regular {C.PG} tables.
You use regular {C.PG} tables for relational data, and interact with {C.HYPERTABLE}s
and regular {C.PG} tables in the same way.

This section shows you how to create regular tables and {C.HYPERTABLE}s, and import

## Write fast and efficient analytical queries

Aggregation is a way of combing data to get insights from it. Average, sum, and count are all
examples of simple aggregates. However, with large amounts of data, aggregation slows things down, quickly.
{C.CAGG_CAP}s are a kind of {C.HYPERTABLE} that is refreshed automatically in
the background as new data is added, or old data is modified. Changes to your dataset are tracked,
and the {C.HYPERTABLE} behind the {C.CAGG} is automatically updated in the background.

<ThemeImage light={imgCaggsLight} dark={imgCaggsDark} alt="How a continuous aggregate incrementally materializes time-bucketed rollups from a raw hypertable, with a real-time aggregate query reading both pre-computed and recent raw data" />

You create {C.CAGG}s on uncompressed data in high-performance storage. They continue to work
on [data in the {C.COLUMNSTORE}](#write-fast-and-efficient-analytical-queries)
and [rarely accessed data in tiered storage](#slash-storage-charges). You can even
create [{C.CAGG}s on top of your {C.CAGG}s](/learn/continuous-aggregates/hierarchical-continuous-aggregates).

You use {C.TIME_BUCKET}s to create a {C.CAGG}. {C.TIME_BUCKET_CAP}s aggregate data in {C.HYPERTABLE}s by time
interval. For example, a 5-minute, 1-hour, or 3-day bucket. The data grouped in a {C.TIME_BUCKET} uses a single
timestamp. {C.CAGG_CAP}s minimize the number of records that you need to look up to perform your
query.

This section shows you how to run fast analytical queries using {C.TIME_BUCKET}s and {C.CAGG}s in
{C.CONSOLE}. You can also do this using psql.

<Tabs>

<TabItem label={C.DATA_MODE}>

<NumberedList>
  <NumberedItem title={`In ${C.CONSOLE}, toggle ${C.DATA_MODE} at the top right`}></NumberedItem>

<NumberedItem title={`Connect to your ${C.SERVICE_SHORT}`}>
  In the connection drop-down in the top right, select your {C.SERVICE_SHORT}.
</NumberedItem>

  <NumberedItem title={`Create a ${C.CAGG}`}>

    For a {C.CAGG}, data grouped using a {C.TIME_BUCKET} is stored in a
    {C.PG} `MATERIALIZED VIEW` in a {C.HYPERTABLE}. `timescaledb.continuous` ensures that this data
    is always up to date.
    In {C.DATA_MODE}, use the following code to create a {C.CAGG} on the real-time data in
    the `crypto_ticks` table:

    ```sql
    CREATE MATERIALIZED VIEW assets_candlestick_daily
    WITH (timescaledb.continuous) AS
    SELECT
      time_bucket('1 day', "time") AS day,
      symbol,
      max(price) AS high,
      first(price, time) AS open,
      last(price, time) AS close,
      min(price) AS low
    FROM crypto_ticks srt
    GROUP BY day, symbol;
    ```

    This {C.CAGG} creates the [candlestick chart](https://www.investopedia.com/terms/c/candlestick.asp) data you use to visualize
    the price change of an asset.

  </NumberedItem>

  <NumberedItem title="Create a policy to refresh the view every hour">

   ```sql
   start_offset => INTERVAL '3 weeks',
   end_offset => INTERVAL '24 hours',
   schedule_interval => INTERVAL '3 hours');
   ```
  </NumberedItem>

## Slash storage charges

In the previous sections, you used {C.CAGG}s to make fast analytical queries, and
{C.HYPERCORE} to reduce storage costs on frequently accessed data. To reduce storage costs even more,
you create tiering policies to move rarely accessed data to the object store. The object store is
low-cost bottomless data storage built on Amazon S3 or Azure Blob storage. However, no matter the tier, you can
[query your data when you need](/build/data-management/storage/query-tiered-data). {C.CLOUD_LONG} seamlessly accesses the correct storage
tier and generates the response.

<ThemeImage light={imgTieredStorageLight} dark={imgTieredStorageDark} alt="Tiered storage in Tiger Cloud: a hypertable's rowstore and columnstore chunks live on high-performance block storage, while older chunks tier to low-cost bottomless object storage and remain transparently queryable" />

To set up data tiering:

<NumberedList>

<NumberedItem title="Enable data tiering">

 1. In [{C.CONSOLE}](https://console.cloud.tigerdata.com/dashboard/services), select the {C.SERVICE_SHORT} to modify.

 1. In `Explorer`, click `Data tiering` > `Enable tiered storage`.

     <Image src={imgEnableTieredStorage} alt="Enable tiered storage" />

     When tiered storage is enabled, you see the amount of data in the tiered object storage.
</NumberedItem>
<NumberedItem title="Set the time interval when data is tiered">

 In {C.CONSOLE}, toggle {C.DATA_MODE}, then set up a tiering policy on a {C.HYPERTABLE} with the following query:
  ```sql
  SELECT add_tiering_policy('assets_candlestick_daily', INTERVAL '3 weeks');
  ```

</NumberedItem>

<NumberedItem title="Query tiered data">
 You enable reads from tiered data for each query, for a session or for all future
 sessions. To run a single query on tiered data:

 1. Enable reads on tiered data:
    ```sql
    set timescaledb.enable_tiered_reads = true
    ```
 1. Query the data:
    ```sql
    SELECT * FROM crypto_ticks srt LIMIT 10
    ```
 1. Disable reads on tiered data:
    ```sql
    set timescaledb.enable_tiered_reads = false;
    ```
 For more information, see [Querying tiered data](/build/data-management/storage/query-tiered-data).

</NumberedItem>
</NumberedList>

## Reduce the risk of downtime and data loss

By default, all {C.SERVICE_LONG}s have rapid recovery enabled. However, if your app has very low tolerance
for downtime, {C.CLOUD_LONG} offers {C.HA_REPLICA}s. {C.HA_REPLICA_SHORT}s are exact, up-to-date copies
of your database hosted in multiple AWS availability zones (AZ) within the same region as your primary node.
{C.HA_REPLICA_SHORT}s automatically take over operations if the original primary data node becomes unavailable.
The primary node streams its write-ahead log (WAL) to the replicas to minimize the chances of
data loss during failover.

<HASetup />

For more information, see [{C.HA_REPLICA_CAP}](/deploy/tiger-cloud/tiger-cloud-aws/high-availability/high-availability).
