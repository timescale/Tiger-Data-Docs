In {C.COMPANY} products, **{C.CHUNK}s** are the physical partitions behind a {C.HYPERTABLE}: each one holds rows for a time range (and optional space keys). You always query the {C.HYPERTABLE} name; the engine routes work to the right {C.CHUNK}s. {C.CHUNK_CAP}s are what make [{C.HYPERTABLE}s](/learn/hypertables/understand-hypertables) fast and manageable. You rarely interact with {C.CHUNK}s directly, but understanding them helps you design schemas, tune performance, and reason about how {C.CLOUD_LONG} (and {C.SELF_LONG}) organize your data.

For step-by-step tasks (e.g. choosing {C.CHUNK} intervals or listing {C.CHUNK}s), see the links in [How to use {C.CHUNK}s effectively](#how-to-use-chunks-effectively) and [Learn more](#learn-more).

---

## What are chunks?

A {C.CHUNK} is a horizontal partition of a [{C.HYPERTABLE}](/learn/hypertables/understand-hypertables): it is a table that holds rows for a specific time range (and optionally a specific space partition if you use multiple dimensions). When you insert data into a {C.HYPERTABLE}, {C.TIMESCALE_DB} does not store everything in one giant table. Instead, it splits the data into {C.CHUNK}s, smaller tables, each responsible for a slice of time (for example one day or one week). That split happens automatically and transparently: you always insert and query against the {C.HYPERTABLE} name; the system creates and uses {C.CHUNK}s behind the scenes.

In practice, a {C.HYPERTABLE} is the logical table you see; {C.CHUNK}s are the physical partitions that store the data. You can think of a {C.HYPERTABLE} as a single table in SQL, and {C.CHUNK}s as the internal "drawers" that the database opens only when they’re needed for a given query or write.

<Callout variant="note">
**Inheritance** is not supported for {C.HYPERTABLE}s (and therefore for {C.CHUNK}s). Using table inheritance with {C.HYPERTABLE}s can lead to unexpected behavior.
</Callout>

## Why chunks matter

{C.CHUNK_CAP}s are not just an implementation detail — they are why {C.HYPERTABLE}s can deliver efficient data management, better query performance, and scalable maintenance without you changing how you write SQL.

### Query performance and chunk skipping

Time-series queries usually filter by time (for example, "last 24 hours" or "September 2024"). Because each {C.CHUNK} covers a known time range, the query planner can skip {C.CHUNK}s that don’t contain any data for that range. So instead of scanning the entire table, {C.TIMESCALE_DB} only touches the {C.CHUNK}s that might contain matching rows. {C.CHUNK_SKIPPING_CAP} dramatically reduces work and speeds up queries. On {C.CLOUD_LONG}, you can also [enable {C.CHUNK_SKIPPING} on non-partitioning columns](/build/performance-optimization/improve-hypertable-performance#enable-chunk-skipping) (for example, a "received at" timestamp when the {C.HYPERTABLE} is partitioned by "event time"), so even more {C.CHUNK}s can be skipped when they’re irrelevant to the query.

### Maintenance and lifecycle

Many operations in a time-series database are easier when data is partitioned by time:

- **{C.COLUMNSTORE_CAP}**: Policies can convert older {C.CHUNK}s to [{C.COLUMNSTORE}](/build/columnar-storage/setup-hypercore) while keeping recent {C.CHUNK}s in {C.ROWSTORE} for fast inserts and updates. Conversion is applied per {C.CHUNK}.
- **Data retention**: You can drop old data by dropping entire {C.CHUNK}s (e.g. with [`drop_chunks()`](/reference/timescaledb/hypertables/drop_chunks)) instead of running row-by-row `DELETE`, which avoids bloat and is much faster.
- **Tiered storage**: On [{C.CLOUD_LONG}](/get-started/quickstart/create-service), you can move {C.CHUNK}s to different storage tiers based on age or access patterns.

So {C.CHUNK}s matter because they give the system clear boundaries: "this block of time is hot," "this block is cold," "this block can be converted to {C.COLUMNSTORE} or dropped." That makes automation and tuning predictable.

### Parallelism and indexing

{C.CHUNK_CAP}s are independent storage units. The database can process multiple {C.CHUNK}s in parallel when executing a query, and indexes are maintained per {C.CHUNK}. That keeps index sizes manageable and allows the planner to use {C.CHUNK}-level statistics. By default, when you create a {C.HYPERTABLE}, a time-descending index is created; additional indexes you add are also built at the {C.CHUNK} level, which helps both insert and query performance when you have many rows.

## How chunks relate to the chunk interval

The **{C.CHUNK} interval** is the time span each {C.CHUNK} is responsible for (e.g. one day or seven days). It is set when you create the {C.HYPERTABLE} (or later via [`set_chunk_time_interval()`](/reference/timescaledb/hypertables/set_chunk_time_interval)) and determines how many {C.CHUNK}s you get for a given time range: smaller intervals mean more, smaller {C.CHUNK}s; larger intervals mean fewer, larger {C.CHUNK}s.

- **Default**: Typically each {C.CHUNK} holds about 7 days of data, but you can change this to match how you ingest and query (e.g. one {C.CHUNK} per day for high-volume, time-bound queries).
- **Creation**: When you insert a row whose time falls in a range that doesn’t yet have a {C.CHUNK}, {C.TIMESCALE_DB} creates a new {C.CHUNK} for that range automatically. So the number of {C.CHUNK}s grows as new time ranges receive data.
- **{C.COLUMNSTORE_CAP}**: A [{C.COLUMNSTORE} policy](/build/columnar-storage/setup-hypercore) often converts {C.CHUNK}s to columnar format after a certain age (e.g. after one {C.CHUNK} interval). So the {C.CHUNK} interval also influences when data moves into the {C.COLUMNSTORE}. See the [{C.HYPERTABLE_CAP}s and {C.CHUNK}s](/reference/timescaledb/hypertables) overview for the exact behavior of your version.

Choosing the right {C.CHUNK} interval is a trade-off: you want {C.CHUNK}s small enough that active (recent) {C.CHUNK}s and their indexes fit in memory for fast access, but not so small that you end up with too many {C.CHUNK}s (which can slow query planning and reduce {C.COLUMNSTORE} effectiveness). The [Improve {C.HYPERTABLE} and query performance](/build/performance-optimization/improve-hypertable-performance) guide explains how to choose and tune the {C.CHUNK} interval in practice.

## How to use chunks effectively

You don’t need to create or manage {C.CHUNK}s manually for normal use — you create a [{C.HYPERTABLE}](/learn/hypertables/understand-hypertables) and insert/query it; {C.CHUNK}s are created and used automatically. "Using {C.CHUNK}s effectively" means designing and tuning so that chunking works in your favor.

<NumberedList>
<NumberedItem title="Choose an appropriate chunk interval">
Set the {C.CHUNK} interval when you [create the {C.HYPERTABLE}](/learn/hypertables/creating-and-configuring-hypertables) (or change it for new {C.CHUNK}s with `set_chunk_time_interval()`). A common guideline is to size the interval so that the indexes of {C.CHUNK}s you’re currently ingesting into fit within a reasonable share of main memory (e.g. 25% of RAM). For step-by-step guidance and examples, see [Optimize {C.HYPERTABLE} {C.CHUNK} intervals](/build/performance-optimization/improve-hypertable-performance#optimize-hypertable-chunk-intervals).
</NumberedItem>

<NumberedItem title="Use time-based filters in queries">
Queries that filter on the partitioning (time) column allow the planner to skip irrelevant {C.CHUNK}s. If you often filter by another column (e.g. "ingested at"), consider [enabling {C.CHUNK_SKIPPING}](/build/performance-optimization/improve-hypertable-performance#enable-chunk-skipping) on that column (where supported) so more {C.CHUNK}s can be skipped.
</NumberedItem>

<NumberedItem title="Inspect chunks when tuning or debugging">
You can list {C.CHUNK}s for a {C.HYPERTABLE} with [`show_chunks()`](/reference/timescaledb/hypertables/show_chunks) and inspect size with functions like [`chunks_detailed_size()`](/reference/timescaledb/hypertables/chunks_detailed_size). That’s useful when you’re deciding whether to change the {C.CHUNK} interval or investigating query plans.
</NumberedItem>

<NumberedItem title="Prefer chunk-level operations for bulk lifecycle actions">
For dropping old data, use retention policies or [`drop_chunks()`](/reference/timescaledb/hypertables/drop_chunks) instead of large `DELETE`s. For {C.COLUMNSTORE} conversion, policies operate per {C.CHUNK}, so your {C.CHUNK} interval and policy settings work together.
</NumberedItem>
</NumberedList>

If you’re just getting started, [Create and configure a {C.HYPERTABLE}](/learn/hypertables/creating-and-configuring-hypertables) is the right place to begin; the default {C.CHUNK} interval is a reasonable starting point, and you can refine it later using the guides above.
