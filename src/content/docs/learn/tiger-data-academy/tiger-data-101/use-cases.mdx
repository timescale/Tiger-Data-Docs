## IoT & Sensors

**The challenge:** Thousands of devices generating readings every few seconds — that's millions of rows per day, per deployment.

**Key characteristics of IoT data:**

- High ingest rate (many devices, sub-second intervals)
- Append-only (sensor readings are never updated retroactively)
- Queries are almost always time-bounded ("last 24 hours", "last week")
- Device metadata (location, type, firmware) lives in relational tables alongside raw readings

**How {C.TIMESCALE_DB}} helps:**

- {C.HYPERTABLE}}s absorb high-velocity writes efficiently and partition data by time automatically
- {C.HYPERCORE}} compression dramatically reduces storage cost for historical sensor data
- Continuous Aggregates power real-time dashboards (avg temp per device, per hour) without scanning raw rows
- Standard SQL makes it easy to JOIN sensor readings with device metadata tables

## Financial Data

**The challenge:** Markets generate enormous volumes of data with strict latency requirements — and every data point must be preserved for backtesting, audits, and compliance.

**Key characteristics of financial data:**

- Tick data: individual trade and quote events, potentially millions per second
- OHLC aggregations (Open, High, Low, Close) at multiple time granularities (1m, 5m, 1h, 1d)
- Long retention requirements (years of historical data for backtesting)
- High query performance needed for real-time risk analytics

**How {C.TIMESCALE_DB}} helps:**

- {C.HYPERTABLE}}s handle high-frequency tick ingestion without degrading over time
- Continuous Aggregates generate OHLC candles at multiple resolutions automatically
- {C.HYPERCORE}} keeps years of tick history queryable at a fraction of the storage cost
- Full SQL enables complex analytics: correlations, window functions, ranking, without a separate analytics layer

## Analytics & Reporting

**The challenge:** Business intelligence on time-series events (clickstreams, transactions, user activity) needs to be fast and always fresh, without expensive nightly batch jobs.

**Key characteristics of analytics workloads:**

- Aggregations over large time ranges (weekly, monthly, quarterly trends)
- Multiple granularities needed: hourly for ops, daily for stakeholders, monthly for executives
- Data arrives continuously; dashboards must reflect recent data in near-real-time
- Ad-hoc queries alongside pre-built reports

**How {C.TIMESCALE_DB}} helps:**

- Continuous Aggregates replace nightly ETL jobs with automatically refreshing rollups
- Hierarchical CAGGs (hourly → daily → monthly) mean each granularity only reads from the next finer level, with no repeated raw data scans
- `time_bucket()` and window functions make time-windowed analytics natural in SQL

## Industrial & Energy

**The challenge:** Manufacturing lines, power grids, and HVAC systems generate continuous streams of operational data — and downtime is expensive. Organizations need both real-time alerting and long-term trend analysis in one place.

**Key characteristics of industrial/energy data:**

- High-frequency readings from machinery and grid sensors
- Long retention requirements (regulatory compliance, warranty analysis)
- Mix of numeric telemetry and discrete state changes (machine on/off, fault codes)
- Predictive maintenance: identifying anomalies before failure

**How {C.TIMESCALE_DB}} helps:**

- {C.HYPERTABLE}}s handle continuous ingestion from dozens or hundreds of data streams
- Continuous Aggregates power trend dashboards (rolling averages, cumulative energy consumption)
- Retention + tiering policies keep decades of data accessible without runaway storage costs
- SQL-native anomaly detection: window functions for rolling standard deviation, deviation from baseline

## Application & Performance Monitoring

**The challenge:** Distributed applications produce enormous volumes of metrics, traces, and logs. Traditional monitoring tools either cap retention or become prohibitively expensive at scale.

**Key characteristics of APM data:**

- High cardinality: thousands of unique service/endpoint/host combinations
- High write throughput: metrics emitted every few seconds per service instance
- Queries are almost always recent ("last 15 minutes", "last hour") but historical comparison matters
- Correlating metrics across services requires JOIN-capable storage

**How {C.TIMESCALE_DB}} helps:**

- {C.HYPERTABLE}}s absorb continuous metric streams from any number of services
- {C.HYPERCORE}} compression keeps months of metric history without exploding storage
- SQL enables cross-service correlation queries that purpose-built metrics tools can't express
- Native integrations with Prometheus (via `pg_prometheus`) and Grafana

---

## Infrastructure Monitoring

**The challenge:** Centralized infrastructure monitoring (servers, containers, cloud resources) at scale requires storing millions of data points per minute while keeping queries fast.

**Key characteristics of infrastructure monitoring:**

- Diverse sources: bare metal servers, VMs, containers, Kubernetes pods, cloud services
- Short-term alerting on current state AND long-term capacity planning on historical trends
- Integration with existing tools (Prometheus, Telegraf, Grafana)

**How {C.TIMESCALE_DB}} helps:**

- Acts as long-term storage backend for Prometheus (replacing default local storage limitations)
- Telegraf writes directly to {C.TIMESCALE_DB}} via the PostgreSQL output plugin
- Grafana connects natively; the {C.TIMESCALE_DB}} datasource is built in
- Continuous Aggregates power capacity planning dashboards without scanning raw metrics

## Summary & Key Patterns

**Across all use cases, three patterns repeat:**

| Pattern | {C.TIMESCALE_DB}} feature |
| --- | --- |
| High-volume ingestion | {C.HYPERTABLE}}s with automatic chunking |
| Storage cost management | {C.HYPERCORE}} compression + data tiering |
| Fast analytics at any granularity | Continuous Aggregates (including hierarchical) |

## Knowledge Check

### Question 1

A company is collecting temperature and humidity readings from 10,000 sensors every 5 seconds. Which {C.TIMESCALE_DB}} feature is most important for managing the write volume efficiently?

- A) Continuous Aggregates
- B) {C.HYPERTABLE}}s with automatic time partitioning
- C) {C.HYPERCORE}} compression
- D) Retention policies

### Question 2

Which of the following use cases is the WORST fit for {C.TIMESCALE_DB}} as the primary database?

- A) Storing and querying millions of IoT sensor readings
- B) Tracking financial tick data with OHLC rollups
- C) Managing a social network's user profiles and friend connections
- D) Centralizing infrastructure metrics from a Kubernetes cluster

---

## Answers

| # | Answer | Explanation |
| --- | --- | --- |
| 1 | **B** | {C.HYPERTABLE}}s handle high write throughput by partitioning data into chunks; inserts only touch the current chunk |
| 2 | **C** | Social graphs are a relational/graph workload, not time-series. {C.TIMESCALE_DB}} is optimized for time-ordered measurements, not entity relationship modeling |
