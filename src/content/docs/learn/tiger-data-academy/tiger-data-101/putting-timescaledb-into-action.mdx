## Knowledge Check

### Question 1

Which {C.TIMESCALE_DB}} policy automatically removes data older than a specified interval, without manual intervention?

- A) Compression policy
- B) Retention policy
- C) Tiering policy
- D) Vacuum policy

### Question 2

Which of the following correctly describes a full data lifecycle in {C.TIMESCALE_DB}} from hot to expired?

- A) Ingest → Compress → Tier to object storage → Retain indefinitely
- B) Ingest (hot) → Compress (warm) → Tier to object storage (cold) → Drop (expired)
- C) Ingest → Query → Archive → Delete
- D) Compress → Ingest → Tier → Retain

### Question 3

Cloudflare chose {C.TIMESCALE_DB}} over alternatives like ClickHouse for analytics on its Zero Trust product suite. What was a primary driver?

- A) {C.TIMESCALE_DB}} requires no infrastructure management
- B) {C.TIMESCALE_DB}} has zero storage costs at scale
- C) {C.TIMESCALE_DB}}'s PostgreSQL compatibility fit their existing tooling and team expertise
- D) {C.TIMESCALE_DB}} automatically generates dashboards and alerts

---

## Answers

| # | Answer | Explanation |
| --- | --- | --- |
| 1 | **B** | `add_retention_policy()` schedules automatic chunk drops; no manual DELETEs needed |
| 2 | **B** | The full lifecycle flows from hot (recent, uncompressed) → warm (compressed with {C.HYPERCORE}}) → cold (tiered to object storage) → expired (dropped by retention policy) |
| 3 | **C** | Cloudflare favored {C.TIMESCALE_DB}} because it extends standard PostgreSQL; their existing stack, drivers, and team SQL skills all transferred directly |
