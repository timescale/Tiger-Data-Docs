{C.HYPERTABLE_CAP}s are designed for real-time analytics, they are {C.PG} tables that automatically partition your data by
time. Typically, you partition {C.HYPERTABLE}s on columns that hold time values.
[Best practice is to use `timestamptz`](https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_timestamp_.28without_time_zone.29) column type. However, you can also partition on
`date`, `integer`, `timestamp` and [UUIDv7](/reference/timescaledb/uuid-functions) types.

## Create a {C.HYPERTABLE}

Create a [{C.HYPERTABLE}](/learn/hypertables/understand-hypertables) for your time-series data using [CREATE TABLE](/reference/timescaledb/hypertables/create_table).
For [efficient queries](/build/performance-optimization/secondary-indexes), remember to `segmentby` the column you will use most often to filter your
data:

```sql
CREATE TABLE conditions (
   time        TIMESTAMPTZ       NOT NULL,
   location    TEXT              NOT NULL,
   device      TEXT              NOT NULL,
   temperature DOUBLE PRECISION  NULL,
   humidity    DOUBLE PRECISION  NULL
) WITH (
   tsdb.hypertable,
   tsdb.segmentby = 'device',
   tsdb.orderby = 'time DESC'
);

```

<CreateHypertablePolicyNote />

To convert an existing table with data in it, call `create_hypertable` on that table with
[`migrate_data` to `true`](/reference/timescaledb/hypertables/create_hypertable#arguments). However, if you have a lot of data, this may take a long time.

## Alter a {C.HYPERTABLE}

You can alter a {C.HYPERTABLE}, for example to add a column, by using the {C.PG}
[`ALTER TABLE`](https://www.postgresql.org/docs/current/sql-altertable.html) command. Some operations are not supported for {C.HYPERTABLE}s with {C.COLUMNSTORE} enabled. See [Altering {C.HYPERTABLE}s with {C.COLUMNSTORE} enabled](/build/performance-optimization/alter-update-table-schema).

### Add a column to a {C.HYPERTABLE}

You add a column to a {C.HYPERTABLE} using the `ALTER TABLE` command. In this
example, the {C.HYPERTABLE} is named `conditions` and the new column is named
`humidity`:

```sql
ALTER TABLE conditions
  ADD COLUMN humidity DOUBLE PRECISION NULL;
```

Adding a column is fast regardless of the default value. {C.PG} 11+ stores the
default in the catalog without rewriting existing rows.

### Rename a {C.HYPERTABLE}

You can change the name of a {C.HYPERTABLE} using the `ALTER TABLE` command. In this
example, the {C.HYPERTABLE} is called `conditions`, and is being changed to the new
name, `weather`:

```sql
ALTER TABLE conditions
  RENAME TO weather;
```

### Change a column data type

You can change the data type of a column in a {C.HYPERTABLE} using the `ALTER TABLE`
command. In this example, the `temperature` column data type is changed from `DOUBLE PRECISION`
to `NUMERIC`:

```sql
ALTER TABLE conditions
  ALTER COLUMN temperature TYPE NUMERIC;
```

The following restrictions apply:

- For time dimension columns, you can only change to `TIMESTAMPTZ`, `TIMESTAMP`, `DATE`,
  `INTEGER` (smallint, integer, or bigint), or `UUID`.
- You cannot change the type of columns with custom partitioning functions.
- You cannot change column types when the {C.HYPERTABLE} has {C.COLUMNSTORE} {C.CHUNK}s. Convert those {C.CHUNK}s back to {C.ROWSTORE} first. See [Altering {C.HYPERTABLE}s with {C.COLUMNSTORE} enabled](/build/performance-optimization/alter-update-table-schema).
- For columns with statistics enabled, you can only change to integer or timestamp types.
  To change to other types, first disable statistics using `disable_column_stats`.

### Drop a column

You can drop a column from a {C.HYPERTABLE} using the `ALTER TABLE` command. In this
example, the `humidity` column is dropped from the `conditions` {C.HYPERTABLE}:

```sql
ALTER TABLE conditions
  DROP COLUMN humidity;
```

You cannot drop partitioning columns.

## Delete data

Prefer [`drop_chunks()`](/reference/timescaledb/hypertables/drop_chunks/) to remove whole time
ranges instead of running large `DELETE` statements. Dropping {C.CHUNK}s is faster and avoids
table bloat:

```sql
SELECT drop_chunks('conditions', older_than => INTERVAL '30 days');
```

For automated deletion, use a
[data retention policy](/reference/timescaledb/data-retention/).

## Vacuum and bloat

Heavy `INSERT`, `UPDATE`, and `DELETE` operations cause table bloat over time. {C.PG}
autovacuum runs by default, but you may need to tune its settings for high write-rate
{C.HYPERTABLE}s. Run `VACUUM ANALYZE` manually when you need to reclaim space or refresh
query planner statistics:

```sql
VACUUM ANALYZE conditions;
```

## Drop a {C.HYPERTABLE}

Drop a {C.HYPERTABLE} using a standard {C.PG} [`DROP TABLE`](https://www.postgresql.org/docs/current/sql-droptable.html)
command:

```sql
DROP TABLE conditions;
```

All {C.CHUNK}s belonging to the {C.HYPERTABLE} are deleted. For very large {C.HYPERTABLE}s
that may time out, drop {C.CHUNK}s first with `drop_chunks()`, then drop the table.
