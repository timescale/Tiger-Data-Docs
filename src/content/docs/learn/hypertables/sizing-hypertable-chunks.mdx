import * as C from "@constants";

{C.CHUNK_CAP} size affects insert and query performance. You want {C.CHUNK}s small enough to
fit into memory so you can insert and query recent data without reading from disk. However,
too many small {C.CHUNK}s can slow query planning and reduce {C.COLUMNSTORE} effectiveness.

## How the {C.CHUNK} interval works

The {C.CHUNK} interval is the time range each {C.CHUNK} covers. It determines how many
{C.CHUNK}s you get for a given time range:

- **Default**: 7 days for timestamp columns. For integer columns, defaults vary by type
  (`smallint`: 10,000, `integer`: 100,000, `bigint`: 1,000,000).
- **New {C.CHUNK}s only**: Changing the interval with
  [`set_chunk_time_interval()`](/reference/timescaledb/hypertables/set_chunk_time_interval)
  affects only {C.CHUNK}s created after the change. Existing {C.CHUNK}s keep their original
  boundaries.
- **Minimum**: For timestamp types, intervals shorter than 1 second trigger a warning.

## Sizing guideline

Set `chunk_interval` so that the indexes of {C.CHUNK}s currently being ingested into fit
within 25% of main memory (`shared_buffers`).

{C.PG} builds indexes on the fly during ingestion. When an index doesn't fit in memory, it is
constantly flushed to disk and read back, wasting I/O that would otherwise be used for writes.

**Example**: On a system with 64 GB of memory, `shared_buffers` is typically ~16 GB.

- If index growth is approximately 2 GB per day, a 7-day interval is appropriate
  (2 GB x 7 = 14 GB, fits in 16 GB).
- If index growth is around 10 GB per day, use a 1-day interval
  (10 GB, fits in 16 GB).

## Active vs inactive {C.CHUNK}s

- **Active** {C.CHUNK}s receive new writes and their indexes should fit comfortably in cache.
- **Inactive** {C.CHUNK}s are older and mostly read-only — they can rely more on disk,
  especially after conversion to {C.COLUMNSTORE}.

## Too many {C.CHUNK}s

Having too many {C.CHUNK}s in the system has costs:

- **Query planning**: The planner must evaluate each {C.CHUNK} to decide whether to include
  or skip it. More {C.CHUNK}s means more planning time.
- **{C.COLUMNSTORE_CAP}**: Very small {C.CHUNK}s compress less effectively because there is
  less data to find patterns in.
- **System limits**: Limit the number of {C.HYPERTABLE}s in your {C.SERVICE_SHORT} — tens of
  thousands of {C.HYPERTABLE}s is not recommended.

## Setting the {C.CHUNK} interval

Set the interval at creation time:

```sql
CREATE TABLE sensor_data (
  time        TIMESTAMPTZ NOT NULL,
  device_id   INT,
  value       DOUBLE PRECISION
) WITH (
  timescaledb.hypertable,
  timescaledb.chunk_interval = '1 day'
);
```

Or change it for an existing {C.HYPERTABLE}:

```sql
SELECT set_chunk_time_interval('sensor_data', INTERVAL '1 day');
```

You can also set a global default for all new {C.HYPERTABLE}s:

```sql
SET timescaledb.default_chunk_time_interval = '1 day';
```
