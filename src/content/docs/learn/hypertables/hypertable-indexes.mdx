Indexes on {C.HYPERTABLE}s work the same as on regular {C.PG} tables, with a few
{C.TIMESCALE_DB}-specific behaviors.

## Default indexes

When you create a {C.HYPERTABLE}, {C.TIMESCALE_DB} automatically creates a B-tree index on the
partition column (time descending). If the {C.HYPERTABLE} has a space dimension, a second
composite index on (space column, time descending) is also created. You can disable this with
`timescaledb.create_default_indexes = false` if you plan to add custom indexes after
loading data.

Indexes speed up `SELECT` queries but slow down `INSERT` operations and increase storage.
Drop any indexes you don't actively use.

## Supported index types

{C.HYPERTABLE}s support all {C.PG} index types:

- **B-tree** — the default. Best for equality and range filters on time, device IDs, and
  other scalar columns.
- **Hash** — useful for equality-only lookups.
- **GIN** — for JSONB, arrays, and full-text search columns.
- **GiST** — for geometric, range, and full-text search data.
- **BRIN** — block range indexes, useful for very large append-only tables.

## Unique indexes and primary keys

Any `UNIQUE` or `PRIMARY KEY` index must include the partition column. This is a
{C.TIMESCALE_DB} requirement because uniqueness is enforced per {C.CHUNK}. See
[Primary keys, time columns, and uniqueness](/learn/data-model/primary-keys-time-and-uniqueness)
for details.

## Per-{C.CHUNK} index builds

Use the `timescaledb.transaction_per_chunk` option when creating indexes to build per
{C.CHUNK} in separate transactions, reducing lock contention:

```sql
CREATE INDEX idx_device_time ON sensor_data (device_id, time DESC)
  WITH (timescaledb.transaction_per_chunk = true);
```

## {C.COLUMNSTORE_CAP} and indexes

{C.PG} indexes (including B-tree) are kept on {C.CHUNK}s converted to {C.COLUMNSTORE} and
continue to work for queries. {C.TIMESCALE_DB} also uses batch-level metadata (min/max values)
to skip irrelevant batches during scans. For best {C.COLUMNSTORE} query performance, tune
segmenting and ordering in addition to indexes. See
[Improve query and upsert performance](/build/performance-optimization/secondary-indexes) for
details.
