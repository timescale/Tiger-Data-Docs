Time-series data is relentless. It grows at an ever-increasing rate and quickly
becomes expensive and unwieldy to store and query. Managing your time-series data
across its entire lifecycle is essential to building high-performance,
cost-effective applications.

{C.TIMESCALE_DB}, a time-series database built on {C.PG}, provides purpose-built
features for every stage of the data lifecycle, from the moment data is ingested
to when it is archived or dropped. These features work together so you can
maintain query performance, control storage costs, and automate routine
maintenance — without building custom pipelines or relying on external tools.

For definitions of all terms used in this guide, see the [glossary](/learn/glossary).

## The five phases

The data lifecycle describes the journey your data takes as it ages. Each phase
maps to a set of {C.TIMESCALE_DB} features that help you manage that stage
efficiently:

| Phase                            | What happens                                    | {C.TIMESCALE_DB} features                                                                                                                         |
| -------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Ingest and store**          | Data arrives and is written to disk             | [{C.HYPERTABLE_CAP}s](/learn/hypertables/understand-hypertables), [{C.CHUNK}s](/learn/chunks/understanding-chunks)                                |
| **2. Query recent data**         | Applications read and analyze fresh data        | SQL, [`time_bucket`](/reference/timescaledb/hyperfunctions/time-series-utilities/time_bucket), [indexes](/learn/hypertables/hypertable-indexes)   |
| **3. Create aggregated rollups** | Summarize data at coarser intervals             | [{C.CAGG_CAP}s](/learn/continuous-aggregates), [downsampling](/build/data-management/example-downsample-and-compress)                             |
| **4. Compress and archive**      | Compress and move aging data to cheaper storage | [{C.COLUMNSTORE_CAP}](/learn/columnar-storage/compression-methods), [tiered storage](/learn/data-lifecycle/storage/about-storage-tiers)          |
| **5. Drop old data**             | Remove data that is no longer valuable          | [Retention policies](/learn/data-lifecycle/data-retention/about-data-retention), [`drop_chunks`](/reference/timescaledb/hypertables/drop_chunks) |

## Phase 1: Ingest and store data efficiently

When it comes to time-series data, storing data as quickly and as efficiently as
possible is the foundation of everything else. {C.TIMESCALE_DB} achieves this
through [{C.HYPERTABLE}s](/learn/hypertables/understand-hypertables), {C.PG}
tables that are automatically partitioned by time into smaller tables called
[{C.CHUNK}s](/learn/chunks/understanding-chunks). Each {C.CHUNK} holds data for a
specific time range, such as one week.

Because only recent {C.CHUNK}s are in memory, ingest throughput stays high even
as overall data volume grows. You interact with {C.HYPERTABLE}s using standard
SQL — there is no new query language to learn.

Key considerations at this stage:

- **Choose the right {C.CHUNK} interval.** The default is 7 days. Aim for each
  {C.CHUNK} to be about 25% of available memory. See
  [sizing {C.HYPERTABLE} {C.CHUNK}s](/learn/hypertables/sizing-hypertable-chunks).
- **Plan for {C.COLUMNSTORE} conversion.** As {C.CHUNK}s age past their "hot"
  query window, you can convert them to the
  [{C.COLUMNSTORE}](/learn/columnar-storage/compression-methods) for significant
  storage savings. See [Phase 4](#phase-4-compress-and-archive-older-data).

## Phase 2: Query recent data

Once data is stored, you need to query it efficiently. {C.TIMESCALE_DB} extends
the {C.PG} query planner with time-series-aware optimizations. Queries on recent
data benefit from {C.CHUNK} exclusion, an optimization where the planner
automatically skips any {C.CHUNK}s that fall outside your query's time range.

For time-series analysis, the
[`time_bucket`](/reference/timescaledb/hyperfunctions/time-series-utilities/time_bucket)
function is a {C.TIMESCALE_DB} SQL function that groups rows into fixed time
intervals (1 minute, 1 hour, 1 day), making it easy to compute aggregates over
time windows:

```sql
SELECT
  time_bucket('1 hour', time) AS bucket,
  device_id,
  avg(temperature) AS avg_temp
FROM conditions
WHERE time > now() - INTERVAL '7 days'
GROUP BY bucket, device_id
ORDER BY bucket DESC;
```

As your dataset grows and queries over longer time ranges slow down, it is time
to move to the next phase.

## Phase 3: Create aggregated rollups

As data ages, individual data points often matter less than statistical
summaries. [{C.CAGG_CAP}s](/learn/continuous-aggregates) solve this. A
{C.CAGG} is a materialized view that {C.TIMESCALE_DB} keeps up to date
automatically — it pre-computes and stores the results of an aggregate query
(such as averages or counts) and incrementally refreshes only the
{C.TIME_BUCKET}s where underlying data changed, not the entire view.

Unlike standard {C.PG} materialized views that recompute everything on each
refresh, {C.CAGG}s are efficient even over very large datasets.

```sql
CREATE MATERIALIZED VIEW conditions_daily
WITH (timescaledb.continuous) AS
SELECT
  time_bucket('1 day', time) AS day,
  device_id,
  avg(temperature) AS avg_temp,
  min(temperature) AS min_temp,
  max(temperature) AS max_temp
FROM conditions
GROUP BY day, device_id;

SELECT add_continuous_aggregate_policy('conditions_daily',
  start_offset => INTERVAL '7 days',
  end_offset => INTERVAL '1 day',
  schedule_interval => INTERVAL '1 day');
```

{C.CAGG_CAP}s are stored as {C.HYPERTABLE}s themselves, so they benefit from all
the same features — {C.COLUMNSTORE} conversion, tiered storage, and retention
policies.

You can also create
[hierarchical {C.CAGG}s](/learn/continuous-aggregates/hierarchical-continuous-aggregates),
where one {C.CAGG} reads from another instead of from raw data, to build
multi-resolution rollup pipelines (for example, hourly to daily to monthly).

## Phase 4: Compress and archive older data

As {C.CHUNK}s age past their "hot" query window, you can dramatically reduce
storage costs in two ways: convert {C.CHUNK}s to the {C.COLUMNSTORE} for
compression, and move them to cheaper storage tiers.

### Convert to the {C.COLUMNSTORE}

The [{C.COLUMNSTORE}](/learn/columnar-storage/compression-methods) is a columnar
storage format that compresses your data. Converting older {C.CHUNK}s to the
{C.COLUMNSTORE} can reduce storage by up to 98% while improving analytical query
performance.

Use a
[{C.COLUMNSTORE} policy](/reference/timescaledb/hypercore/add_columnstore_policy)
to automatically convert {C.CHUNK}s after a set interval:

```sql
SELECT add_columnstore_policy('conditions', after => INTERVAL '7 days');
```

Once a {C.CHUNK} is in the {C.COLUMNSTORE}, it still supports inserts and
updates — [hypercore](/learn/columnar-storage/understand-hypercore), the
underlying storage engine, handles this transparently.

### Tier to low-cost storage

Even with the {C.COLUMNSTORE} and {C.CAGG}s, there are cases where you need
access to raw data for long periods — for compliance, model training, or
historical analysis. Rather than paying for high-performance storage you rarely
query, you can move older {C.CHUNK}s to cheaper storage.

#### On {C.CLOUD_LONG}

[Tiered storage](/learn/data-lifecycle/storage/about-storage-tiers) is a
{C.CLOUD_LONG} feature that automatically moves older {C.CHUNK}s from
high-performance storage to a low-cost object storage tier backed by S3 and
Azure Blob. Data is stored in Apache Parquet format with automatic {C.CHUNK},
row group, and column pruning for efficient queries. You set a policy and
{C.CLOUD_LONG} handles the rest:

```sql
SELECT add_tiering_policy('conditions', INTERVAL '6 months');
```

Tiered data remains queryable via standard SQL — no separate query path or
external pipeline required.

#### On self-hosted {C.TIMESCALE_DB}

Use {C.PG}
[tablespaces](https://www.postgresql.org/docs/current/manage-ag-tablespaces.html)
with the [`move_chunk`](/reference/timescaledb/hypertables/move_chunk) function
to relocate {C.CHUNK}s to slower, cheaper disks. You can automate this with a
[custom {C.JOB}](/build/data-management/example-tiered-storage).

## Phase 5: Drop old data

At some point, raw data is no longer valuable. Keeping it around slows down
queries, inflates storage costs, and adds maintenance overhead.
[Retention policies](/learn/data-lifecycle/data-retention/about-data-retention),
scheduled rules that automatically drop {C.CHUNK}s older than a threshold you
define, automate this process.

```sql
SELECT add_retention_policy('conditions', INTERVAL '12 months');
```

Because {C.TIMESCALE_DB} drops entire {C.CHUNK}s rather than deleting rows one
by one, retention is nearly instantaneous and avoids the performance overhead
of `DELETE` + `VACUUM`.

<Callout variant="warning">
  If you use {C.CAGG}s, make sure your retention policy interval is longer than
  the {C.CAGG} refresh window. Otherwise, the refresh sees the deleted raw data
  and removes the aggregate too. For details, see [data retention with {C.CAGG}
  s](/learn/data-lifecycle/data-retention/data-retention-with-continuous-aggregates).
</Callout>

## Putting it all together

A complete lifecycle strategy combines multiple phases. Here is an example
configuration for a `conditions` {C.HYPERTABLE} that stores device telemetry:

```sql
-- Phase 1: Create the hypertable
SELECT create_hypertable('conditions', by_range('time'));

-- Phase 3: Create a daily rollup
CREATE MATERIALIZED VIEW conditions_daily
WITH (timescaledb.continuous) AS
SELECT time_bucket('1 day', time) AS day, device_id,
       avg(temperature), min(temperature), max(temperature)
FROM conditions
GROUP BY day, device_id;

SELECT add_continuous_aggregate_policy('conditions_daily',
  start_offset => INTERVAL '7 days',
  end_offset => INTERVAL '1 day',
  schedule_interval => INTERVAL '1 day');

-- Phase 4a: Convert to columnstore after 7 days
SELECT add_columnstore_policy('conditions', after => INTERVAL '7 days');

-- Phase 4b: Tier data to low-cost storage after 3 months (Tiger Cloud)
SELECT add_tiering_policy('conditions', INTERVAL '3 months');

-- Phase 5: Drop raw data after 12 months
SELECT add_retention_policy('conditions', INTERVAL '12 months');
```

With this configuration:

- Raw data is converted to the {C.COLUMNSTORE} after 7 days, reducing storage by up to 98%
- Daily summaries are always available via the {C.CAGG}
- After 3 months, raw {C.CHUNK}s move to low-cost object storage
- After 12 months, raw {C.CHUNK}s are dropped entirely
- The daily {C.CAGG} retains its data independently of the raw data

All of this runs automatically via scheduled {C.JOB}s — no cron, no external
scripts, no manual intervention.

## Automate and customize

Every lifecycle feature supports scheduled automation through the
{C.TIMESCALE_DB} [job scheduler](/build/data-management/about-automation). A
{C.JOB} is a user-defined or built-in stored procedure that {C.TIMESCALE_DB}
runs on a schedule you configure — policies like retention, {C.COLUMNSTORE}
conversion, and {C.CAGG} refresh are all implemented as {C.JOB}s under the hood.

If the built-in policies don't cover your use case, you can create
[custom {C.JOB}s](/build/data-management/create-and-manage-jobs). Common examples include:

- [Generic retention across all {C.HYPERTABLE}s](/build/data-management/example-generic-retention)
- [Automated tablespace management](/build/data-management/example-tiered-storage)
- [Downsampling and converting to {C.COLUMNSTORE} in one step](/build/data-management/example-downsample-and-compress)
